## 1. `refresh_cli` 完整流程（含 external wrapper contract preflight 與 atomic commit）

```mermaid
flowchart TD
    Start(["python -m impact_orch.refresh_cli &lt;system_id&gt; [system_id ...]"]) --> Health{"rag_client.health()<br/>Impact 服務在線？"}
    Health -- 否 --> Fail["提示先啟動 uvicorn service.api:app<br/>結束"]
    Health -- 是 --> Loop["for system_id in system_ids"]

    Loop --> Call["rag_client.refresh(system=system_id)<br/>→ POST /refresh"]
    Call --> Api["service/api.py：refresh(req)"]
    Api --> RS["analyze_service.refresh_source(source)"]

    RS --> Ensure["repo_manager.ensure_repo(source, refresh=True)"]
    Ensure --> Cloned{"repo 是否已 clone？<br/>（data/repos/&lt;project&gt;/&lt;repo&gt;）"}
    Cloned -- 否 --> Clone["AzureDevOpsFetcher.fetch()：clone"]
    Cloned -- 是 --> Pull["AzureDevOpsFetcher.fetch(update=True)：git pull"]
    Clone --> Scan
    Pull --> Scan

    Scan["get_or_scan(root, refresh=True)<br/>略過快取，強制重新掃描"] --> Parser["ProjectScanner(root).scan_project(analyze_sp=False)"]
    Parser --> Detect["ProjectTypeDetector 偵測框架<br/>→ 動態啟用 CSharpParser/ASPXParser/RazorParser/VueParser"]
    Detect --> Extract["解析方法/呼叫鏈/SP 名稱/資料表/View 層欄位<br/>（不連資料庫）"]
    Extract --> Save["_save()：覆寫 data/scan_cache/&lt;hash&gt;.pkl + .meta.json"]

    Save --> Preflight["run_contract_preflight()<br/>依本次 scans + system 目前設定的 selector 比對 external wrapper contract registry<br/>onboarding_status：selected／not_required／created／reused／conflicted／preflight_failed"]
    Preflight --> Reconcile["reconcile_refresh_wrappers()<br/>用 preflight 判定的 formal selector/registry<br/>分類本次觀察到的 external wrapper 呼叫 → wrapper_summary"]
    Reconcile --> GuardCheck{"完整 system refresh（非 --program 局部更新）<br/>且有 database（system_id）<br/>且 onboarding_status ∈ {created, reused}？"}
    GuardCheck -- 否 --> SkipCommit["contract_transaction = not_required<br/>（不 onboard 新 contract，僅回傳分類結果）"]
    GuardCheck -- 是 --> Commit["commit_staged_contract_transaction()<br/>registry.json + system_catalog.json<br/>atomic two-file commit：先寫 transaction manifest，<br/>依序替換兩個檔案並驗證 hash，任一步失敗即 rollback"]
    SkipCommit --> Resp
    Commit --> Resp["回傳 source_root、files、inline facts 計數、<br/>wrapper_summary、contract_transaction、<br/>analysis_manifest.contract_revision_reference"]
    Resp --> Print["CLI 印出 ✅ system_id 更新完成"]
    Print --> NextCheck{"還有下一個 system_id？"}
    NextCheck -- 是 --> Loop
    NextCheck -- 否 --> End(["結束"])
```

> ⚠️ **常見誤解**：`get_or_scan(refresh=True)` 本身就會**自動覆寫**磁碟快取，不需要手動刪除 `data/scan_cache/*.pkl`。但如果剛編輯過 `code_analyzer/`／`service/` 底下的解析器程式碼，**已在執行的 uvicorn 服務仍是記憶體裡的舊程式碼**（Python 不會熱重載），必須先重啟服務才能讓 `refresh_cli` 真正套用新邏輯。
>
> 💡 **preflight／atomic commit**：`refresh_source()` 每次 refresh 都會跑 contract preflight 與 wrapper reconciliation，不需另外觸發；`onboarding_status=preflight_failed` **不會**讓整個 refresh 失敗，只會讓對應的 wrapper 呼叫留在 unresolved/review，其餘分析照常完成。只有「完整 system refresh（`--program` 局部更新一律不會）＋ 該 system 有 `database`＋ `onboarding_status` 為 `created` 或 `reused`」三個條件同時成立時，才會呼叫 `commit_staged_contract_transaction(trigger="refresh")` 把 staged 的 registry／catalog 正式寫入磁碟。人工的 `accept_external_wrapper_contract.py`（見 [進階手冊.md](./進階手冊.md#external-wrapper-contract-維護)）的 `--apply` 路徑現在也走同一個 `commit_staged_contract_transaction()`，只是傳入 `trigger="manual_acceptance"`——兩條入口在**何時觸發**上仍互不取代（refresh 是「自動偵測到足夠證據就自動沿用/建立」，`accept_*` 工具是「人工審核後明確套用」），但在**如何寫入**兩個檔案這件事上已共用同一套 atomic two-file commit／recovery 機制；manifest 裡的 `trigger` 欄位就是唯一用來分辨是哪條入口寫入的依據。

> 💡 之後問問題時，`sp_fetcher.py`／`view_fetcher.py`／`udf_fetcher.py` 讀取已驗證的本機 SQL cache；正式 Graph/path consumer 不會因為缺少某個物件而退回逐物件即時查詢。若 cache 不存在、過期或 database scope 不符，正式 Graph operation 會回報 `sql_execution_graph_required`，而不是猜測 relationship。
>
> ⚠️ 資料庫是**多系統共用資源**（不像 git repo 是每個系統各自一份），跟 `refresh_cli`（更新程式碼）是不同軸的更新指令，需要個別觸發。
>
> 📌 **位置參數是資料庫名稱，不是系統代號**（ADR-0006）：`refresh_sql_cli STC` 掃的是名叫 `STC` 的資料庫，要掃「STC 系統宣告依賴的每個資料庫」請改用 `--system_id STC`。三種寫法（資料庫名稱、`--system_id`、`--server`/`--database`）不能混用；`--system_id` 展開前會先核對每筆宣告是否真的登錄過（ADR-0003），核對失敗時不掃描任何一筆。`GET /scan_records`（Impact 端新端點）只在真的要列出多台候選時才會被打一次，一台候選或沒有 terminal 的報錯路徑完全不碰它。

## 3. Agentic 模式（run_cli 模式 4／5）詳細步驟：AI 介入點

模式 4（CLI 預設）與模式 5（同一套流程，額外啟用 Phase 1 code routing）都走 `run_impact_analysis_agentic`（位於 spec-rag 端 `impact_orch/orchestrator.py`／`impact_orch/agent_tools.py`）。兩者差別只在**給 agent 幾個工具**：模式 4 給全部 7 個（`search_specs`、`search_specs_by_sp`、`search_specs_by_table`、`search_specs_scoped`、`analyze_system`、`get_flow_chains`、`collect_path_evidence`）；模式 5 拿掉兩個 exact 反查工具（改成在呼叫 agent 之前就用程式先跑完），只給 5 個。

內部有**五種完全不同性質的「AI/模型」角色**，很容易被混為一談：

| 角色 | 使用的模型 | 是不是真正的「推理判斷」 | 出現在哪一步 |
|---|---|---|---|
| 1. Router Agent | `cfg.AGENT_ROUTER_MODEL`（`FunctionAgent`） | ✅ 真的 LLM 推理 | 工具選擇、system scope／澄清判斷與工具參數 |
| 2. Embedding 相似度 | `cfg.OPENAI_EMBEDDING_MODEL` | ❌ 不是推理，是固定的向量 cosine 相似度計算 | 候選錪點、程式碼片段、畫面區塊與規格書分段挑選 |
| 3. 片段一句話摘要 | `cfg.OPENAI_LOW_MODEL` | ✅ 是 LLM，但只做摘要不做決策 | SP/View/UDF/前端 script 的「AI 摘要」（`USE_CODE_ANNOTATION=true` 時） |
| 4. 證據充分性裁決 | `cfg.OPENAI_LOW_MODEL` | ✅ 是 LLM，但只判「還缺什麼類型的證據」，不改寫 evidence | 每一輪 agent 跑完之後（見下方證據充分性迴圈） |
| 5. 最終整合答案 | `cfg.OPENAI_MODEL`（`ai_reasoner.reason()`） | ✅✅ 真正做「這是哪個分支/這條鏈才對」的實質判斷 | 完整 context 組裝後 |


### 環繞在外的三道閘門

上圖的 ①～⑥ 是「一輪」。實際跑起來還有三道環繞在外面的機制，都在 spec-rag 端，不改變 evidence 判定：

| 機制 | 什麼時候發生 | 做的事 |
|---|---|---|
| **Object Kind Ambiguity（物件種類歧義）** | ① 之前，程式化判斷，不呼叫 agent | 問題裡出現一個沒有標示種類的名稱，而它同時可能是預存程序、資料表或程式代號時，直接列出每一種解讀請使用者選（terminal 用上下鍵，非 terminal 改成輸入關鍵字），不猜、也不同時全查 |
| **Locked Analysis Scope（分析範圍鎖定）** | 第一輪 agent 跑完之後，立刻鎖定 | 把當下的候選 system/program 快照起來。之後的輪次只能在鎖定範圍內深挖：`search_specs`／`search_specs_by_sp`／`search_specs_by_table` 一律拒絕，改用 `search_specs_scoped`（只讀鎖定範圍內程式的規格書）；`get_flow_chains` backward 反查到範圍外的程式會被濾掉並記成一筆 Evidence Gap |
| **Evidence Sufficiency Loop（證據充分性迴圈）** | 每一輪 ①～④ 跑完之後 | 用低成本模型判斷「證據夠不夠」；不夠就指出缺哪一類（規格書／C# 原始碼／SP 定義／關係鏈／path evidence），對應到該呼叫的工具，再跑一輪。最多 `AGENT_MAX_SUFFICIENCY_ROUNDS` 輪；某一輪完全沒有新增證據就直接停（不再多花一次裁決） |

> 💡 停止原因（`sufficient`／`round_limit`／`no_progress`／`empty_scope` 等）與每一次 HTTP 重試，都會寫進最終報告末尾的「證據蒐集」附錄，不經過 AI 改寫。查不到的東西會列成 **Evidence Gap**，並附一句「換句話怎麼問」的建議。

### `get_flow_chains`：forward／backward 兩種方向

| 方向 | 觸發時機 | 需要的參數 | 內部行為 |
|---|---|---|---|
| `forward` | 問「某個畫面操作／UI 動作」的影響（含回復/修正類問題） | `program_name` + agent 判斷的 `ui_action_hint` | 取得 `view_layer` → 攤平候選 → embedding 依 `ui_action_hint` 排序取前 5 → 逐一組鏈到 SP/資料表 |
| `backward` | 問「異動某張資料表/欄位」會影響哪些程式 | `table_name` | 直接反查 `(program, method)` 候選 |

兩種方向都只有在**已經對該 system 呼叫過 `analyze_system` 之後**才允許呼叫，且都受 `AGENT_MAX_FLOW_CHAIN_CALLS` 呼叫次數上限保護。`forward` 對 GridView 列命令按鈕（`OnRowDeleting`/`OnRowEditing`/`OnRowUpdating`/`OnRowCancelingEdit`/`OnRowCommand`）有特別處理：這類事件語法上只掛在 grid 容器本身，`_flatten_ui_field_events()` 會把該 grid 底下「有文字但沒有自己事件」的每個欄位（如按鈕文字「取消」）跟容器層級的 handler 配對，合成出「真實按鈕文字 + 真實 handler」的候選。

## 4. `find_by_table` 寫入反查（access_type／巢狀路徑／evidence）流程

`/find_by_table` 同時處理 C# inline SQL facts 與 database-scoped `SQL Execution Graph`。`query_table_accesses()` 依 typed operation、lineage 與 nested CALL branch 回傳 `access_type`、`path_id` 與 evidence；`proven` 才是 confirmed relationship，`likely`/`unresolved` 只留在 diagnostics 或 candidate context。

```mermaid
flowchart TD
    Start(["find_by_table(req)<br/>table_name + database=system_id"]) --> Direct

    subgraph Step1["① 直接命中：比對 C# inline SQL facts"]
        Direct["逐一比對 scan inline table facts"] --> DirectHit["命中 → access_type = READ/INSERT/UPDATE/DELETE"]
    end

    DirectHit --> HasDb{"req.database 有值？"}
    HasDb -- 否 --> InlineOnly["只回傳 C# inline facts<br/>不宣稱 Graph-backed relationship"]
    HasDb -- 是 --> LoadCache["sql_cache_store.load_cached(database)<br/>驗證 database scope / graph version"]

    subgraph Step2["② Graph query：typed operation／lineage／nested CALL"]
        LoadCache --> Query["query_table_accesses(graph, table_name)"]
        Query --> Classify["依實際 DML 分類 access_type<br/>READ / INSERT / UPDATE / DELETE / WRITE_INDIRECT"]
        Classify --> Join["CSharpAnalysisGateway<br/>join proven source invocation 與 Graph access"]
        Join --> HitObjects["TableMatchProgram：via_sp、path_id、sp_chain、source_span"]
    end

    Join --> Evidence["附加 evidence、reason、database attribution<br/>likely / unresolved 不升格"]

    subgraph Step3["③ 巢狀路徑：A 呼叫 B，B 才寫入這張表"]
        HitObjects --> Nested["Graph nested CALL branches<br/>沿 typed CALL edge 展開"]
        Nested --> Visited["visited path set 防循環呼叫（A→B→A）"]
        Visited --> Indirect["保留完整 sp_chain + path_id<br/>間接寫入標記 WRITE_INDIRECT"]
    end

    InlineOnly --> WriteOnly{"req.write_only？"}
    Evidence --> WriteOnly
    Indirect --> WriteOnly
    WriteOnly -- 是 --> Filter["只保留寫入類（INSERT/UPDATE/DELETE/WRITE_INDIRECT）的命中"]
    WriteOnly -- 否 --> AllMatches["回傳全部命中"]
    Filter --> Resp(["FindByTableResponse.matches"])
    AllMatches --> Resp
```

> 💡 **Graph readiness 是查詢前置條件**：`database` 對應的 SQL cache 必須通過版本、Graph version 與 database scope 驗證；缺失或過期時正式 endpoint 回 HTTP 409（`sql_execution_graph_required`）。`/refresh_sql/status/{job_id}` 的 `completed` 只表示 refresh worker 結束，不取代這個 readiness gate。
>
> 💡 **`write_only` 篩選**：C# inline SQL 的 `INSERT`/`UPDATE`/`DELETE` 與 Graph 的 `WRITE`/`WRITE_INDIRECT`/具體 DML operation 都可納入寫入篩選；無法判斷的 evidence 不會因 `write_only` 而被猜成寫入。CLI 模式 3（資料表反查）目前不暴露這個開關（維持回傳讀寫命中），API 與 Agent tool 可傳 `write_only=True`。

### 發請求之前：Candidate Database Set（候選資料庫集合）

上圖是 **一個資料庫** 的處理流程。一個 System 可能宣告好幾個資料庫，舊做法是逐個都發一次請求、逐個都把快取整份讀開（最大一份約 105 MB）。現在 spec-rag 先做一步剪枝：

```mermaid
flowchart TD
    Q(["find_by_sp ／ find_by_table"]) --> Declared["Lookup Database Set：該 System 在 catalog 宣告的每個 (server, database)"]
    Declared --> Empty{"有宣告任何資料庫？"}
    Empty -- 否 --> AsIs["不問 /locate_object<br/>（沒有可以交集的對象）"]
    Empty -- 是 --> Locate["POST /locate_object<br/>{object_name, kind: sp／table}"]
    Locate --> Fail{"呼叫成功？"}
    Fail -- "否（連不上／逾時／回應不可解析）" --> AsIs2["退回全量查詢（與以前一樣）<br/>不報錯、不中斷"]
    Fail -- 是 --> Intersect["Candidate Database Set＝<br/>（matched ∪ unindexed）∩ Lookup Database Set"]
    Intersect --> Pruned{"剪完還剩幾個？"}
    Pruned -- "≥ 1" --> Fan["只對這幾個資料庫發請求"]
    Pruned -- "0" --> InlineOne["只發一次不帶 database 的請求<br/>（C# inline SQL 這一關不能因剪枝而遺漏）"]
    AsIs --> Fan2["逐個宣告的資料庫都發請求"]
    AsIs2 --> Fan2
```

> 💡 **剪枝是權威的，但只會變慢不會變錯**：`/locate_object` 只看 Object Location Index，完全不開 SQL 快取。`matched`＝索引新鮮且持有這個名稱；`unindexed`＝索引缺席／過期／版本不符，服務不能代答，必須整份讀；**兩份都沒出現的資料庫才是真的被剪掉**。索引建立時寧可多報不可少報，所以一份過期的索引只會少剪一點（多讀一份快取），不會把真正的答案剪掉。見 `docs/adr/0012-object-location-index-authoritative-pruning.md`。
