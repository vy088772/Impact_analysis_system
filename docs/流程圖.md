## 1. 整體資料流程（靜態掃描快取 vs 即時資料庫查詢）

同一次「問問題」裡，資料其實來自兩種完全不同時機的來源：

- **靜態掃描結果**（方法、呼叫鏈、SP/資料表**名稱**、View 層欄位）：來自 [`data/scan_cache/*.pkl`](../data/scan_cache)，只有跑 `refresh_cli` 時才會重新產生。
- **SP/View 完整定義**：優先讀本機 [`data/sql_cache/*.json`](../data/sql_cache)（由獨立指令 `refresh_sql_cli` 落地），快取沒有才 fallback 即時連線 SQL Server。
- **FK 連動表**：每次問問題都**即時連線 SQL Server**現撈，不快取（目前尚未落地化，相對輕量）。

```mermaid
sequenceDiagram
    participant User as 使用者
    participant CLI as impact_orch.run_cli
    participant Impact as service/api.py（/analyze）
    participant Svc as analyze_service.analyze()
    participant Cache as scan_store.get_or_scan()<br/>（data/scan_cache/*.pkl）
    participant SP as sp_fetcher.fetch_sp_definitions()
    participant VF as view_fetcher.fetch_view_definitions()
    participant SqlCache as sql_cache_store.load_cached()<br/>（data/sql_cache/*.json）
    participant FK as fk_resolver.resolve_fk_related()
    participant DB as SQL Server
    participant Ctx as context_builder.build_context()
    participant AI as ai_reasoner.reason()
    participant Ground as grounding.verify_grounding()

    User->>CLI: 輸入問題
    CLI->>Impact: rag_client.analyze(program_names, refresh=False)
    Impact->>Svc: analyze_service.analyze(req)
    Svc->>Cache: get_or_scan(root, refresh=False)
    Cache-->>Svc: 方法/呼叫鏈/SP 名稱/View 層欄位（讀快取，不連 DB）

    opt include_sp_defs=true
        Svc->>SP: fetch_sp_definitions(sp_names)
        SP->>SqlCache: 優先查本機 SQL 快取
        alt 快取命中
            SqlCache-->>SP: SP 完整定義/參數（不連 DB）
        else 快取沒有（從未 refresh_sql_cli 或新增的 SP）
            SP->>DB: fallback 即時連線查 T-SQL 定義
            DB-->>SP: 完整定義/參數/引用資料表
        end
        SP-->>Svc: sp_definitions

        Svc->>VF: fetch_view_definitions(table_names)
        VF->>SqlCache: 只讀快取，比對 table_names 中哪些其實是 View
        SqlCache-->>VF: View 完整定義（沒快取時回空清單，不連線）
        VF-->>Svc: view_definitions
    end

    opt fk_depth > 0
        Svc->>FK: resolve_fk_related(table_names)
        FK->>DB: 查 sys.foreign_keys（不快取）
        DB-->>FK: 連動資料表
        FK-->>Svc: related_tables
    end

    Svc-->>Impact: AnalyzeResponse（JSON）
    Impact-->>CLI: programs / not_found / source_root

    CLI->>Ctx: build_context(user_query, spec_context, impact_results)
    Ctx-->>CLI: 完整上下文（依 USE_CODE_EMBEDDING 挑相關片段/畫面區塊；SP/View 定義視 USE_CODE_ANNOTATION 附上一句話 AI 摘要）

    opt RUN_AI=true
        CLI->>AI: ai_reasoner.reason(ctx)
        AI-->>CLI: 整合答案
        CLI->>Ground: verify_grounding(answer, impact_results)
        Ground-->>CLI: 可疑名稱清單（0 token，程式化比對）
    end
```

> 💡 **重點**：`refresh_cli` 更新的是**靜態掃描快取**（方法、呼叫鏈、SP/資料表名稱、View 層欄位）；`refresh_sql_cli` 更新的是 **SQL 快取**（SP/View/Function 完整定義、資料表 Schema）——兩者是不同軸的獨立更新指令（資料庫是多系統共用資源，不跟某個 system_id 綁定）。FK 連動表仍然每次即時查，沒有對應的更新指令。

## 2. `impact_orch.run_cli` 流程（互動式 CLI）

```mermaid
flowchart TD
    Start(["python -m impact_orch.run_cli"]) --> Health{"_check_service()<br/>Impact 服務在線？"}
    Health -- 否 --> HealthFail["提示先啟動 uvicorn service.api:app<br/>結束"]
    Health -- 是 --> Menu{"主選單<br/>main() 的 while 迴圈"}

    Menu -- "1" --> M1["_mode_direct()"]
    Menu -- "2" --> M2["_mode_rag()"]
    Menu -- "3" --> M3["_mode_agentic()"]
    Menu -- "0" --> Exit(["離開"])

    subgraph 模式1["模式 1｜直接輸入程式名（快速，不需 RAG/AI）"]
        M1 --> M1a["列出系統（_list_systems）→ 輸入 system_id"]
        M1a --> M1b["輸入程式名（多個逗號分隔）"]
        M1b --> M1c["rag_client.analyze(refresh=False)"]
        M1c --> M1d["_print_result() 顯示方法/SP/資料表/呼叫鏈"]
        M1d --> M1e{"SEE_AI_PROMPT=true？"}
        M1e -- 是 --> M1f["build_context() + ai_reasoner.build_prompt()<br/>寫出 ai_input_*.txt（不呼叫 AI，不花 token）"]
        M1e -- 否 --> M1g["跳過"]
        M1f --> BackMenu1(["回主選單"])
        M1g --> BackMenu1
    end

    subgraph 模式2["模式 2｜用問題經 RAG 找程式再分析（完整流程，可選 AI）"]
        M2 --> M2a["載入 Chat()（首次較久）"]
        M2a --> M2b["輸入問題"]
        M2b --> M2c["chat.analyze_impact(question)<br/>→ orchestrator.run_impact_analysis()"]
        M2c --> M2d["RAG 檢索 → program_extractor 萃取程式名<br/>→ 依系統分組 → 逐系統呼叫 Impact"]
        M2d --> M2e["build_context() 組上下文"]
        M2e --> M2f{"cfg.RUN_AI？"}
        M2f -- 是 --> M2g["ai_reasoner.reason() + verify_grounding()"]
        M2f -- 否 --> M2h["只顯示送進 AI 的上下文前 2000 字"]
        M2g --> BackMenu2(["回主選單（單次問答）"])
        M2h --> BackMenu2
    end

    subgraph 模式3["模式 3｜問題模糊/可能跨多系統 → agent 決定範圍或請你澄清"]
        M3 --> M3a["載入 Chat()（只建一次）"]
        M3a --> M3loop{"while True：<br/>輸入問題（Enter 空白 → 返回主選單）"}
        M3loop -- 空白 --> BackMenu3(["回主選單"])
        M3loop -- 有輸入 --> Ask["_ask_agentic_once(chat, question)"]
        Ask --> Agent["chat.analyze_impact_agentic()<br/>→ orchestrator.run_impact_analysis_agentic_sync()<br/>→ FunctionAgent 判斷要不要分析、分析哪個系統"]
        Agent --> Clarify{"agent 選擇反問澄清？<br/>needs_clarification"}
        Clarify -- 是 --> Reply["使用者補充回答<br/>併入 combined_query，最多 3 輪"]
        Reply --> Agent
        Clarify -- 否（已分析）--> Show["_print_result() 顯示結果 + AI 整合答案"]
        Show --> M3loop
    end

    BackMenu1 --> Menu
    BackMenu2 --> Menu
    BackMenu3 --> Menu
```

> 💡 模式 3 的關鍵設計（2026-07-03 調整）：`Chat()` 只在**進入模式 3 時**載入一次；每次 agent 回答完（不論是分析結果或反問澄清後的最終答案），會**直接再問下一個問題**，不用回主選單重新選「3」，也不用重新等待系統載入——只有直接按 Enter 才會返回主選單。

## 3. `impact_orch.refresh_cli` 流程（更新指令）

```mermaid
flowchart TD
    Start(["python -m impact_orch.refresh_cli &lt;system_id&gt; [system_id ...]"]) --> Health{"rag_client.health()<br/>Impact 服務在線？"}
    Health -- 否 --> Fail["提示先啟動 uvicorn service.api:app<br/>結束"]
    Health -- 是 --> Loop["for system_id in system_ids"]

    Loop --> Call["rag_client.refresh(system=system_id)<br/>→ POST /refresh"]
    Call --> Api["service/api.py：refresh(req)"]
    Api --> RS["analyze_service.refresh_source(source)"]

    RS --> Ensure["repo_manager.ensure_repo(source, refresh=True)"]
    Ensure --> Cloned{"repo 是否已 clone？<br/>（data/repos/&lt;project&gt;/&lt;repo&gt;）"}
    Cloned -- 否 --> Clone["AzureDevOpsFetcher.fetch()：clone"]
    Cloned -- 是 --> Pull["AzureDevOpsFetcher.fetch(update=True)：git pull"]
    Clone --> Scan
    Pull --> Scan

    Scan["get_or_scan(root, refresh=True)<br/>略過快取，強制重新掃描"] --> Parser["ProjectScanner(root).scan_project(analyze_sp=False)"]
    Parser --> Detect["ProjectTypeDetector 偵測框架<br/>→ 動態啟用 CSharpParser/ASPXParser/RazorParser/VueParser"]
    Detect --> Extract["解析方法/呼叫鏈/SP 名稱/資料表/View 層欄位<br/>（不連資料庫）"]
    Extract --> Save["_save()：覆寫 data/scan_cache/&lt;hash&gt;.pkl + .meta.json"]

    Save --> Resp["回傳 {source_root, files, sp_relations, table_relations}"]
    Resp --> Print["CLI 印出 ✅ system_id 更新完成"]
    Print --> NextCheck{"還有下一個 system_id？"}
    NextCheck -- 是 --> Loop
    NextCheck -- 否 --> End(["結束"])
```

> ⚠️ **常見誤解**：`get_or_scan(refresh=True)` 本身就會**自動覆寫**磁碟快取，不需要手動刪除 `data/scan_cache/*.pkl`。但如果你剛編輯過 `code_analyzer/`／`service/` 底下的解析器程式碼，**已在執行的 uvicorn 服務仍是記憶體裡的舊程式碼**（Python 不會熱重載），必須先重啟服務（或加 `--reload`）才能讓 `refresh_cli` 真正套用新邏輯——這點與快取本身無關，詳見 [使用說明書.md](./使用說明書.md) 的常見問題排除。

## 4. `impact_orch.refresh_sql_cli` 流程（更新 SQL 快取）

```mermaid
flowchart TD
    Start(["python -m impact_orch.refresh_sql_cli &lt;system_id&gt; [system_id ...]"]) --> Health{"rag_client.health()<br/>Impact 服務在線？"}
    Health -- 否 --> Fail["提示先啟動 uvicorn service.api:app<br/>結束"]
    Health -- 是 --> Loop["for system_id in system_ids"]

    Loop --> Resolve["source_resolver.resolve_db_source(system_id)<br/>讀 catalog 的 database.server/database.name"]
    Resolve --> Check{"server 與 name<br/>是否都有值？"}
    Check -- 否（缺一） --> ClientErr["本地直接報錯（ImpactServiceError）<br/>不呼叫 Impact，不嘗試連線"]
    ClientErr --> NextCheck
    Check -- 是 --> Call["rag_client.refresh_sql(system_id)<br/>→ POST /refresh_sql {database:system_id, server, db_name, db_schema}"]

    Call --> Api["service/api.py：refresh_sql(req)<br/>再次驗證 server/db_name 非空"]
    Api --> RS["analyze_service.refresh_sql_source(system_id, server, db_name, schema)"]

    RS --> Dump["sql_cache_store.get_or_dump(system_id, schema, refresh=True, server, db_name)<br/>略過快取，強制重新連線"]
    Dump --> Connect["SQLAnalyzer(system_id, server=server, database_name=db_name).connect()<br/>settings.build_database_config() 現組設定（不查 .env 的 DB_SERVER/DB_DATABASES）"]
    Connect --> DumpAll["dump_all_sql_objects(schema)"]

    DumpAll --> P1["get_all_procedures() → 逐一 _get_sp_basic_info()<br/>（定義 + 參數）"]
    DumpAll --> P2["get_all_views() → 逐一 get_object_definition()"]
    DumpAll --> P3["get_all_functions() → 逐一 get_object_definition()<br/>+ get_function_parameters()"]
    DumpAll --> P4["get_all_tables() → 逐一 get_table_columns()<br/>（欄位名稱/型別/是否可為 NULL）"]

    P1 --> Save
    P2 --> Save
    P3 --> Save
    P4 --> Save

    Save["_save()：覆寫<br/>data/sql_cache/&lt;system_id&gt;__&lt;schema&gt;.json + .meta.json"] --> Resp["回傳 {database, db_schema, procedures, views, functions, tables} 數量"]
    Resp --> Print["CLI 印出 ✅ system_id 更新完成（各類別數量）"]
    Print --> NextCheck{"還有下一個 system_id？"}
    NextCheck -- 是 --> Loop
    NextCheck -- 否 --> End(["結束"])
```

> 💡 之後問問題時，[`sp_fetcher.py`](../service/sp_fetcher.py)／[`view_fetcher.py`](../service/view_fetcher.py) 會**優先讀這份本機快取**，不必每次都連線 SQL Server；`sp_fetcher.py` 在快取沒有該 SP 時仍會 fallback 即時查詢（此時也需要 `db_server`/`db_name`，安全網），`view_fetcher.py` 則只讀快取（避免逐一表名都連線判斷是否為 View）。
>
> ⚠️ 資料庫是**多系統共用資源**（不像 git repo 是每個系統各自一份），跟 `refresh_cli`（更新程式碼）是不同軸的更新指令，需要個別觸發；資料庫端的 SP/View/Function 若被直接修改（未經程式碼部署），也需要重跑這支指令才會反映到之後的問答結果。
>
> ⚠️ **`system_id` 不是資料庫名稱**：實際連線目標（`server`/`db_name`）從 catalog 的
> `database.server`/`database.name` 解析。若該系統在 catalog 未設定完整（缺一即算），
> `refresh_sql_cli` 會在**本地**直接報錯、不會呼叫 Impact 服務，避免誤連到錯誤或未知的
> 資料庫；`/analyze` 呼叫的 SP/View/FK 部分則維持「盡力而為」，缺 server/db_name 時安全
> 回空，不會讓整個問答失敗。
