## 1. 整體架構

同一次「問問題」裡，資料來自兩個完全獨立的更新軸：**程式碼掃描快取**（`refresh_cli` 才會更新）與 **SQL Execution Graph**（`refresh_sql_cli` 才會更新）。兩者在 `CSharpAnalysisGateway` 這一層 join 起來，只有 `proven` 證據才會形成正式的 confirmed relationship。

```mermaid
flowchart LR
    U["使用者提問"] --> Rag["spec-rag：找出候選系統／程式<br/>（RAG 檢索，或依明確 SP／資料表名稱 exact 反查）"]
    Rag -->|"POST /analyze"| Impact["Impact 服務：靜態分析（全程無 AI）"]

    subgraph ImpactInner["Impact_analysis_system 內部"]
        Impact --> Cache["scan_cache<br/>方法／inline SQL／View 層<br/>（refresh_cli 更新）"]
        Impact --> Graph["SQL Execution Graph<br/>（refresh_sql_cli 更新）"]
        Cache --> Gateway["CSharpAnalysisGateway<br/>join 出 proven／likely／unresolved evidence"]
        Graph --> Gateway
        Gateway --> Paths["Execution Paths<br/>（compact，含 path_id）"]
    end

    Paths --> Ctx["spec-rag：組裝 context<br/>（規格書＋程式碼片段＋selected path evidence）"]
    Ctx -->|"RUN_AI=true"| AI["OpenAI 整合答案"]
    AI --> Ground["grounding.py<br/>程式化比對答案是否落地（0 token）"]
    Ground --> Out(["最終答案／報告"])
    Ctx -->|"RUN_AI=false"| Out2(["只顯示送進 AI 的完整內容"])
```

> 💡 **多子資料夾系統**：一個 `system_id` 若在 catalog 對應到多個子資料夾（`azure.path` 為 list），Impact 會逐一解析每個子路徑，再合併成一個邏輯上的掃描結果，下游比對邏輯不需感知這是多資料夾組成。
>
> 💡 **agentic 模式（run_cli 模式 3）的差異**：不是直接走 RAG 檢索，而是由 `FunctionAgent` 依問題訊號決定要不要呼叫 RAG、SP 反查、資料表反查，符合條件的可以同時呼叫；命中多個系統且問題未明示範圍時，會先反問使用者澄清。詳細步驟見 [流程圖_進階.md](./流程圖_進階.md)。

## 2. `impact_orch.run_cli` 四種模式

```mermaid
flowchart TD
    Start(["python -m impact_orch.run_cli"]) --> Health{"Impact 服務在線？"}
    Health -- 否 --> Fail["提示先啟動 uvicorn service.api:app<br/>結束"]
    Health -- 是 --> Menu{"主選單：選擇模式"}

    Menu -- "1｜直接輸入程式名" --> M1["輸入系統＋程式名<br/>→ 直接呼叫 /analyze（不經 RAG）<br/>→ 顯示結果<br/>→（可選）預覽送給 AI 的內容"]
    Menu -- "2｜用問題找程式再分析" --> M2["輸入問題<br/>→ RAG 檢索找出程式<br/>→ /analyze<br/>→（依 .env RUN_AI）AI 整合答案"]
    Menu -- "3｜問題模糊／可能跨系統" --> M3["輸入問題<br/>→ agent 判斷分析範圍，或反問澄清（最多 3 輪）<br/>→ /analyze<br/>→ AI 整合答案<br/>（可連續問下一題，不必回主選單）"]
    Menu -- "4｜輸入資料表名反查" --> M4["輸入資料表名<br/>→ 反查所有系統中存取它的程式<br/>→ 批次呼叫 /analyze<br/>→ 顯示各系統結果"]

    M1 --> Menu
    M2 --> Menu
    M3 --> Menu
    M4 --> Menu
    Menu -- "0" --> Exit(["離開"])
```

> 💡 模式 1、4 完全不經 RAG／AI，是最快的「零 token」路徑；模式 2、3 才會用到規格書檢索與（可選的）AI 整合。是否呼叫 AI、是否顯示送進 AI 的完整內容，一律由 spec-rag 的 `.env`（`RUN_AI`／`SEE_AI_PROMPT`）決定，不受模式選擇影響。
>
> 💡 模式 4 命中不只一個系統時只會警告、不會自動判斷是否真的共用同一張表（純字串比對表名，不驗證跨系統 schema 是否相同）；agentic 模式（模式 3）遇到同樣情況則會直接反問使用者。

## 3. 更新程式碼快取：`refresh_cli`

```mermaid
flowchart TD
    Start(["refresh_cli &lt;system_id&gt; [--program X]"]) --> Ensure["repo_manager：clone 或 git pull"]
    Ensure --> Scan["重新解析程式碼<br/>（C#/ASPX/Razor/Vue）"]
    Scan --> Save["覆寫 scan_cache"]
    Save --> Preflight["順帶跑 external wrapper<br/>contract preflight／reconciliation"]
    Preflight --> Commit{"完整 refresh 且判定<br/>created／reused？"}
    Commit -- 是 --> Write["atomic 寫入 contract registry + catalog"]
    Commit -- 否 --> Skip["只分類，不寫檔案"]
    Write --> Done(["✅ 完成"])
    Skip --> Done
```

> ⚠️ `refresh_cli` 本身就會自動覆寫磁碟快取，**不需要手動刪 `data/scan_cache/`**。但若剛編輯過 `code_analyzer/`／`service/` 的解析器程式碼，正在跑的 Impact 服務仍是記憶體裡的舊版本（Python 不會熱重載），必須先重啟服務才能讓 `refresh_cli` 套用新邏輯。
>
> ⚠️ `--program` 局部更新要求該系統所有已解析的子資料夾都已有目前版本的快取，否則會停止並提示先跑一次不帶 `--program` 的完整更新，不會偷偷升級成整包重掃。
>
> 完整的 external wrapper contract 狀態機（`created`/`reused`/`conflicted`/`preflight_failed`）與 atomic two-file commit 細節見 [流程圖_進階.md](./流程圖_進階.md)。

## 4. 更新 SQL 快取：`refresh_sql_cli`

```mermaid
flowchart TD
    Start(["refresh_sql_cli &lt;system_id&gt;"]) --> Resolve["由 catalog 的 database.server/name 解析連線目標"]
    Resolve --> Check{"server／name 都有值？"}
    Check -- 否 --> ClientErr["本地直接報錯，不嘗試連線"]
    Check -- 是 --> Connect["連線 SQL Server"]
    Connect --> Dump["dump 整庫 SP／View／Function／資料表 Schema"]
    Dump --> Build["建立 SQL Execution Graph"]
    Build --> Save["覆寫 data/sql_cache/&lt;system_id&gt;__&lt;schema&gt;.json"]
    Save --> Done(["✅ 完成"])

    Connect -.同步輪詢.-> Poll["CLI 每 0.5 秒輪詢進度<br/>（連線／SP／View／Function／表／Graph build）"]
```

> 📌 `system_id` 不是資料庫名稱——實際連線的主機/資料庫從 catalog 的 `database.server`/`database.name` 解析，缺一即在本地直接報錯，不會誤連到未知資料庫。
>
> ⚠️ 資料庫是**多系統共用資源**，跟 `refresh_cli`（每個系統各自的 git repo）是不同軸的獨立更新指令；資料庫端 SP/View/Function 若被直接修改（未經程式部署），需要重跑這支指令才會反映到之後的問答結果。
>
> ⚠️ 進度顯示 `completed` 只代表 refresh worker 正常結束，**不等於**正式查詢已通過 Graph readiness 驗證；若 cache 缺失、過期或 database scope 不符，正式 API 會回 HTTP 409（`sql_execution_graph_required`）。
