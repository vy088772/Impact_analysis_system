## 兩個入口：main.py 與 service/api.py

`main.py` 是**另一個獨立的舊版互動式選單 CLI**（測試設定／掃描專案／智慧搜尋／生成依賴圖／分析 SP），跟 `service/api.py`（FastAPI 服務，主要工作流程的真正入口）彼此不互相呼叫。使用說明書描述的完整流程（Impact 服務 + spec-rag 的 `run_cli`/`refresh_cli`）全部走 `service/api.py`；如果只是要做「變更影響分析」的日常操作，不需要用到 `main.py`，它比較適合單機除錯或不想啟動服務時的臨時查詢。

## HTTP API 完整清單

不經 spec-rag、直接打 Impact 服務時使用（除錯用）：

| Method | Path | 用途 |
|---|---|---|
| GET | `/health` | 健康檢查 |
| POST | `/analyze` | 對指定程式跑靜態分析，回傳方法/SP/資料表/呼叫鏈/Execution Paths |
| POST | `/refresh` | 更新程式碼快取（git pull + 重新解析），對應 `refresh_cli` |
| POST | `/refresh_sql` | 更新 SQL 快取（dump 物件 + 建 Graph + 寫 Object Location Index），對應 `refresh_sql_cli` |
| GET | `/refresh_sql/status/{job_id}` | 輪詢 `/refresh_sql` 的 job 進度 |
| GET | `/scan_records` | 列出每份 SQL 快取的 Scan Record（掃描紀錄）：伺服器、資料庫、上次掃描時間；不再含 schema |
| POST | `/find_by_sp` | 以 SP 名稱反查有呼叫它的程式 |
| POST | `/find_by_table` | 以資料表名稱反查有存取它的程式（含 `access_type`/`write_only`） |
| POST | `/locate_object` | 只看 Object Location Index，回答「哪幾個資料庫可能持有這個名稱」；完全不開 SQL 快取，供反查前先縮小範圍 |
| POST | `/flow_chain` | 組出 forward（UI 操作→資料表）或 backward（資料表→程式）候選鏈 |
| POST | `/path_evidence` | 取得單一 `path_id` 的 source-backed 完整證據 |
| POST | `/wrapper_contracts/accept` | 審核並套用 external wrapper contract proposal（對應 `tools/accept_external_wrapper_contract.py` 的邏輯，該 CLI 直接呼叫 `service/contract_acceptance.py`，未必經過這支 API） |

> 完整的請求／回應欄位以 `docs/openapi/openapi.json` 為準。該檔由 `python -m tools.export_openapi_schema` 從實際路由導出，**不手改**；新增或修改任何路由後必須重新導出，否則 `tests/test_export_openapi_schema.py` 會失敗。用 `--check` 可只檢查不寫檔。

### 範例：`/locate_object`

```powershell
$locReq = @{ object_name = "SOrder"; kind = "table" } | ConvertTo-Json
Invoke-RestMethod -Uri http://127.0.0.1:8800/locate_object -Method Post -Body $locReq -ContentType "application/json"
```

`kind` 接受 `sp` 或 `table`，不分大小寫；其他值回 HTTP 400。`sp` 比對 procedure／view／function。`matched` 表示新鮮索引命中，`unindexed` 表示無法代答。兩份都沒出現的資料庫才能剪枝。

同一 `(server, database)` 可有多筆 schema 命中。回應另帶 `schema`、`risk_flags` 與選填 `stated_database`。候選交集只使用伺服器與資料庫。`unproven_schema` 表示尚未證明命中 schema，不代表可以忽略該資料庫。

### 範例：`/analyze`

```powershell
$body = @{
  system = "Y-Docs_TTPUR"
  source = @{ project = "System Dept 1"; repo = "Y-DOCs"; branch = ""; path = "TTPUR" }
  program_names = @("PUR_CostUpload", "PUR_YMMCPriceImport.aspx")
  database = "Y-Docs_TTPUR"
  db_server = "SQLSRV01"
  db_name = "PUR_Production"
  include_snippets = $true
  include_sp_defs = $false
  include_view_layer = $true
  include_execution_paths = $true
  question = "取消一筆採購單時會寫到哪些表？"
  refresh = $false
} | ConvertTo-Json

Invoke-RestMethod -Uri http://127.0.0.1:8800/analyze -Method Post -Body $body -ContentType "application/json"
```

`question` 是選填的分析問題原文，只用來排 Compact Path Candidates 的相關性順序，**不會改變任何 evidence 判定**；留空則依預設順序回傳。

`AnalyzeResponse`（分析回應模型）嚴格驗證巢狀資料。spec-rag 在 HTTP 接收點驗證一次，再合併為 `TypedAnalyzeResult`（型別化分析結果）。正式回應不接受未宣告欄位。

驗證失敗時，客戶端回報 `analyze_contract_error`。錯誤列出系統、資料庫、欄位路徑與錯誤種類，不附完整程式碼或回應本文。請同步更新兩專案，不要把契約錯誤當成「沒有結果」。

MVC／Razor Pages 依 `program_screen.py` 解析畫面。一個程式代號可產生多筆 `ProgramAnalysis`。請以 `program` 與 `file` 分辨畫面。`shared_component_contributions` 另列 ViewComponent（共用畫面元件）的存取貢獻。

### 範例：`/find_by_sp`、`/find_by_table`

```powershell
# 以 SP 名稱反查（不知道屬於哪個系統時，逐系統呼叫）
$spReq = @{ source = @{ project = "System Dept 1"; repo = "Y-DOCs"; branch = ""; path = "TTPUR" }; sp_name = "usp_POPublish"; database = "PUR_Production"; db_server = "SQLSRV01"; cache_only = $true } | ConvertTo-Json
Invoke-RestMethod -Uri http://127.0.0.1:8800/find_by_sp -Method Post -Body $spReq -ContentType "application/json"

# 以資料表名稱反查，write_only=true 只取得寫入類命中
$tblWriteReq = @{ source = @{ project = "System Dept 1"; repo = "Y-DOCs"; branch = ""; path = "TTPUR" }; table_name = "SOrder"; cache_only = $true; database = "PUR_Production"; db_server = "SQLSRV01"; write_only = $true } | ConvertTo-Json
Invoke-RestMethod -Uri http://127.0.0.1:8800/find_by_table -Method Post -Body $tblWriteReq -ContentType "application/json"
```

`cache_only=true`（預設）時只比對已快取的掃描結果，不觸發 clone；提供 `database` 後正式反查需通過 database-scoped Graph readiness，缺失/過期回 HTTP 409（code `sql_execution_graph_required`）。比對表名時會去掉中括號，並把 schema 與 Database 分開比：問 `dbo.AVM` 不會找到 `COMMON.AVM`；只問 `AVM` 則兩個 schema 都會列出；圖裡沒人證明 schema 的目標仍會列出，並在 `risk_flags` 帶 `unproven_schema`。名稱沒寫 Database 時，取請求的 Database。命中不只一個系統時，代表可能是同名巧合，不會自動合併，呼叫端（CLI/agent）應反問使用者確認。

> 範例修正：舊版反查以 `database=system_id` 示範。現在請傳實際資料庫名稱與 `db_server`。spec-rag 會從 catalog 帶入完整身分。上述伺服器與資料庫仍為示例值，請換成實際宣告。

| 回應欄位／錯誤 | 閱讀方式 |
|----------------|----------|
| `evidence_status` | 正式證據狀態；不再使用反查回應的舊 `evidence` 別名 |
| SP 的 `matches`／`likely_matches` | 正式與可能呼叫分開；可能呼叫不能當成正式分析範圍 |
| table 的 `is_write` | 服務計算寫入判定；客戶端不另建操作清單 |
| `write_only=true`／`excluded_count` | 只保留已證實寫入；回報排除數量 |
| `read_through`／`schema_source` | 說明經由哪個 View／Function 讀取，以及 schema 來源 |
| HTTP 409 `ambiguous_database` | 同名資料庫存在多台主機；請指定 `db_server`，不要改猜另一份快取 |

## 環境變數與設定

### Impact 服務的 `.env`

```env
AZURE_DEVOPS_ORG=topmost
AZURE_DEVOPS_PAT=<你的 PAT，需要 Code:Read 權限>
AZURE_DEVOPS_BRANCH=            # 留空用 repo 預設分支

SERVICE_HOST=127.0.0.1
SERVICE_PORT=8800
AZURE_CLONE_ROOT=./data/repos
SCAN_CACHE_ROOT=./data/scan_cache
SQL_CACHE_ROOT=./data/sql_cache   # SP/View/Function/資料表 Schema 的本機落地快取根目錄
DERIVED_EXECUTION_EVIDENCE_STORE_ROOT=./data/derived_execution_evidence
DERIVED_EXECUTION_EVIDENCE_RETENTION_LIMIT=100 # 記憶體保留的完整證據 scope 數
SQL_CACHE_MEMORY_RETENTION_LIMIT=20           # 記憶體保留的 SQL 快取份數
```

`sql_cache_store.CacheIdentity` 以伺服器與資料庫識別快取。一份包含全部 schema；檔名不再帶 schema。兩項記憶體上限各自使用 LRU（優先淘汰最久未使用資料）。淘汰後讀磁碟，不重新連線 SQL Server。

帳號、密碼、連接埠、加密等 SQL Server **連線共用參數**（`DB_*`）也在這裡；每個系統實際依賴哪些 (伺服器, 資料庫)，由 spec-rag catalog 的 `databases`（一組 `{server, name}` 清單）逐系統標注，實際登錄哪些伺服器、資料庫則另外記在 spec-rag 的 `SQLServerData.json`（見下）。

### spec-rag 的 catalog（`catalog/system_catalog.json`）

```jsonc
{
  "system_id": "Y-Docs_TTPUR",
  "azure": { "project": "System Dept 1", "repo": "Y-DOCs", "branch": "", "path": "TTPUR" },
  "databases": [
    { "server": "SQLSRV01", "name": "PUR_Production" }
  ]
}
```

- `azure.repo` 為空的系統無法分析（已停用讀取本機任意路徑）。
- `azure.path` 支援**陣列**（如 `["TTPUR", "ATV", "Notification", "Response"]`），用於同一邏輯系統橫跨同一 repo 底下多個子資料夾的情況；Impact 會逐一 clone/掃描再合併成單一邏輯結果。
- `databases` 為空時，SQL 定義與 Graph 證據受限。直接掃描仍可用 `--server`／`--database` 指定完整目標。
- 未明示資料庫時，`rag_client.analyze()` 逐筆讀取宣告，再合併結果與 `impact_coverage`。明示目標時使用單次請求；缺值可由第一筆宣告補齊。
- 請用 `refresh_sql_cli --system_id <system_id>` 掃描全部宣告。每筆都必須先登錄。

## 內容品質與檢索控制（spec-rag 端）

| 設定 | 作用 | 成本 |
|------|------|------|
| `INCLUDE_SP_DEFS` | 從已驗證 SQL cache 帶入 SP 完整 T-SQL、參數與實際碰的表；只列出被挑中方法有引用到的 SP | 需先跑 `refresh_sql_cli`；不花 token |
| `CONTEXT_MAX_CODE_CHARS` / `CONTEXT_MAX_SPEC_CHARS` | 送進 AI 的程式碼／規格書總量上限；超過的內容只列名不展開全文 | — |
| `USE_CODE_EMBEDDING` | 把方法向量化建索引（依程式碼版本快取），中文問題也能準確命中相關方法 | 索引一次 + 每次一個 query embedding，極便宜 |
| `CODE_EMBED_TOP_K` / `CODE_EMBED_MIN_SIM_RATIO` / `CODE_EMBED_MIN_ABS_SIM` | 三重篩選：先取前 K 個候選，再用「相對本程式最相關方法的相似度比例」與「絕對相似度下限」濾掉真正不相關的方法，避免方法數只比 K 多一點時幾乎全選 | — |
| `USE_CODE_ANNOTATION` | 先用便宜模型把每個函式/畫面區塊/SQL 定義注記成一句中文摘要再檢索（中文 vs 中文更準），送給 AI 的仍是原始程式碼 | 一次性注記成本，依內容雜湊快取 |
| `INCLUDE_VIEW_LAYER` | 回傳 ASPX/View 層擷取的欄位、GridView 分組、查詢條件與前端 script；與 C# 方法共用同一套語意檢索機制（`domain="view"`） | — |

**落地驗證（grounding，自動、0 token）**：`ANSWER_SYNTHESIS=llm` 跑完答案後，程式比對程式／SP／資料表名稱。找不到的列在報告末尾。驗證本身不呼叫模型。

`finalize_analysis()` 呼叫 `classify_query_intent()`（問題意圖分類）。`ai_reasoner.build_prompt()` 合併答案指示與 `prompts/shapes/` 的物件種類片段。`EvidenceFlags`（證據條件旗標）限制無證據的章節。模型不能把候選證據升格為正式證據。

**建議組合**：
- 平時檢視：設定 `ANSWER_SYNTHESIS=off`、`SEE_AI_PROMPT=true`。需要定義時，設定 `INCLUDE_SP_DEFS=true`。其他模型成本仍依各自開關。
- 正式產答案：設定 `ANSWER_SYNTHESIS=llm`。需要中文片段注記時，設定 `USE_CODE_ANNOTATION=true`。

## 一次性維護工具

下列工具均在 **Impact 專案目錄**、用 **Impact 的 venv** 執行，**不需要啟動 Impact 服務**、也不連線 SQL Server。只在升級到對應版本之後對「舊快取」跑一次，之後的 `refresh_sql_cli` 都會自動做對。兩支都支援 `--dry-run`（只列出會做什麼）與 `--cache-root`（指定快取根目錄）。

| 工具 | 做的事 | 什麼時候跑 |
|------|--------|------------|
| `python tools\backfill_object_location_indexes.py` | 幫磁碟上每份已存在的 SQL 快取補寫 `<cache_key>.index.json`（Object Location Index）。只讀快取、不改快取內容，重跑等冪 | 索引版本上升（或索引檔被刪）之後重跑一次，把索引從本機快取重建回來；不跑只會慢（每次反查都整份讀），不會錯 |
| `python tools\repair_sql_execution_graphs.py` | 拿快取裡本來就正確的定義文字重建 `sql_execution_graph`，不連資料庫 | 每次 `graph_version` 提高之後對舊快取一次（`3`：修正 offset；`5`：每個讀、寫、呼叫對象保留四段名稱；`7`：沒寫 schema 的對象不再補 `dbo`；`8`：沒寫 schema 的對象照 SQL Server 的規則解析，CTE 名稱不算讀表，`UPDATE`／`DELETE` 別名寫的是它所指的物件；`9`：`UPDATE`／`DELETE` 的 `WHERE` 與 `SET` 子查詢所讀的資料表算進讀取；`10`：`INSERT ... EXEC` 的 `EXEC` 算成一次呼叫；`11`：`MERGE` 算成寫入目標表、讀取來源，`INSERT` 寫進 CTE 不算寫入同名資料表） |
| `python -m tools.export_openapi_schema` | 從 `service.api:app` 導出 `docs/openapi/openapi.json`；`--check` 只比對不寫檔 | **新增或修改任何 HTTP 路由／回應欄位之後必跑**，否則測試會失敗 |

> 💡 Object Location Index 本身就是「寧可多報、不可少報」：索引過期、讀不到、或版本不符時一律降級成 `unindexed`（呼叫端整份讀），不會因此產生錯的答案——所以這些工具沒跑完也可以先上線。見 `docs/adr/0012-object-location-index-authoritative-pruning.md`。

請在重建 Graph 後執行索引補建。Graph 修復不更新 SQL 快取身分或快取版本。舊 schema 分檔快取需重新執行 `refresh_sql_cli`。目前程式碼快取為 `44`，SQL 快取為 `11`，Graph 為 `11`，索引為 `1`。

## Coverage Report：量測分析到底走到哪裡

`coverage_report` 逐一報出每一個 System 的**兩個**比例，永遠不合成一個數字：

| 比例 | 意義 |
|------|------|
| `executed_procedure_name` | Database Invocation 解出 Executed Procedure Name 的比例 |
| `resolved_connection_source` | Database Invocation 解出 Resolved Connection Source 的比例 |

分開報是因為實測過的 repository 卡在相反的地方——有的解不出程序名稱、有的解不出連線來源——合成一個數字只會把「卡在哪裡」藏起來。線以下的每一筆都計入一個具名理由代碼；一個比例數字本身分不出「解析變好了」與「只是變得有自信」。

```powershell
cd d:\pratice\Python\Impact_analysis_system
python -m tools.coverage_report --system Y-Docs_TTPUR
python -m tools.coverage_report --system IQCS --format json --output review\coverage.json
python -m tools.coverage_report --root data\repos\System_Dept_1\Y-DOCs\ATV --cached-only
```

有 current scan cache 時直接重用，所以同一個 System 可以反覆量測而不必重掃；沒有快取時才會掃一次。加 `--cached-only` 連那一次都不做，改成把該掃描根目錄回報成 `scan_cache_missing`／`scan_cache_stale`／`scan_cache_invalid`——「沒量到」和「量到零」永遠不會讀起來一樣。WebForms 系統由同一個指令量測，所以它的數字可以直接跟既有基準比對。

常見理由代碼：

| 理由代碼 | 意義 |
|----------|------|
| `command_text_method_parameter` | 指令文字跨方法邊界傳進來，刻意不做跨方法推導（ADR-0020） |
| `command_text_conflicting_assignments` | 同一方法內有兩個互相衝突的字面指定，不擇一 |
| `wrapper_source_unavailable` | external wrapper 沒有已審核的 contract，見上方 contract 維護 |
| `no_semantic_model` | 該專案沒有語意模型（Semantic Binding Availability 非 `available`） |
| `no_project_connection_scope` | 原始檔上方沒有專案檔，因此沒有連線查找表（ADR-0018） |
| `ambiguous_parent_application` | 兩個以上的專案同樣接近，選不出唯一的 Parent Application，所以不繼承（ADR-0038）；這是 Web.config 路徑唯一會記的理由，不影響 Evidence Status |
| `root_configuration_namespace_not_connection_strings` | 查找鍵讀自 Configuration 根命名空間，兩個命名空間不合併（ADR-0008） |
| `context_type_not_registered` | 組合根沒有註冊這個 DbContext 型別（僅在這個型別的接收者真的被呼叫過時回報） |
| `receiver_declaration_unresolved` | 一次呼叫發生過，但這個檔案裡讀不到它接收者宣告成什麼型別 |
| `no_connection_expression` | 呼叫點本身沒有連線運算式（連線開在看不到的 external wrapper 裡） |

## External wrapper contract 維護

外部 wrapper（第三方 library 封裝的 DB 存取）需要完整且可採信的 contract。完整 refresh 可用反編譯證據自動建立或沿用；人工工具處理未完成或衝突情況。日常問答不需執行盤點工具。

完整 refresh 且未設定 selector 時，服務會嘗試反編譯被引用的 wrapper DLL。已設定 selector、selector 無效或局部更新時，不自動替換人工選擇。CLI 會列出框架、wrapper、反編譯嘗試與交易結果。

反編譯未完成不代表解析成功。請檢查嘗試理由與 `preflight_failed`。只有完整證據通過 preflight，才可進入正式寫入。

### Step A｜盤點（唯讀）

`discover_external_wrappers` 讀取 `data/scan_cache/` 裡的 `db_invocations`，分組並比對 `config/external_wrapper_contracts.json`，**不會** clone、pull 或重新解析。應在 `refresh_cli` **之後**執行（先有 current scan cache 才盤點得到東西）：

```powershell
cd d:\pratice\Python\Impact_analysis_system
python -m tools.discover_external_wrappers --system Y-Docs_TTPUR
```

重點狀態：

| 狀態 | 意義 |
|------|------|
| `source_wrapper` | wrapper 原始碼在本機可追蹤，不需 external contract |
| `auto_selected` / `explicit_selected` | 已唯一對應已審核的 reusable contract，自動/明確套用 |
| `ambiguous_contract` | 一個 receiver type 對到多個 contract，需整理 registry |
| `ambiguous_implementation` | 一個 interface 對到多個本機實作類別，需人工挑一個 |
| `unresolved_contract`／`unresolved_method`／`receiver_mismatch` | 需人工 review |
| `scan_cache_stale`／`scan_cache_missing` | 不是 contract 問題；先回去跑 `refresh_cli` |

### Step B｜審核並套用

找到需要人工介入的 wrapper 後，依實際查到的 external library 實作整理出 proposal JSON（至少含 `receiver_types` 與 `implementation_snapshot`），用 `accept_external_wrapper_contract.py` 審核：

```powershell
# 1) 先不帶 --apply：只看 diff/reclassification 預覽，不寫任何檔案
python -m tools.accept_external_wrapper_contract --proposal review\proposal.json --system-id Y-Docs_TTPUR --selector sqlobject --scan-root data\repos\System_Dept_1\Y-DOCs\TTPUR

# 2) 確認 diff 符合預期後，加 --apply 正式套用
python -m tools.accept_external_wrapper_contract --proposal review\proposal.json --system-id Y-Docs_TTPUR --selector sqlobject --scan-root data\repos\System_Dept_1\Y-DOCs\TTPUR --apply
```

不帶 `--apply` 一定是安全的預覽，即使 proposal 內容有誤也不會寫入任何檔案。此工具**只改本機檔案，不會建立 git commit**，仍需自行 review 並提交。

> `refresh_cli`（完整 refresh、該 system 有 `database`、preflight 判定 `created`/`reused` 時）也會**自動**把 staged contract 寫入同一組檔案——那是「自動偵測、自動沿用/建立」；這裡是「人工審核、明確套用」，用於 `conflicted`／`preflight_failed` 或需要人工指定 `--selector` 的情境。兩者觸發時機互相獨立，但都經由同一個 `commit_staged_contract_transaction()` 寫入：先寫 transaction manifest、依序替換兩個檔案並驗證 hash，任一步失敗即 rollback；`--apply` 失敗時的錯誤代碼從 `commit_failed`/`commit_rollback_failed` 回報（皆為 `ContractAcceptanceError`），manifest 只在真正需要寫入時才建立，並記錄 `trigger="manual_acceptance"` 以便和 `refresh_cli` 產生的 `trigger="refresh"` manifest 區分。見 [流程圖_進階.md](./流程圖_進階.md)。

## 常見問題（進階）

| 症狀 | 處理 |
|------|------|
| `find_by_table` 的 `write_only=true` 沒過濾到預期的寫入 SP，或回 HTTP 409 | 傳入實際 `database` 與 `db_server`。重跑 `refresh_sql_cli`。檢查 `evidence_status`、`is_write` 與 `excluded_count`；CLI 模式 3 不暴露此開關 |
| `refresh_sql/status/{job_id}` 顯示 `completed` 但正式查詢仍回 409 | `completed` 只代表 worker 正常結束，不代表通過 readiness 驗證；檢查 database scope、Graph version 與 cache version，必要時重跑 `refresh_sql_cli` |
| 不確定哪些系統忘記 clone/掃描/更新 SQL 快取 | 執行 `python tools\check_data_status.py` |
| `discover_external_wrappers` 只回報 `scan_cache_missing`/`scan_cache_stale` | 先跑 `refresh_cli`，這個工具本身不會補做掃描 |
| `coverage_report` 的某個 System 兩個比例都是 `n/a` | 代表「沒量到」不是「量到零」；看同一列的 `not measured:` 理由（快取狀態或 `source_root_unresolved`） |
| `/locate_object` 把每個資料庫都放進 `unindexed`，剪枝完全沒效 | 這些快取還沒有 Object Location Index；跑 `python tools\backfill_object_location_indexes.py` 補建（見上方一次性維護工具） |
| `/locate_object` 回 HTTP 400 | `kind` 只接受 `sp` 或 `table`，不會被猜成其中一種 |
| 新增了路由後 `tests/test_export_openapi_schema.py` 失敗 | 跑 `python -m tools.export_openapi_schema` 重新導出 `docs/openapi/openapi.json` |
| SP 完整定義回傳比以前少 | 即時查詢 fallback 已移除（ADR-0011）；快取沒有就是沒有，請重跑 `refresh_sql_cli`，不要重試 |
| HTTP 409 `ambiguous_database` | 指定 `db_server`。檢查 catalog 的主機宣告，不要把身分歧義當成未掃描 |
| 客戶端回報 `analyze_contract_error` | 同步兩專案版本。按錯誤欄位路徑核對分析回應契約 |
| 結果列出未讀取系統 | 檢查 `not_scanned`、`request_failed`、`request_ceiling_reached` 或 `ambiguous_database`；保留已取得結果，不宣稱分析完整 |
| 啟動時顯示 `RUN_AI 已移除` | 移除環境變數，改用三個新開關 |

## 設計重點

| 設計 | 說明 |
|------|------|
| **兩專案分工** | `llamaindex-spec-rag` 負責理解問題、檢索規格書與呼叫 AI；`Impact_analysis_system` 全程無 AI，只做確定性靜態分析，責任邊界清楚、可各自獨立測試 |
| **Azure DevOps clone-only 來源政策** | 一律以 catalog 的 `azure.{project,repo,branch,path}` clone/沿用，不會退回讀取任意本機路徑；`repo` 為空直接報錯 |
| **持久化掃描快取 + 版本化失效** | `scan_store.py` 一次掃描、之後秒回；`_CACHE_VERSION` 遞增時舊快取自動失效重掃，不需手動清快取 |
| **依實際檔案啟用解析器** | `ProjectScanner` 按檔案類型啟用解析器；`ProjectTypeDetector` 回報框架標籤，不阻擋混合專案 |
| **View 層欄位擷取＋GridView 分組** | 擷取畫面實際顯示文字、查詢條件、前端驗證 script，讓「畫面顯示哪些欄位」可直接引用；預設關閉，需 `INCLUDE_VIEW_LAYER=true` |
| **跨程式呼叫參照展開** | `reference_expander.py` 自動把「被分析程式呼叫到、但定義在其他檔案」的方法一併帶入，類似 IDE 的「跟隨參照」 |
| **SQL Execution Graph 正式來源** | `refresh_sql_cli` 建立並寫入 `data/sql_cache/`；`sql_cache_store.py` 以版本、graph version 與 database scope 驗證，缺失/過期時正式 API 回 409，不猜測 relationship |
| **Evidence contract：proven / likely / unresolved** | 只有 `proven` 能形成 confirmed relationship；`likely` 只作 candidate/risk evidence；`unresolved` 必須保留 reason/target。LLM 不能把 `likely`/`unresolved` 改寫成 `proven` |
| **Path Evidence boundary** | `execution_path_builder.py` 只產生 compact path candidate；`/path_evidence` 才展開完整 source-backed 細節。未展開的 path 是 uncertainty，不代表不存在 |
| **AI 決策分開控制** | `config.Settings` 拒絕殘留 `RUN_AI`；`finalization.py`、`orchestrator.py` 分別讀取具名決策設定 |
| **以 SP／資料表反查程式** | `/find_by_sp`、`/find_by_table` 透過 Gateway 與 database-scoped Graph 比對正式 invocation；`cache_only=True`（預設）未 clone/掃描過即直接 `skipped`，避免逐 catalog 系統投機呼叫觸發昂貴 clone |
| **Object Location Index：只會變慢，不會變錯** | 每份 SQL 快取旁邊一張 `<cache_key>.index.json`，記錄該快取能回答哪些 SP／資料表名稱。`/locate_object` 只看索引、不開快取；索引新鮮且不持有該名稱的資料庫才能被剪枝，缺席／過期／版本不符一律降級成 `unindexed`（呼叫端整份讀）。建立時寧可多報不可少報（ADR-0012） |
| **不再默默回退去連資料庫** | `sp_fetcher.py` 的即時查詢 fallback 已移除（ADR-0011）：快取沒有就回報沒有。請重跑 `refresh_sql_cli`，不是重試 |
| **同一系統可橫跨多個子資料夾** | `azure.path` 支援陣列，`repo_manager` 逐一解析每個子路徑再合併成單一邏輯掃描結果，下游比對邏輯不需感知這是多資料夾組成 |
| **External wrapper contract 兩條寫入入口，一種寫入方式** | `refresh_cli` 完整 refresh 時自動偵測沿用/建立；`accept_external_wrapper_contract.py` 是人工審核觸發的入口；兩者「何時觸發」互相獨立，但都經由同一個 `commit_staged_contract_transaction()` 完成 atomic two-file commit，只有 manifest 裡的 `trigger`（`refresh` vs `manual_acceptance`）不同 |
| **Contract registry/catalog 的 atomic two-file commit** | `contract_transaction.py` 把 registry 與 catalog 視為需一起成功的兩個檔案，任一步失敗即 rollback，不會出現「registry 已更新、catalog 還是舊的」的 mixed state |
| **資料整理狀態一鍵盤點** | `tools/check_data_status.py` 逐系統比對五項狀態，自動列出未完成項目對應的補跑指令 |
| **完整 Database 身分** | `sql_cache_store.CacheIdentity` 管理伺服器與資料庫；一份快取涵蓋全部 schema |
| **請求準備集中管理** | `request_context.build_request_context()` 準備來源、掃描與 scope；handler 保留各自拒絕規則 |
| **派生證據跨請求重用** | `derived_execution_evidence.evidence_for_scope()` 先驗證，再重用記憶體／磁碟證據；部分派生結果不保留 |
| **分析範圍集中管理** | spec-rag 的 `AnalysisScope` 控制候選合併、範圍鎖定與範圍外缺口 |
| **分析回應嚴格驗證** | `rag_client._parse_analyze_response()` 驗證 HTTP 資料；`analyze_merge.py` 合併型別化結果 |
| **未讀取不等於沒有影響** | `cross_system_lookup.find_cached_program_matches()` 保留已讀命中，另列未讀系統與原因 |
