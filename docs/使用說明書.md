# 使用說明書 — 變更影響分析（RAG → 靜態分析 → AI 整合）

本說明書說明如何操作完整的「變更影響分析」流程。系統由兩個專案組成：

| 角色 | 專案 | 職責 |
|------|------|------|
| **RAG 大腦** | `llamaindex-spec-rag` | 理解問題、檢索規格書、萃取程式名、呼叫 Impact、用 AI 整合答案 |
| **靜態分析服務** | `Impact_analysis_system`（本專案） | 無 AI；clone 原始碼、解析 C#、回傳方法/SP/資料表/FK/呼叫鏈/程式碼片段 |

完整流程：

```
使用者提問
  → (spec-rag) RAG 檢索命中規格書
  → (spec-rag) 從規格書取得 program_code（程式名）
  → (Impact) /analyze：clone 進 data/、靜態解析、回傳結構化結果
  → (spec-rag) 組裝上下文 → AI 整合 → 產生影響分析報告
```

## 1. 前置準備

### 1.1 兩個獨立虛擬環境

| 專案 | venv 路徑 | 啟用 |
|------|-----------|------|
| Impact | `Impact_analysis_system\.venv` | `.\.venv\Scripts\Activate.ps1` |
| spec-rag | `llamaindex-spec-rag\.venv` | `.\.venv\Scripts\Activate.ps1` |

### 1.2 Impact 服務的 `.env`（機密只放這裡）

```env
AZURE_DEVOPS_ORG=topmost
AZURE_DEVOPS_PAT=<你的 PAT，需要 Code:Read 權限>
AZURE_DEVOPS_BRANCH=            # 留空用 repo 預設分支

SERVICE_HOST=127.0.0.1
SERVICE_PORT=8800
AZURE_CLONE_ROOT=./data/repos
SCAN_CACHE_ROOT=./data/scan_cache
```

> PAT 是機密，務必確認 `.env` 已在 `.gitignore`。請勿提交或在對話中貼出。

### 1.3 spec-rag 的 catalog 來源對應

`llamaindex-spec-rag\catalog\system_catalog.json` 中每個系統的 `azure` 區塊提供 Impact 的來源：

```jsonc
{
  "system_id": "Y-Docs_TTPUR",
  "azure": { "project": "System Dept 1", "repo": "Y-DOCs", "branch": "", "path": "TTPUR" }
}
```

- `repo` 為空的系統目前無法分析（已停用讀取本機任意路徑）。
- 多系統共用 repo 時，以 `path` 子資料夾區分（如 `Y-DOCs/TTPUR`、`Y-DOCs/TTRDQ`）。

### 1.4 spec-rag 的 `.env`（指向 Impact 服務）

```env
IMPACT_SERVICE_URL=http://127.0.0.1:8800
IMPACT_SERVICE_TIMEOUT=300
IMPACT_FK_DEPTH=1

# 影響分析 AI 控制（注意：AI 跑在 spec-rag，所以放這裡，不是 Impact 的 .env）
RUN_AI=false               # false → 不呼叫 OpenAI（省 token），只做靜態分析與組裝
SEE_AI_PROMPT=true         # true  → 寫出/顯示「送進 AI 的完整 prompt」供檢視

# 內容品質 / 檢索（皆可選；詳見第 9 節）
INCLUDE_SP_DEFS=true       # 連資料庫撈 SP 完整定義（讓 AI 看到 SP 邏輯；需 DB）
CONTEXT_MAX_CODE_CHARS=24000  # 送進 AI 的程式碼總量上限（避免大檔撐爆 prompt）
USE_CODE_EMBEDDING=true    # 用 embedding 語意檢索挑相關方法（中文問題也準）
CODE_EMBED_TOP_K=6         # 檢索取最相關的前幾個方法
USE_CODE_ANNOTATION=false  # 先用便宜模型把每個函式注記再檢索（更準，一次性成本）
```

> `RUN_AI` / `SEE_AI_PROMPT` 由 .env 強制決定，**忽略程式呼叫時傳入的 `run_ai=` / `dump_ai_input=`**；要改行為請改 .env。


```powershell

```
啟動後依選單操作（**預設不跑 AI、不花 token**）：

```
1) 直接輸入程式名分析（快速，不需 RAG/AI）
   → 選系統 → 輸入程式名（如 PUR_CostUpload, RMBudget_MT）
```

- **第一次使用建議選 [1]**：不需載入 RAG、不呼叫 AI，最快確認整條靜態分析通不通。

- 是否跑 AI、是否顯示送給 AI 的資料，皆由 `.env` 的 `RUN_AI` / `SEE_AI_PROMPT` 控制（見第 9 節）。
- CLI 會自動檢查 Impact 服務是否在線，沒開會提示你先啟動（見第 2 節）。

### 3.1 程式化（寫進自己的程式：完整 RAG → Impact → AI 流程）

```python
from query.chat import Chat

chat = Chat()
# 對最近一次查詢命中的規格書做影響分析；首次會觸發一次檢索
result = chat.analyze_impact(
    "修改 YMMC 單價轉入的邏輯會影響什麼？",
    write_report=True,   # 寫出 Markdown 報告
    refresh=False,       # True → 要求 Impact 重新 clone/解析
    # run_ai / dump_ai_input 已忽略，AI 行為由 .env 的 RUN_AI / SEE_AI_PROMPT 決定
)

print(result.answer)            # AI 整合的影響分析（RUN_AI=false 時為空）
print(result.context)           # 送給 AI 的上下文
print(result.ai_prompt)         # 實際送進 OpenAI 的完整 prompt
print(result.report_path)       # 報告路徑（logs/impact_analysis/）
for sysid, data in result.impact_results:
    print(sysid, [p["program"] for p in data["programs"]], data["not_found"])
```

> 💡 **省 token**：在 .env 設 `RUN_AI=false` 即可跑完「萃取程式名 → Impact 靜態分析 → 組裝上下文」而**不呼叫 OpenAI**；設 `SEE_AI_PROMPT=true` 會把送進 AI 的完整內容寫成檔案供檢視。

## 4. 更新程式碼（更新指令）

平常 `/analyze` **不會**重新 clone 或重新解析（沿用 data/ 內的副本與快取）。
要取得最新程式碼時，使用更新指令（git pull + 重新解析 + 覆寫快取）：

### 4.1 分析時順帶更新

```python
chat.analyze_impact("...", refresh=True)
```

### 4.2 只更新某系統（不分析）

```python
from impact_orch import rag_client
print(rag_client.refresh(system="Y-Docs_TTPUR"))
```

## 7. 常見問題排除

| 症狀 | 原因與處理 |
|------|-----------|
| `/analyze` 回 400「source.repo 為空」 | 該系統未在 catalog 設定 Azure `repo`；補上 `azure.repo`（與 `path`）。 |
| `not_found` 含某程式 | 該 `program_code` 在 repo 對應路徑找不到對應檔案；確認 `path` 子資料夾正確、或程式名拼寫。 |
| 第一次 `/analyze` 很久（數分鐘） | 首次需 clone + 完整解析 C#；完成後會快取，之後秒回。 |
| 改了程式碼但結果沒變 | 快取沿用舊解析；用 `refresh=true` 或 `POST /refresh` 重新解析。 |
| 連不到 Impact 服務 | 確認服務已啟動、`IMPACT_SERVICE_URL` 正確、防火牆未擋 127.0.0.1:8800。 |
| FK 連動表總是空 | 該資料庫未定義外鍵（`sys.foreign_keys` 為空），或未提供可連線的 `database`；屬正常。 |

## 9. 進階：內容品質與檢索控制

送給 AI 的內容品質，由下列開關控制（皆在 **spec-rag 的 `.env`**）。預設都偏保守、省 token，可依需要開啟。

| 設定 | 預設 | 作用 | 成本 |
|------|------|------|------|
| `RUN_AI` | false | 是否呼叫 OpenAI 整合答案 | false 不花 GPT token |
| `SEE_AI_PROMPT` | false | 是否寫出/顯示「送進 AI 的完整 prompt」 | 0（純檢視） |
| `INCLUDE_SP_DEFS` | false | 連資料庫撈 SP 完整定義（T-SQL、參數、引用表） | 需 DB 連線；不花 token |
| `CONTEXT_MAX_CODE_CHARS` | 24000 | 程式碼總量上限；超過則其餘方法只列名 | — |
| `USE_CODE_EMBEDDING` | false | embedding 語意檢索挑相關方法（中文也準） | 索引一次（快取）+ 每次 1 個 query embedding，極便宜 |
| `CODE_EMBED_TOP_K` | 6 | 檢索取最相關的前幾個方法 | — |
| `USE_CODE_ANNOTATION` | false | 先用便宜模型注記每個函式再檢索，命中更準 | 一次性注記成本（gpt-5.4-mini，逐函式快取） |

### 9.1 SP 完整定義（`INCLUDE_SP_DEFS`）
C# 只看得到「呼叫了哪個 SP」，看不到 SP 內部。開啟後會連 SQL Server 撈出 SP 的完整 T-SQL、參數與**它實際碰的資料表**（常揭露 C# 看不到的關聯表）。需要可連線的資料庫（由 `database` 或預設 DB 決定）。

### 9.2 完整片段 + 總量預算（`CONTEXT_MAX_CODE_CHARS`）
被選中的方法送**完整本體**（不再中途截斷）；但全部程式碼總量受此上限保護——上千行的大檔也不會把 prompt 撐爆，超過的方法只列名。想更省 token 就調小（如 8000）。

### 9.3 語意檢索（`USE_CODE_EMBEDDING`）
把方法向量化建索引（依程式碼版本快取，**建一次重複用**），查詢時把問題向量化取最相關的前 `CODE_EMBED_TOP_K` 個方法。**中文問題也能命中**（解決關鍵字比對的不足）。索引存於 `storage/code_embeddings/`。

### 9.4 注記式檢索（`USE_CODE_ANNOTATION`）
進一步用便宜模型（`gpt-5.4-mini`）把每個函式注記成一句中文摘要，再拿**注記**做檢索（中文 vs 中文，命中更準），但仍把**原始程式碼**送給 AI（summary for retrieval, code for generation）。注記依「單一函式內容雜湊」快取，**更新時只重做有變動的函式（單支程式即可）**。

### 9.5 落地驗證（grounding，自動、0 token）
`RUN_AI=true` 跑完 AI 答案後，系統會**程式化比對**答案裡提到的程式/SP/資料表是否真的存在於靜態分析資料；找不到的會列在報告末尾「⚠️ 落地驗證」區塊，提醒可能是 AI 臆測。完全不呼叫 LLM、不增加 token。

### 9.6 建議組合
- **平時檢視（省 token）**：`RUN_AI=false`、`SEE_AI_PROMPT=true`、`INCLUDE_SP_DEFS=true`、`USE_CODE_EMBEDDING=true` → 先看「送給 AI 的完整資料」對不對。
- **要正式產答案**：再把 `RUN_AI=true` 打開；需要最高命中率時加 `USE_CODE_ANNOTATION=true`（接受一次性注記成本）。
