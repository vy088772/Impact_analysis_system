# 🔍 使用說明書 — 變更影響分析（RAG → 靜態分析 → AI 整合）

本說明書涵蓋**日常操作**：啟動服務、跑分析、資料變動時怎麼更新。系統由兩個專案組成：

| 角色 | 專案 | 職責 |
|------|------|------|
| **RAG 大腦** | `llamaindex-spec-rag` | 理解問題、檢索規格書、萃取程式名、呼叫 Impact、用 AI 整合答案 |
| **靜態分析服務** | `Impact_analysis_system`（本專案） | 無 AI；clone 原始碼、解析 C#/ASPX/Razor/Vue，比對 SQL 關聯，回傳 source-backed 分析結果 |

> 想看內部怎麼運作，見 [流程圖.md](./流程圖.md)。
> 想找進階設定（API 完整清單、內容品質開關、專案結構、external wrapper contract 維護），見 [進階手冊.md](./進階手冊.md)。

> 🌐 **想用網頁，不想用終端機選單？** 雙擊 `llamaindex-spec-rag` 專案根目錄的 `start_impact_web.bat`，再用瀏覽器開 `http://127.0.0.1:8000`。第一次使用前要先建置前端一次。完整步驟見 [啟動 Web 介面](#-啟動-web-介面)。

## ⚡ 快速開始

### 1. 兩個獨立虛擬環境

| 專案 | venv 路徑 | Windows PowerShell 啟用 | macOS／Linux 啟用 |
|------|-----------|------------------------|------------------|
| Impact | `Impact_analysis_system/.venv` | `.\.venv\Scripts\Activate.ps1` | `source .venv/bin/activate` |
| spec-rag | `llamaindex-spec-rag/.venv` | `.\.venv\Scripts\Activate.ps1` | `source .venv/bin/activate` |

**所有檔案路徑都使用相對路徑，不綁定磁碟代號或使用者目錄。** 每段指令請從標示的專案根目錄開始執行（可先用 VS Code 開啟該專案，再開終端機），並啟用該專案的 venv。

建議兩個專案放在同一層：

```text
工作目錄/
├── Impact_analysis_system/
└── llamaindex-spec-rag/
```

此配置下，從 spec-rag 切到 Impact 用 `cd ../Impact_analysis_system`；反向用 `cd ../llamaindex-spec-rag`。切換專案後請停用原本的 venv（`deactivate`），再依上表啟用目標專案的 venv。從前端目錄回到 spec-rag 根目錄用 `cd ../..`。

下方範例以 Windows PowerShell 為主；一般檔案路徑統一用 `/`，可在兩個平台使用。macOS／Linux 的 venv 啟用方式見上表；健康檢查請以 `curl` 取代 `Invoke-RestMethod`（例如 `curl http://127.0.0.1:8800/health`）。

### 2. 設定檔（一次性，之後不用再管）

**Impact 的 `.env`**（機密只放這裡，勿提交或貼出）：

```env
AZURE_DEVOPS_ORG=topmost
AZURE_DEVOPS_PAT=<你的 PAT，需 Code:Read 權限>
SERVICE_HOST=127.0.0.1
SERVICE_PORT=8800
```

**spec-rag 的 `.env`**（指向 Impact 服務、分別控制 AI 決策）：

```env
IMPACT_SERVICE_URL=http://127.0.0.1:8800
IMPACT_REPO_DIR=            # 只有雙擊啟動器用：建議留空，自動找同層的 Impact_analysis_system，不需設定絕對路徑
IMPACT_WEB_HOST=0.0.0.0     # 只有 Web 介面用：監聽位址；預設 0.0.0.0，區網同事才連得到
IMPACT_WEB_PORT=8000        # 只有 Web 介面用：監聽埠號
SUFFICIENCY_JUDGE=llm       # 證據充分性裁決：llm / deterministic
PATH_SELECTION=llm         # 路徑選擇：llm / deterministic
ANSWER_SYNTHESIS=llm       # 最終答案整合：llm / off
SEE_AI_PROMPT=false  # true  → 把「送給 AI 的完整內容」寫出來供檢視
```

> 升級提醒：移除 `.env` 與環境變數中的 `RUN_AI`。殘留設定會使程式啟動失敗。`ANSWER_SYNTHESIS=off` 只停用答案整合；模式 4／5 的 Router Agent（工具路由代理）仍呼叫模型。Embedding（文字向量化）與片段注記另有設定。

**spec-rag 的 `catalog/system_catalog.json`**：請設定每個系統的 `azure.project/repo/branch/path`。分析與更新需要 Azure repo 來源。`databases` 使用 `{server, name}` 清單，每筆都是完整資料庫身分。未明示資料庫時，分析會讀取宣告的多個快取，再合併結果。覆蓋紀錄會列出已讀與未讀資料庫。

請在 `catalog/SQLServerData.json`（資料庫登錄檔）登錄每筆 `{server, name}`。`refresh_sql_cli --system_id` 會逐筆核對，再掃描全部宣告。

> 完整設定項與各自作用，見 [進階手冊.md § 環境變數與設定](./進階手冊.md#環境變數與設定)。

## 🌐 啟動 Web 介面

Web 介面是**模式 4（agent）的網頁版**。分析師在瀏覽器輸入問題，不用操作終端機選單。它屬於 `llamaindex-spec-rag` 專案（套件名稱 `impact_web`），底層仍呼叫 Impact 服務。

啟動它有兩種方式。**方式 A 一鍵啟動**會一併啟動 Impact 服務。**方式 B 手動啟動**要自己開兩個終端機。

### 第 0 步｜一次性準備（每台機器做一次）

在 **spec-rag 專案目錄**、用 **spec-rag 的 venv** 安裝 Web 需要的套件（`fastapi`、`uvicorn`、`httpx` 已列在 `requirements.txt`）：

```powershell
# 從 spec-rag 根目錄執行
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

macOS／Linux 請將啟用指令換成 `source .venv/bin/activate`，其餘指令相同。

接著建置前端。這一步需要 Node.js。Node.js 只在建置時使用，執行時不需要：

```powershell
cd impact_web/frontend
npm install
npm run build
cd ../..
```

- 上述指令從 spec-rag 根目錄開始，最後回到該根目錄。
- 建置結果在 `impact_web/frontend/dist`。這個目錄不進版控，所以每台新機器都要建置一次。
- 修改 `impact_web/frontend/src` 之後，重新執行 `npm run build`。
- 沒建置就啟動時，指令會停下來，並印出 `前端尚未建置：找不到 …\index.html。請先執行：…`。

### 方式 A｜一鍵啟動（推薦）

在檔案總管雙擊 `llamaindex-spec-rag/start_impact_web.bat`。也可以在 PowerShell 輸入：

```powershell
# 從 spec-rag 根目錄執行
.\start_impact_web.bat
```

macOS 雙擊 `start_impact_web.command`，或從 spec-rag 根目錄執行 `./start_impact_web.command`。

啟動器依序做四件事：

1. 檢查前端是否已建置。沒建置就停止，什麼都不啟動。
2. 檢查 `IMPACT_SERVICE_URL` 的 `/health`。服務在線就重用它，不開第二份。
3. 服務沒回應時，用 `IMPACT_REPO_DIR`（預設是同層的 `Impact_analysis_system`）裡的 `.venv` 啟動 Impact 服務。啟動器最多等 120 秒，等健康檢查通過。
4. 啟動 `python -m impact_web`。

看到 `網頁介面已啟動。` 就代表可以開瀏覽器了。啟動器**不會**印出網址，請依下一節自己輸入。

**停止**：按 `Ctrl+C`，或關閉視窗。啟動器會停掉 Web 介面，以及它自己啟動的 Impact 服務。它重用的 Impact 服務不是它啟動的，所以不會被停掉。每個服務最多約 25 秒停完。

> 💡 在 `.bat` 視窗按 `Ctrl+C` 時，`cmd` 可能問 `Terminate batch job (Y/N)?`。啟動器此時已停好服務，回答 `Y` 或 `N` 都沒有影響。
>
> ⚠️ 啟動器啟動 Impact 時，監聽位址取自 spec-rag `.env` 的 `IMPACT_SERVICE_URL`，**不是** Impact `.env` 的 `SERVICE_PORT`。請讓兩者一致。

### 方式 B｜手動啟動（兩個終端機）

**終端機 1：啟動 Impact 服務**（Impact 的 venv）

```powershell
# 從 Impact 根目錄執行，先啟用 Impact 的 venv
python -m uvicorn service.api:app --host 127.0.0.1 --port 8800
```

**終端機 2：啟動 Web 介面**（spec-rag 的 venv）

```powershell
# 從 spec-rag 根目錄執行，先啟用 spec-rag 的 venv
python -m impact_web
```

- 一定要在 spec-rag 專案**根目錄**執行 `python -m impact_web`，並使用 spec-rag 的 venv。
- 先啟動 Impact 服務，再啟動 Web 介面。Impact 沒啟動時，Web 介面仍可開啟，但頁面頂端會顯示警告，分析也會失敗。
- 指令固定使用一個 uvicorn worker、不重新載入（no reload）。指令不開放這些選項。
- 停止：在各自的終端機按 `Ctrl+C`。

### 打開頁面

| 誰連線 | 網址 |
|--------|------|
| 啟動服務的那台機器 | `http://127.0.0.1:8000` |
| 區網同事 | `http://<啟動服務那台機器的 IP 或主機名>:8000` |

- 預設監聽 `0.0.0.0:8000`。同事連不上時，請讓那台機器的防火牆放行該埠號。
- 要換埠號，在 spec-rag 的 `.env` 設定 `IMPACT_WEB_PORT=<埠號>`，再重新啟動。
- 要只允許本機連線，設定 `IMPACT_WEB_HOST=127.0.0.1`。
- 確認狀態：

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
# impact_service_reachable : True    ← Impact 服務連得到
# worker_state             : ready   ← 分析 worker 已載入完成
# worker_error             :
```

`worker_state` 有三種值：`loading`（第一次載入，請稍等）、`ready`（可以提問）、`restarting`（有人剛停止一個分析，新 worker 載入中）。

### 在頁面上怎麼用

| 功能 | 說明 |
|------|------|
| **提問** | 在輸入框輸入問題，按 Enter。每個問題獨立分析，前一個答案不會改變後一個。 |
| **答案優先** | 綜合答案放最上面。系統、程式、SP、資料表、呼叫鏈與證據缺口收在下方可展開的區塊。 |
| **進度** | 送出後顯示目前階段：`排隊中，前面還有 N 個分析`、`判斷分析範圍`、`檢索規格文件`、`分析系統 <system_id>`、`檢查證據是否足夠（第 N 輪）`、`整理答案`。答案出來後，階段清單自動收合。 |
| **側邊欄對話** | 可新增、切換、改名、刪除對話。標題由 AI 依第一個問題寫成（最多 15 字）；AI 失敗時用問題的前 30 字。自己改過的名稱不會被覆蓋。 |
| **釘選系統（Pinned System）** | 在對話上選一個系統，把檢索與分析鎖在該系統內。其他系統若也碰到同一個資料表或 SP，只列為「未分析的命中」，不分析。換釘選從下一個問題起生效。 |
| **澄清** | agent 反問時，會顯示成一則助理訊息，你的下一則訊息就是回覆。物件種類不明（SP／資料表／程式代號）時，每種解讀是一個按鈕，點選即可。回覆空白＝放棄這次澄清。 |
| **停止** | 分析中按停止鈕會立即結束該分析，問題保留並標示「已停止」，可一鍵重送。排隊中的問題也能取消。 |
| **排隊** | 一次只跑一個分析，其他依序排隊。停止會結束分析 worker 再重啟，期間排隊的問題顯示 `分析服務重新啟動中`。 |

> ⚠️ **對話存在瀏覽器裡，伺服器不存。** 換瀏覽器、換電腦或清除網站資料，都看不到舊對話。
>
> 💡 AI 設定（`SUFFICIENCY_JUDGE`、`PATH_SELECTION`、`ANSWER_SYNTHESIS`）只從 spec-rag 的 `.env` 讀。頁面不顯示，也不能改。`ANSWER_SYNTHESIS=llm` 時，worker 仍會像 CLI 一樣寫出報告檔（給維護者檢查用，分析師看不到）。
>
> 💡 釘選系統會限制範圍。被釘選的回答**不代表其他系統不受影響**，答案會明確註明這一點。

### 開發前端時（選用）

改前端程式碼時，開兩個終端機，不必每次重新建置：

```powershell
# 終端機 1：後端（spec-rag 根目錄）
python -m impact_web

# 終端機 2：前端熱重載
cd impact_web/frontend
npm run dev
```

Vite 開發伺服器會把 `/api` 轉給 `127.0.0.1:<IMPACT_WEB_PORT>`（預設 8000）。請開 `npm run dev` 印出的網址。

## 🚀 日常操作：跑分析

### Step 1｜啟動 Impact 服務

在 **Impact 專案目錄**、用 **Impact 的 venv**：

```powershell
# 從 Impact 根目錄執行，先啟用 Impact 的 venv
python -m uvicorn service.api:app --host 127.0.0.1 --port 8800
```

確認上線（另開一個終端機）：

```powershell
Invoke-RestMethod http://127.0.0.1:8800/health
# → @{status=ok}
```

> ⚠️ 改過 `service/`／`code_analyzer/` 的程式碼後，服務不會自動套用——uvicorn 只在啟動時讀一次 `.py`。要生效必須 `Ctrl+C` 停掉再重啟（開發時可加 `--reload` 讓它自動重啟）；重啟後再跑一次下方的 `refresh_cli`。

### Step 2｜執行分析（互動式 CLI）

在 **spec-rag 專案目錄**、用 **spec-rag 的 venv**：

```powershell
# 從 spec-rag 根目錄執行，先啟用 spec-rag 的 venv
python -m impact_orch.run_cli
```

CLI 會先自動檢查 Impact 服務是否在線，接著顯示 5 種模式：

| 模式 | 什麼時候用 | 需要 RAG／AI？ |
|------|-----------|----------------|
| **1. 直接輸入程式名** | 已經知道要分析哪支程式 | 都不需要，最快 |
| **2. 用問題找程式再分析** | 有明確問題，讓 RAG 幫你找出對應規格書與程式 | 需要 RAG；AI 可選 |
| **3. 輸入資料表名反查程式** | 要改一張表，想知道有哪些程式會受影響 | 都不需要，最快 |
| **4. 問題模糊／可能跨系統（預設）** | 不確定屬於哪個系統，讓 agent 自己判斷分析範圍或反問你 | 需要 RAG＋AI |
| **5. 模式 4 的比較版本** | 同一套 agent 流程，但啟用 Phase 1 code routing；供評估比對用 | 需要 RAG＋AI |

> ⚠️ **模式編號在 2026-08 之後換過**：舊版的「模式 3＝agent、模式 4＝資料表反查」已對調成現在的「模式 3＝資料表反查、模式 4＝agent」。直接按 Enter 不再是模式 1，而是**模式 4**（選單提示 `選項 [4]`）。

- **第一次使用建議輸入 [1]**：不需載入 RAG，最快確認 repo、快取與 `/analyze` 是否正常。
- 請分別設定 `SUFFICIENCY_JUDGE`、`PATH_SELECTION`、`ANSWER_SYNTHESIS`。CLI 不另問 AI 開關；`SEE_AI_PROMPT` 控制輸入存底。
- 分析一律直接用快取結果，不會每次問問題都重新解析程式碼；原始碼有變動時另外執行下面的更新指令。
- 模式 3 命中不只一個系統時會印出警告——請確認是否真的共用同一張表，還是恰好同名但邏輯上不同的表。
- 網頁版（見[啟動 Web 介面](#-啟動-web-介面)）跑的是模式 4。網頁另有「釘選系統」，CLI 沒有這個功能。
- 證據充分性迴圈只會要求「再跑一輪就能補到」的證據。重跑也補不到的種類（例如呼叫次數已用完的關係鏈、已讀完的規格書）會被程式移除。報告仍列出裁決原文與被移除的種類。
- 模式 4／5 可連續問下一個問題，不必回主選單重選；agent 判斷問題模糊時會反問你，最多來回 3 輪，直接按 Enter 可放棄本次提問。
- 模式 4／5 遇到「一個名稱可能是預存程序、也可能是資料表或程式代號」時，會列出每一種解讀讓你用**上下鍵選擇、Enter 確認**（Esc／Ctrl-C 放棄本次提問）。沒有 terminal（例如排程執行）時改成請你輸入種類關鍵字（`預存程序`／`資料表`／`程式代號`）；輸入無法辨識的關鍵字只會再問一次，不會猜測，也不會消耗澄清次數。

- 同一問題含多個歧義名稱時，CLI 會逐一確認種類，再繼續原問題。
- 請檢查報告的未讀取系統與 Evidence Gap（證據缺口）。未掃描、請求失敗、額度耗盡或資料庫身分歧義都不等於零影響。
- 未證實的 SP／資料表呼叫不會進入正式分析範圍。報告會保留相關缺口。
- MVC（控制器與畫面分工框架）與 Razor Pages（頁面與頁面模型框架）會按畫面解析。一個程式代號可以回傳多筆畫面結果。

## 🔄 資料變動時：更新快取

平常分析**不會**重新 clone 或重新解析，一律吃快取。以下是兩條**互相獨立**的更新指令，都在 **spec-rag 專案目錄**、用 **spec-rag 的 venv** 執行：

### 程式碼有變動 → `refresh_cli`

```powershell
python -m impact_orch.refresh_cli Y-Docs_TTPUR              # 可一次填多個 system_id
python -m impact_orch.refresh_cli Y-Docs_TTPUR --program PUR_MasterEdit   # 只更新單支程式
```

做的事：git pull → 重新解析程式碼 → 覆寫掃描快取。`--program` 局部更新要求該系統已有目前版本的完整快取，否則會報錯提示先跑一次完整更新。

完整更新會回報框架、wrapper、反編譯嘗試與契約交易狀態。未設定 selector（契約選擇設定）時，服務可嘗試以 DLL 反編譯證據建立契約。不完整證據會保留為待審查，不會自動核准。

### 資料庫端（SP／View／Function／表結構）有變動 → `refresh_sql_cli`

```powershell
python -m impact_orch.refresh_sql_cli PUR                        # 依資料庫名稱掃描，伺服器由 SQLServerData.json 補上
python -m impact_orch.refresh_sql_cli PUR STC SysErrorRecord      # 一次掃多個資料庫
python -m impact_orch.refresh_sql_cli --system_id Y-Docs_TTPUR    # 改掃某系統宣告依賴的每個資料庫（可重複 --system_id）
python -m impact_orch.refresh_sql_cli --server vmsystest07.topmost.com.tw --database SysErrorRecord   # 直接指定，不查 catalog／登錄檔
```

做的事：連線 SQL Server dump 整庫物件、建立 SQL 關聯圖（SQL Execution Graph）、覆寫快取，並在快取旁邊一併寫出 Object Location Index（物件位置索引，見[一次性維護指令](#-一次性維護指令)）；CLI 會即時顯示進度。這是**多系統共用的資料庫資源**，不會隨 `refresh_cli` 自動更新，資料庫端有人直接改 SP/View（未經程式部署）時才需要跑。

位置參數是**資料庫名稱**，不是系統代號：`refresh_sql_cli STC` 掃的是名叫 `STC` 的資料庫，要掃「STC 系統宣告依賴的每個資料庫」請改用 `--system_id STC`。資料庫名稱、`--system_id`、`--server`/`--database` 三種寫法不能混用。同名資料庫若登錄在多台伺服器，會列出候選（伺服器、資料庫、上次掃描時間）讓你挑一台；沒有 terminal（例如排程執行）時直接報錯，並列出每台候選各自可直接執行的指令，不會卡住等一個永遠不會來的輸入。掃描不會把資料庫順手寫進 `SQLServerData.json`——建檔仍是另一個要自己動手的步驟。

目前一份 SQL 快取涵蓋一個 `(server, database)` 與庫內全部 schema（物件命名空間）。舊的 schema 分檔快取不再採用。請重新執行 `refresh_sql_cli`；Graph 修復工具不會轉換舊快取身分。

> 兩者的完整內部流程（含 external wrapper contract 治理、atomic commit、Graph readiness）見 [流程圖_進階.md](./流程圖_進階.md)。

### 不確定哪些系統資料忘記更新？

```powershell
# 從 Impact 根目錄執行
python tools/check_data_status.py
```

會逐系統列出規格書／程式碼 clone／掃描快取／SQL 快取的狀態，並直接給出要補跑的指令。此工具只讀本機檔案，不連線 Azure DevOps 或 SQL Server，免啟動 Impact 服務也能跑。

## 🧰 一次性維護指令

下面兩支工具都在 **Impact 專案目錄**、用 **Impact 的 venv** 執行，**不連線 SQL Server、不重新掃描原始碼**。工具只處理現有 SQL 快取；日常問問題不需要。

### 升級到目前版本

1. 移除 `RUN_AI`。設定三個替代開關。
2. 在 spec-rag 執行 `pip install -r requirements.txt`，安裝 Web 介面需要的套件。要用 Web 介面時，再建置前端（見[啟動 Web 介面](#-啟動-web-介面)）。
3. 重啟 Impact 服務。
4. 執行 `refresh_cli <system_id>`，重建舊程式碼快取。
5. 對舊 schema 分檔快取執行 `refresh_sql_cli`。
6. 對目前格式但 Graph 過期的快取，執行 Graph 修復工具。
7. 在 Graph 修復後執行索引補建工具。

目前版本：程式碼快取 `52`、SQL 快取 `11`、Graph `14`、物件位置索引 `1`。這些版本各自驗證，不互相取代。

程式碼快取從 `44` 升到 `52`，原因是：呼叫鏈改為跟隨每個呼叫實際綁定的目標方法（ADR-0044）、Razor 畫面錨點納入 URL helper 與 view 載入的 `.js`，以及 C# 解析器補上 tuple、nullable、泛型與含空白的方法宣告。舊快取會自動失效，請照步驟 4 重掃。

### 補建 Object Location Index（物件位置索引）

```powershell
# 從 Impact 根目錄執行
python tools/backfill_object_location_indexes.py --dry-run   # 只看會做什麼，不寫檔
python tools/backfill_object_location_indexes.py             # 正式補建
python tools/backfill_object_location_indexes.py --cache-root data/sql_cache   # 指定快取根目錄
```

Object Location Index 是每份 SQL 快取旁邊的一小張名單（`<cache_key>.index.json`），記錄這份快取能回答哪些 SP／View／Function 與資料表名稱。有了它，反查（`/find_by_sp`、`/find_by_table`）可以直接跳過確定沒有這個名稱的資料庫，不必把每份快取（最大一份約 105 MB）都打開一次。

- **什麼時候要跑**：索引有自己的版本號。升級到索引版本上升的程式之後，磁碟上每份舊索引都算「沒有索引」，要重跑一次把它們補回來；索引檔被刪掉時也一樣。`refresh_sql_cli` 每次更新都會自動帶上最新格式的索引。
- **不跑會怎樣**：只是慢，不會錯。沒索引的資料庫一律被當成「服務無法代答」，呼叫端會像以前一樣整份讀完。
- 重跑安全：每次都重建並覆寫索引，不會重複累積。快取本身的內容一個字也不會改。
- 印出 `快取無效（讀取路徑不會採信），略過` 代表這份快取連正式查詢都不採信（版本或身分不符）——請對該資料庫重跑 `refresh_sql_cli`。

### 修復舊版 SQL Execution Graph

```powershell
python tools/repair_sql_execution_graphs.py --dry-run
python tools/repair_sql_execution_graphs.py
python tools/backfill_object_location_indexes.py
```

請在重建 Graph 後補建索引。修復工具只更新 Graph，不更新快取身分或索引。

這支工具拿快取裡**本來就正確**的 SP／View／Function 定義文字重建一次 Graph，同樣不需要資料庫連線與帳密。`graph_version` 每次提高，磁碟上的舊 Graph 就全部不被採信，要對舊快取跑一次：`graph_version 3` 修正舊寫法偏掉的位置（offset）；`graph_version 5` 讓每個讀、寫、呼叫的對象保留 server、database、schema、名稱四段，例如 `PUR.dbo.Users` 不再把 `PUR` 當成 schema；`graph_version 7` 讓沒寫 schema 的對象保持空白，不再補成 `dbo`；`graph_version 8` 讓沒寫 schema 的對象照 SQL Server 的規則解析（先找模組自己的 schema，再找 `dbo`），CTE 名稱不再算成讀表，`UPDATE`／`DELETE` 的別名改記成它所指的物件；`graph_version 9` 讓 `UPDATE`／`DELETE` 的 `WHERE` 與 `SET` 子查詢所讀的資料表也算進讀取；`graph_version 10` 讓 `INSERT ... EXEC` 的 `EXEC` 也算成一次呼叫，被呼叫的 SP 才會出現在 Execution Path 上；`graph_version 11` 讓 `MERGE` 算成一次寫入（目標表）與讀取（`USING` 來源），`INSERT` 寫進 CTE 不再當成寫入同名資料表；`graph_version 12` 讓非 DML 陳述式（例如 `SET @x = (SELECT ... FROM T)`、`RETURN (SELECT ...)`）裡的讀取也算一次 SELECT 操作，這類讀取不再漏掉（ADR-0041）；`graph_version 13` 讓呼叫其他資料庫的 SP（例如 `eFinanceD.COMMON.OpeneFinanceKey`）的目標 id 保留資料庫名稱，不再誤用本庫同名 SP 的定義當證據（ADR-0042）；`graph_version 14` 讓 `SELECT ... INTO #t` 遮蔽呼叫端同名的暫存表，暫存表來源追蹤不再跨過這種呼叫往上追（ADR-0043）。也可以改成直接重跑 `refresh_sql_cli`（但那會重連資料庫、慢很多）。查詢時不會自動重建 Graph。

## 🧯 常見問題

| 症狀 | 處理 |
|------|------|
| 連不到 Impact 服務 | 確認服務已啟動、`.env` 的 `IMPACT_SERVICE_URL` 正確 |
| `/analyze` 回「source.repo 為空」 | 該系統在 catalog 未設定 `azure.repo` |
| 分析結果 `not_found` 含某程式 | 確認 `azure.path` 子資料夾與程式名拼寫是否正確 |
| 第一次分析很久（數分鐘） | 首次要 clone + 完整解析；完成後會快取，之後秒回 |
| 改了程式碼但結果沒變 | 執行 `python -m impact_orch.refresh_cli <system_id>` |
| 改了 `service/`／`code_analyzer/` 程式碼但行為沒變 | 不是快取問題——服務要重啟才會套用新程式碼，重啟後再跑一次 `refresh_cli`（見 Step 1 提示） |
| `--program` 更新報 `program_refresh_requires_current_cache` | 先不帶 `--program` 跑一次完整更新，再重試指定 program |
| SP/View 定義是舊的、或反查/路徑查詢回 HTTP 409 | 執行 `python -m impact_orch.refresh_sql_cli --system_id <system_id>`（或直接給資料庫名稱） |
| `refresh_sql_cli` 報資料庫不在登錄檔（SQLServerData.json）裡 | 改用印出的 `--server`/`--database` 指令直接掃；掃描不會自動建檔，之後要自己把它登錄進去 |
| `refresh_sql_cli` 印出多台候選要你選一台 | 該資料庫名稱同時登錄在多台伺服器；照提示輸入編號，或改用 `--server` 指定其中一台 |
| `refresh_sql_cli --system_id` 報某筆依賴沒登錄 | 到 `SQLServerData.json` 補上該 `{server, name}`，或修正 `system_catalog.json` 裡打錯的宣告 |
| 反查（模式 3）慢，或想確認有沒有在亂開快取 | 跑一次 `python tools/backfill_object_location_indexes.py` 補上物件位置索引（見上方一次性維護指令） |
| SP／View 定義切出來的片段位置不對 | 舊快取的 Graph offset 偏掉；跑 `python tools/repair_sql_execution_graphs.py` 重建 |
| 問 SP 完整定義，回傳比以前少 | 現在不再默默回退去連資料庫即時查（ADR-0011），快取沒有就是沒有；請重跑 `refresh_sql_cli` |
| 啟動時顯示 `RUN_AI 已移除` | 移除舊環境變數，改設 `SUFFICIENCY_JUDGE`、`PATH_SELECTION`、`ANSWER_SYNTHESIS` |
| 啟動 Web 時顯示 `前端尚未建置：找不到 …\index.html` | 從 spec-rag 根目錄依序執行 `cd impact_web/frontend`、`npm install`、`npm run build`、`cd ../..`（見[啟動 Web 介面](#-啟動-web-介面)） |
| 啟動 Web 時顯示 `IMPACT_WEB_PORT 必須是整數` | 修正 spec-rag `.env` 的 `IMPACT_WEB_PORT`，只填數字 |
| 啟動 Web 時 `8000` 埠號被佔用 | 在 spec-rag `.env` 設定 `IMPACT_WEB_PORT=<別的埠號>`，或先結束佔用的程式 |
| 雙擊 `.bat` 後視窗顯示 `Cannot find .venv\Scripts\python.exe` | 先在 spec-rag 專案根目錄建立 `.venv` 並安裝套件 |
| 啟動器顯示 `找不到 Impact 專案目錄` | 確認兩個專案放在同一層，且目錄名為 `Impact_analysis_system`；spec-rag `.env` 的 `IMPACT_REPO_DIR` 留空即可 |
| 啟動器顯示 `Impact 專案目錄 … 裡沒有 .venv 直譯器` | 先在 Impact 專案建立 `.venv` 並安裝套件 |
| 啟動器顯示 `Impact 服務啟動後立刻結束` 或等了 120 秒仍未通過 | 看上方的錯誤訊息；`IMPACT_SERVICE_URL` 的埠號可能被舊服務佔用，請先結束它 |
| 頁面頂端出現「Impact 服務沒有回應」警告 | 啟動 Impact 服務（方式 A 或 B），並確認 spec-rag `.env` 的 `IMPACT_SERVICE_URL` 正確 |
| 同事連不上 `http://<IP>:8000` | 確認 `IMPACT_WEB_HOST` 不是 `127.0.0.1`，並讓防火牆放行該埠號 |
| 頁面顯示「分析 worker 已結束，請重新啟動服務」 | 停止並重新啟動 Web 介面（`Ctrl+C` 後再執行啟動指令） |
| 對話列表不見了 | 對話存在瀏覽器裡。換瀏覽器、換電腦或清除網站資料都會看不到；伺服器沒有備份 |

更多疑難排解（`write_only` 篩選、`refresh_sql` 進度 vs Graph readiness 等）見 [進階手冊.md § 常見問題（進階）](./進階手冊.md#常見問題進階)。

## 📌 一頁速查

以下各項是獨立操作，不是要在同一個終端機連續貼上。請先在註明的專案根目錄開終端機，並啟用該專案的 venv。macOS／Linux 的啟用、啟動器與健康檢查替代指令見前文。

```powershell
# 0) 啟動 Web 介面（spec-rag 根目錄；第一次先依前文建置前端）
.\start_impact_web.bat                 # 方式 A：一併啟動 Impact 服務與 Web，瀏覽器開 http://127.0.0.1:8000
python -m impact_web                   # 方式 B：Impact 服務已另外啟動時，只啟動 Web（spec-rag venv）
Invoke-RestMethod http://127.0.0.1:8000/api/health   # Web 健康檢查

# 1) 啟動 Impact 服務（Impact 根目錄、Impact venv）
python -m uvicorn service.api:app --host 127.0.0.1 --port 8800

# 2) 健康檢查
Invoke-RestMethod http://127.0.0.1:8800/health

# 3) 從 spec-rag 執行分析（spec-rag 根目錄、spec-rag venv）
python -m impact_orch.run_cli

# 4) 更新某系統程式碼（spec-rag venv）
python -m impact_orch.refresh_cli Y-Docs_TTPUR

# 5) 更新某系統宣告依賴的 SQL 快取（spec-rag venv）
python -m impact_orch.refresh_sql_cli --system_id Y-Docs_TTPUR

# 6) 盤點所有系統資料整理狀態（Impact 根目錄、Impact venv，免啟動服務）
python tools/check_data_status.py

# 7) 一次性：幫舊 SQL 快取補上物件位置索引（Impact venv，不連資料庫）
python tools/backfill_object_location_indexes.py

# 8) 一次性：重建舊快取的 SQL Execution Graph（Impact venv，不連資料庫）
python tools/repair_sql_execution_graphs.py
```
