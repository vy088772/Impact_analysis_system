## ⚡ 快速開始

### Step 1｜確認執行環境

將兩個專案放在同一層，並各自準備 `.venv`（Python 虛擬環境）與所需套件。

```text
工作目錄/
├── Impact_analysis_system/   # 靜態分析服務
└── llamaindex-spec-rag/      # 問答與 Web 介面
```

**所有指令均從指定專案根目錄執行，並使用該專案的 venv。** 切換專案前，先執行 `deactivate`。

| 操作 | Windows PowerShell | macOS Terminal |
|------|--------------------|----------------|
| 啟用 venv | `.\.venv\Scripts\Activate.ps1` | `source .venv/bin/activate` |
| 一鍵啟動 Web（網頁介面） | `.\start_impact_web.bat` | `./start_impact_web.command` |
| 檢查 Impact 服務 | `Invoke-RestMethod http://127.0.0.1:8800/health` | `curl http://127.0.0.1:8800/health` |

其他指令相同。**ESP（公司規格書網站）更新與 `.doc` 轉檔只能在 Windows 執行，且需要 Microsoft Word。**

### Step 2｜確認設定

在 Impact 的 `.env` 填入 Azure DevOps 存取設定。請勿提交或分享金鑰。

```env
AZURE_DEVOPS_ORG=topmost
AZURE_DEVOPS_PAT=<你的 PAT，需 Code:Read 權限>
```

在 spec-rag 的 `.env` 確認 OpenAI 金鑰，並設定：

```env
IMPACT_SERVICE_URL=http://127.0.0.1:8800
SUFFICIENCY_JUDGE=llm
PATH_SELECTION=llm
ANSWER_SYNTHESIS=llm
```

第一次加入系統時，請完成下方[首次匯入系統](#-首次匯入系統)，再使用 Web 或 CLI 分析。

完整設定與舊版升級方式見 [進階手冊.md § 環境變數與設定](./進階手冊.md#環境變數與設定)。

## 🆕 首次匯入系統

每個新系統執行一次。以下以 `SYS_001_OrderManagement` 為例，請替換為實際系統代號、ESP 網址、程式庫與資料庫。

### Step 1｜宣告系統並更新規格書（ESP 來源）

在 **spec-rag 根目錄、spec-rag venv**，使用能連線 ESP 且已安裝 Word 的 Windows 機器執行。不用手動下載或轉檔。

```powershell
# 宣告系統：只登記規格書來源，不下載
python -m crawler.spec_update_cli --add-system SYS_001_OrderManagement "http://your-intranet/ESP/readdocument.aspx?documentId=1170"

# 檢查該系統的檔案與首次匯入數量，不下載
python -m crawler.spec_update_cli --check SYS_001_OrderManagement

# 首次下載、轉檔，建立索引與系統描述
python -m crawler.spec_update_cli SYS_001_OrderManagement
```

新系統會顯示 `First Import`，更新時下載全部規格書；之後只處理變動檔案。請確認摘要的 `failed` 與 `ESP failed` 都是 `0`，並另行處理 `encrypted` 加密檔。

已有 Markdown 卻顯示 `needs Baseline` 時，請先依[進階手冊的 Baseline 步驟](./進階手冊.md#規格書更新esp-來源)處理。完整選項見 [spec-rag README 的 Specification Update 指令](../../llamaindex-spec-rag/README.md#-specification-update-指令)。

### Step 2｜設定程式庫與資料庫來源

開啟 spec-rag 的 `catalog/system_catalog.json`。在 `systems` 清單找到剛新增的 `system_id`，補上 `azure` 與 `databases`，保留其他欄位：

```json
{
	"system_id": "SYS_001_OrderManagement",
	"azure": {
		"project": "YourProject",
		"repo": "YourRepo",
		"branch": "",
		"path": "OrderManagement"
	},
	"databases": [
		{ "server": "SQLSRV01", "name": "OrderDB" }
	]
}
```

`branch` 留空時，程式會自動使用 Impact `.env` 的 `AZURE_DEVOPS_BRANCH`；未設定或值為空時使用 `main`。若填入 `branch`，則優先使用該值。

`path` 是程式庫內的系統子目錄，多個目錄可用陣列。請填完整的程式碼範圍。

再開啟 spec-rag 的 `catalog/SQLServerData.json`，將資料庫加入對應伺服器的 `databases`。伺服器不存在時，新增一筆；請保留既有項目：

```json
{
	"servers": [
		{
			"server": "SQLSRV01",
			"uid_env": "",
			"pwd_env": "",
			"databases": ["OrderDB"]
		}
	]
}
```

請確認兩份設定中的伺服器與資料庫一致。登錄檔不放密碼。

在 **Impact 的 `.env`** 確認資料庫登入設定與 `DB_DRIVER`。預設使用 Windows 驗證；SQL Server 驗證則設定 `DB_AUTH_MODE=sql`、`DB_USER_ID` 與 `DB_PASSWORD`。執行 Impact 的帳號須有讀取物件定義與結構的權限，並安裝對應 ODBC Driver（資料庫連線驅動程式）。

### Step 3｜啟動 Impact 服務

另開終端機，在 **Impact 根目錄、Impact venv** 執行，並保持視窗開啟：

```powershell
python -m uvicorn service.api:app --host 127.0.0.1 --port 8800
```

若服務已啟動，但剛修改 Impact 的 `.env`，請先停止再重啟。

### Step 4｜首次下載程式碼並建立 SQL 快取

回到 **spec-rag 根目錄、spec-rag venv**，依序執行：

```powershell
# 從 Azure DevOps 下載程式碼，解析並建立掃描快取
python -m impact_orch.refresh_cli SYS_001_OrderManagement

# 連線該系統宣告的所有資料庫，建立 SQL 物件快取與關聯圖
python -m impact_orch.refresh_sql_cli --system_id SYS_001_OrderManagement
```

兩項都要完成。程式碼更新不會同時掃描 SQL Server；資料庫掃描也不會更新程式碼。

### Step 5｜確認資料並試跑

在 **Impact 根目錄、Impact venv** 檢查本機資料狀態：

```powershell
python tools/check_data_status.py
```

依提示補齊缺少的資料。完成後，使用 [Web 介面](#-啟動-web-介面)，或在 [CLI 模式 1](#-日常操作跑分析)指定系統與已知程式試跑。

日後來源有變動時，只需執行[對應更新](#-維護資料變動時更新)，不用重新宣告系統。

## 🌐 啟動 Web 介面

### Step 1｜準備前端（每台機器做一次）

在 **spec-rag 根目錄**啟用 venv，安裝套件並建置前端。建置需要 Node.js，日常執行不需要。

```powershell
pip install -r requirements.txt
cd impact_web/frontend
npm install
npm run build
cd ../..
```

修改前端後，請重新執行 `npm run build`。

### Step 2｜啟動並開啟頁面

在 spec-rag 根目錄雙擊啟動檔，或執行：

```powershell
# Windows
.\start_impact_web.bat
```

```bash
# macOS
./start_impact_web.command
```

啟動器會重用已在線的 Impact 服務；服務未啟動時，會自動啟動同層 Impact 專案的服務。

看到 `網頁介面已啟動。` 後，開啟以下網址：

| 使用者 | 網址 |
|--------|------|
| 本機 | `http://127.0.0.1:8000` |
| 區網同事 | `http://<啟動服務那台機器的 IP 或主機名>:8000` |

預設允許區網連線。請確認防火牆放行 `8000`。若只供本機使用，請在 spec-rag `.env` 設定 `IMPACT_WEB_HOST=127.0.0.1`。

停止時按 `Ctrl+C`。啟動器只會停止自己啟動的服務，不會停止原本已在線的 Impact 服務。

手動啟動、埠號調整與健康檢查見 [進階手冊.md § Web 介面啟動與維運](./進階手冊.md#web-介面impact_web啟動與維運)。

### Step 3｜輸入問題

| 操作 | 說明 |
|------|------|
| 提問 | 輸入問題後按 Enter。每個問題獨立分析 |
| 查看結果 | 先讀綜合答案，再展開程式、規格書名稱、主要呼叫鏈、資料表、SP（預存程序）與證據缺口 |
| 回覆澄清 | 回覆系統的問題；出現種類選項時，點選正確解讀 |
| 釘選系統 | 將分析限制在指定系統，從下一個問題起生效 |
| 管理對話 | 在側邊欄新增、切換、改名或刪除對話 |
| 停止分析 | 按停止鈕；已停止的問題可以重送，排隊中的問題也能取消 |

系統一次執行一個分析，其餘依序排隊。

釘選系統的快取若顯示「需要更新」或「更新中」，Web 會直接列出受阻快取與更新頁連結，不啟動分析。請先完成更新，再重送問題。

> ⚠️ 對話只存在目前的瀏覽器。換電腦、換瀏覽器或清除網站資料，都無法取回舊對話。
>
> ⚠️ 釘選後的答案只涵蓋該系統，不代表其他系統不受影響。

### Step 4｜在網頁更新規格書與快取

在側邊欄按「更新快取」，或開啟 `http://<機器>:8000/#update`。每個系統依序列出三種列：規格書、C# 掃描結果、SQL 快取。每一列有自己的「更新」按鈕。

只顯示系統有設定的來源：有 `spec_url` 才有規格書列，有程式庫才有 C# 列。C# 列另列出 repository（程式庫）與掃描子目錄；沒有子目錄表示整個程式庫。

| 按鈕 | 作用 |
|------|------|
| 檢查來源 | 檢查 C# 是否有新 commit；ESP 可連線時，也比對每個系統的規格書與 ESP。開啟頁面時自動執行一次 |
| 重新檢查環境 | 重新測試這台機器能做哪些更新。修好機器後按它 |
| 全部更新 | 更新數字所示的列（見下方） |
| 更新（每一列） | 只更新這一列 |

**環境檢查與鎖住的按鈕。** 啟動時，Web 測試四項更新條件：ESP 連線、Word、各台 SQL Server 連線、各個 Azure Repos repository。有失敗時，頁面上方出現黃色通知，每項失敗一行，寫出原因與鎖住的列。

| 失敗項目 | 鎖住的列 |
|----------|----------|
| ESP 連線或 Word | 所有規格書列 |
| 一台 SQL Server | 那台伺服器的 SQL 列 |
| 一個 repository | 那個 repository 的 C# 列 |
| Impact 服務沒有回應 | 所有 SQL 列與 C# 列 |

鎖住的按鈕為灰色；滑鼠指著它時，顯示原因。Web 也拒絕鎖住的更新，什麼都不啟動。例如 Mac 沒有 Word，也連不到 ESP，所以規格書列全部鎖住。

**C# 與 SQL 列的狀態。**

| 狀態 | 意思與處理 |
|------|------------|
| 最新（`current`） | 本機快取可用；不保證來源從未變更 |
| 需要更新（`outdated`） | 快取缺少、損壞或格式過期。按「更新」重建 |
| 更新中（`refreshing`） | Impact 正在更新這份快取。等待完成後再提問 |
| 來源有新 commit（`behind_source`） | 只有 C# 列有此狀態。本機快取仍可用，需取得最新程式時按這列的「更新」 |

C# 與 SQL 共用 Impact 的更新佇列，一次執行一個工作。排隊中的工作可以取消；執行中的不能取消。同一份快取重複送出時沿用既有工作，多系統共用的 SQL 快取不會重複排隊。排隊或失敗本身不改變快取狀態，仍以磁碟上的資料為準。

**規格書列的狀態。** Catalog 有 `spec_url` 的系統才有規格書列。

| 狀態 | 意思與處理 |
|------|------------|
| 最新 | 不用更新 |
| 比 ESP 舊（N 份） | 按「更新」，更新 N 份有變動的檔案 |
| 第一次匯入（N 份） | 按「更新」，下載並轉換 N 份檔案，再建立索引與系統描述 |
| 需要索引 | 按「更新」，建立索引 |
| 需要 Baseline | 鎖住。在命令列執行通知所寫的 `spec_update_cli --baseline <system_id>` |
| 尚未檢查 | 按「檢查來源」 |
| 無法檢查：連不到 ESP | 這台機器不能更新規格書 |
| 更新中 | 正在排隊或執行 |

**規格書更新的進行方式。**

- 規格書列的「更新」和 `python -m crawler.spec_update_cli <system_id>` 相同：檢查、下載、轉換、套用、建立索引。列上顯示目前階段與完成數。
- 一次只更新一個系統的規格書，其他的顯示「排隊中，第 N 位」。排隊中的可以按「取消」；執行中的不能取消。
- 規格書更新不等 C# 或 SQL 的更新，兩者可以同時進行。
- 更新工作結束前會重新檢查該系統，列上顯示新狀態。有失敗檔案、Encrypted File（有密碼的檔案）、或需要重建系統描述時，列上多一行說明。失敗時顯示錯誤與交接資料夾。
- 沒有失敗時，會移除本次整個交接資料夾；系統資料夾內的正式 Markdown 不受影響。有失敗時保留交接資料夾供檢查。
- 套用與建立索引期間，提問照常進行。關於該系統的答案多一個證據缺口：「這個系統的規格書正在更新，答案可能不完整。」
- 重新啟動 Web 會丟掉排隊中與執行中的規格書更新，不會自動重跑。按「檢查來源」後，再按一次「更新」即可。

**全部更新。** 更新沒有鎖住、也沒有在排隊的這些列：「需要更新」的 SQL 與 C#，以及「比 ESP 舊」或「需要索引」的規格書列。下列項目要按自己的「更新」：

- 「來源有新 commit」的 C#：完整掃描很久。
- 「第一次匯入」的規格書：下載與轉換全部檔案很久。

Impact 無法更新時，符合條件的規格書仍可排隊；規格書更新不依賴 Impact。重新啟動 Impact 會失去它的更新佇列，請重新檢查後再提交。

**只能在命令列做的事。** 宣告系統（`--add-system`）、Baseline（`--baseline`）、排除舊檔（`--exclude`）、強制更新指定檔案（`--doc`）、看每個檔案的比對結果（`--check --detail`）。見[規格書更新（ESP 來源）](#規格書更新esp-來源)。

## 🚀 日常操作：跑分析

若使用 Web 介面，可略過本節。以下為 CLI（終端機互動選單）的操作方式。

### Step 1｜啟動 Impact 服務

在 **Impact 根目錄**啟用 Impact 的 venv，再執行：

```powershell
python -m uvicorn service.api:app --host 127.0.0.1 --port 8800
```

保持此終端機開啟。停止時按 `Ctrl+C`。

### Step 2｜開啟分析選單

另開終端機，在 **spec-rag 根目錄**啟用 spec-rag 的 venv，再執行：

```powershell
python -m impact_orch.run_cli
```

| 模式 | 用途 | 需要 RAG／AI |
|------|------|-------------|
| 1 | 已知程式名，直接分析 | 都不需要 |
| 2 | 用問題找規格書與程式，再分析 | RAG；AI 依設定 |
| 3 | 用資料表名反查相關程式 | 都不需要 |
| 4（預設） | 由 agent（分析代理）判斷範圍，必要時反問 | RAG＋AI |
| 5 | 模式 4 的評估比較版本 | RAG＋AI |

直接按 Enter 進入模式 4，Web 介面也使用此模式。第一次檢查服務時，可先用模式 1。

模式 4／5 可連續提問。系統反問時，請補充說明；按 Enter 可放棄。出現種類選單時，用上下鍵選擇，再按 Enter 確認。

### Step 3｜確認分析範圍

檢查答案中的「未讀取系統」與「證據缺口」。**未掃描、請求失敗或證據不足，都不代表沒有影響。**

提問只讀既有快取，不會下載程式碼、重新掃描或重建 SQL Graph（SQL 執行關聯圖）。快取缺少或過期時，請先在 Web 的「更新快取」頁更新對應列，或執行 `refresh_cli`／`refresh_sql_cli`，再重送問題。Catalog 沒有程式庫的系統只能提供規格書證據，不會被列為程式碼「未讀取系統」。

模式 3 命中多個系統時，請確認是否為同一張資料表，而非同名物件。

## 🔧 維護：資料變動時更新

來源資料變動後，請執行對應更新。程式碼與資料庫快取需分別更新，不能互相取代。

以下更新指令均在 **spec-rag 根目錄、spec-rag venv** 執行。程式碼與資料庫更新需要 Impact 服務在線。

這些更新也可以在 Web 的「更新快取」頁按按鈕完成，見[在網頁更新規格書與快取](#step-4在網頁更新規格書與快取)。

### 規格書更新（ESP 來源）

在能連線 ESP 且已安裝 Word 的 Windows 機器上執行：

```powershell
# 先檢查，不下載
python -m crawler.spec_update_cli --check

# 更新有變動的檔案
python -m crawler.spec_update_cli
```

只更新一個系統時，執行：

```powershell
python -m crawler.spec_update_cli Y-Docs_TTPUR
```

檢查最後摘要的 `failed` 與 `ESP failed`。兩者為 `0` 代表沒有失敗；`encrypted` 表示加密檔未更新，請另行處理。

有失敗時，先重跑同一個指令。新增系統、Baseline（既有檔案的版本登記）、強制更新與失敗檔案處理，見 [進階手冊.md § 規格書更新](./進階手冊.md#規格書更新esp-來源)。

### 規格書更新（手動來源）

將檔案放進 `data/systems/<system_id>/`，完成 Word 轉 Markdown 後，再更新索引：

```powershell
python indexing/incremental_update.py --system_id <system_id>
```

轉檔指令見 [spec-rag README 的 Step 2 與 Step 3](../../llamaindex-spec-rag/README.md)。`.doc` 轉 `.docx` 只能在 Windows 執行。

### 程式碼更新：`refresh_cli`

```powershell
python -m impact_orch.refresh_cli Y-Docs_TTPUR
```

指令會取得最新原始碼、重新解析並覆寫掃描快取。可一次指定多個系統代號。

完整更新與 SQL 更新都會提交工作並等待完成。按 `Ctrl+C` 時，指令會嘗試取消目前等待的工作，並停止提交後續目標；已在執行的工作仍會在 Impact 繼續完成。未知系統、空結果或任一系統失敗時，`refresh_cli` 以結束碼 `1` 離開；中斷時為 `130`。

若修改的是 **Impact 本身的分析程式**，請先重啟 Impact 服務，再執行更新。

### 資料庫更新：`refresh_sql_cli`

SP、View（檢視表）、Function（函式）或資料表結構變動後，執行：

```powershell
python -m impact_orch.refresh_sql_cli --system_id Y-Docs_TTPUR
```

指令會掃描該系統宣告的全部資料庫，更新 SQL 快取與關聯圖。每筆資料庫須先登錄到 `catalog/SQLServerData.json`。

指定單一程式、直接指定資料庫與升級工具，見 [進階手冊.md § 更新的特殊用法](./進階手冊.md#更新的特殊用法)及[一次性維護工具](./進階手冊.md#一次性維護工具)。

### 不確定哪些資料忘了更新

在 **Impact 根目錄、Impact venv** 執行，不需要啟動服務：

```powershell
python tools/check_data_status.py
```

工具會列出本機資料與快取狀態，並提供補跑指令。它不連線來源網站；檢查 ESP 新版本仍須執行 `spec_update_cli --check`。

## 🧯 常見問題

| 症狀 | 處理 |
|------|------|
| 連不到 Impact，或 Web 顯示服務沒有回應 | 確認 Impact 已啟動，並核對 spec-rag `.env` 的 `IMPACT_SERVICE_URL` |
| 啟動器找不到專案或 venv | 確認兩個專案同層，且各自已建立 `.venv` 並安裝套件 |
| 顯示「前端尚未建置」 | 完成[準備前端](#step-1準備前端每台機器做一次) |
| Web 的 `8000` 埠號被佔用 | 在 spec-rag `.env` 設定 `IMPACT_WEB_PORT=<其他埠號>`，重新啟動並使用新網址 |
| 同事連不上 Web | 確認 `IMPACT_WEB_HOST=0.0.0.0`，並讓防火牆放行 Web 埠號 |
| 程式碼更新後結果沒變 | 執行 `refresh_cli`；若改的是 Impact 分析程式，先重啟服務 |
| SQL 定義過期，或出現 `sql_execution_graph_required` | 執行 `refresh_sql_cli --system_id <system_id>` |
| 答案列出 `cache_outdated` 或 `cache_refreshing` | 更新對應快取或等待更新完成，再重送問題；提問不會自動重建 |
| 資料庫未登錄 | 補齊 `SQLServerData.json`，並核對 catalog 的 `{server, name}` |
| 規格書更新失敗 | 確認 ESP 連線與 Word 可用，再重跑；持續失敗時見[進階處理](./進階手冊.md#規格書更新esp-來源) |
| 規格書轉換顯示 Name Check（名稱檢查）失敗 | 檢查列出的遺漏名稱與交接原檔；本次不覆寫舊 Markdown，修正後重跑 |
| 顯示 `needs Baseline` 或 `First Import` | 依[進階手冊的規格書更新步驟](./進階手冊.md#規格書更新esp-來源)處理 |
| 顯示 `RUN_AI 已移除` | 移除舊變數，改用[三個 AI 設定](./進階手冊.md#spec-rag-的-env) |
| 顯示「分析 worker 已結束」 | 停止並重新啟動 Web 介面 |
| 更新快取頁的「更新」按鈕是灰色 | 滑鼠指著按鈕看原因，或看頁面上方的通知。修好機器後按「重新檢查環境」 |
| 規格書列顯示「無法檢查：連不到 ESP」 | 這台機器不能用 Windows 登入讀 ESP；改在公司 Windows 機器更新規格書 |
| 規格書列顯示「需要 Baseline」 | 在命令列執行 `spec_update_cli --baseline <system_id>`，再按「檢查來源」 |
| 舊對話不見了 | 確認使用原本的電腦與瀏覽器；伺服器沒有對話備份 |

其他錯誤見 [進階手冊.md § 常見問題](./進階手冊.md#常見問題進階)。
