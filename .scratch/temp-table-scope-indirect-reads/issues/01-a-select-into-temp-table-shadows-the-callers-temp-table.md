# 01 — A SELECT INTO temp table shadows the caller's temp table

**What to build:** Stop the Temp Table Scope expansion at a module with Temp Table Shadowing. `/find_by_table MaterialType` lists `dbo.usp_CDCU_RMPriceCount_Delete`, but that procedure does not refer to `MaterialType`. The procedure creates its own `#List` with `SELECT ... INTO #List FROM dbo.fun_GetStatusForRMCD(...)`. The expansion goes up to the caller `dbo.usp_CDCU_RMPriceCount`, and the caller makes its own `#List` from `MaterialType`. The two `#List` tables are different tables at run time.

The first text of this issue said that `fun_GetStatusForRMCD` writes `#List`. That was wrong: a function cannot write a temp table. The `lineage` field of the read shows the true chain: `#List@usp_CDCU_RMPriceCount_Delete → #List@usp_CDCU_RMPriceCount`.

Decision: [ADR-0043](../../../docs/adr/0043-a-select-into-temp-table-shadows-the-callers-temp-table.md).

## Agent Brief

**Category:** enhancement
**Summary:** The temp table lineage expansion does not cross a call into or out of a module with Temp Table Shadowing.

**Current behavior:**
The SQL Execution Graph build expands each read of a scoped `#name` temp table into one derived `reads` relationship for each base table behind it. The derived read keeps `confidence: "proven"` and a `lineage` chain of scoped temp node ids. The expansion follows the writers in the read's own module. It also goes up to callers or down to callees along calls, never up then down (ADR-0036). It takes the union of all visible writers. So a callee that creates its own `#name` with `SELECT ... INTO` still receives the base tables of the caller's `#name`, and a caller receives the base tables of that callee's writers.

**Desired behavior:**
A module has Temp Table Shadowing for a temp table name when it has a `dml_operation` node with `operation_type` `SELECT_INTO`, an empty `branch_path`, and a `writes` relationship to that module's scoped node for the name. For that name:

- A resolution does not go up from a shadowing module to its callers.
- A resolution does not go down from a caller into a shadowing callee.
- A resolution can go up from a callee into a shadowing module. A resolution can go down from a shadowing module into its callees.
- The writers inside the shadowing module still give base tables as before.

The rule applies to each name separately. A `SELECT_INTO` with a non-empty `branch_path` does not shadow. The rule ignores the statement order. A `##name` global temp table, a table variable, and a CTE do not change. `GRAPH_VERSION` rises from 13 to 14, so the read path rejects a v13 graph.

**Key interfaces:**
- The temp table lineage expansion of the SQL Execution Graph build (today `_expand_temp_table_lineage`). It must know, for each scoped temp node, whether its module shadows the name. It must skip the call edges that the rules above forbid.
- `GRAPH_VERSION` — 13 → 14.
- The comments that state "the expansion does not detect shadowing" must state the new rule.

**Acceptance criteria:**
- [ ] Caller A writes `#x` from table `TA` and calls B. B has `SELECT ... INTO #x FROM TB` in no branch and reads `#x`. B's read of `#x` gives a lineage read of `TB` and no lineage read of `TA`.
- [ ] In the same graph, A's read of `#x` gives a lineage read of `TA` and no lineage read of `TB`.
- [ ] B has the `SELECT ... INTO #x` only inside an IF branch. B's read of `#x` gives lineage reads of both `TA` and `TB`, as today.
- [ ] A calls B and B calls C. B shadows `#x`, and C reads `#x` without a writer of its own. C's read gives a lineage read of B's base table and no lineage read of A's base table.
- [ ] B shadows `#x` but not `#y`. A read of `#y` in B still resolves through A's writers of `#y`.
- [ ] A `##x` global temp table resolves as today.
- [ ] Every existing temp table lineage test passes without a change to its expected result. A test that asserts a shadowing over-report on purpose changes to the new rule, and the commit names it.
- [ ] After a rebuild of the PUR cache, the graph has no `reads` relationship from an operation of `dbo.usp_CDCU_RMPriceCount_Delete` to `table:dbo.MaterialType`. Its op 2–5 keep a lineage read of `function:dbo.fun_GetStatusForRMCD`.
- [ ] The SQL cache load rejects a stored v13 graph as not valid.

**Out of scope:**
- A report of `CREATE TABLE #name` by the analyzer (issue 02).
- A mark that shows a lineage read as indirect, or names the temp table it passes through (issue 03).
- A rule that uses the statement order of the read and the `SELECT_INTO`.
- The rebuild of the caches by the operator.
