**Notes:**

- Source: the shared cache rescan of ticket 11 (2026-10-07). The user asked
  why TOPCSCY takes so long.
- Cause, step by step:
  1. Lines 57 to 419 of the file are one block of old methods that `//`
     comments remove (`ExportExcelCus` and others).
  2. Since v44 (`e0cb3be`, inline-sql ticket 09), `strip_csharp_comments`
     replaces each comment with spaces before each extractor reads the text.
     The block becomes one run of 18,650 whitespace characters (lines 55 to
     419). The whole file is 20,689 characters.
  3. `CLASS_PATTERN` starts with two optional groups, each followed by
     `\s*`:
     `(?P<access>public|...)?\s*(?P<modifier>abstract|...)?\s*class\s+`.
     When both groups are absent, the two `\s*` can split one run of
     whitespace in O(n²) ways. `finditer` tries again from each position, so
     the cost is O(n³).

  0.03 s, 1,000 spaces 0.20 s, 2,000 spaces 1.43 s to 1.60 s. Each double
  multiplies the time by about 7 to 8.

## Agent Brief

**Category:** bug
**Summary:** `CSharpParser.CLASS_PATTERN` must run in linear time on a long
run of whitespace.

**Current behavior:**
`CLASS_PATTERN` starts with two optional groups (`access`, `modifier`). A
`\s*` follows each group. On a run of whitespace with no `class` keyword,
the regex engine tries O(n²) splits at each start position, so `finditer`
costs O(n³). `strip_csharp_comments` changes each comment to spaces, so a
large block of commented code becomes one long run. One TOPCSCY file
(18,650 spaces in one run) takes 2656 s to parse. Two callers use the
pattern: the class extractor (`_extract_classes`) and the controller name
lookup (`_find_controller_name`).

**Desired behavior:**
Each match of `CLASS_PATTERN` starts at the access modifier, the modifier,
or the `class` keyword. The match never starts in the whitespace before
them. The named groups `access`, `modifier`, `name` and `bases` keep their
meaning. A possible form:
`\b(?:(?P<access>...)\s+)?(?:(?P<modifier>...)\s+)?class\s+(?P<name>\w+)...`.
Both callers get the fix, because they use the same constant.

**Key interfaces:**
- `CSharpParser.CLASS_PATTERN` — the regex to change.
- `ClassInfo.location` line number — changes only for a class with no
  access modifier. It moves to the line of the declaration.
- `_CACHE_VERSION` in the scan store — rises by one. Merge the main line
  version number first, because parallel tickets can take the same number.

**Acceptance criteria:**
- [x] A test runs `CLASS_PATTERN` (with `re.MULTILINE`) on 20,000 spaces
  and finishes in less than one second.
- [x] A test shows that `class Foo` after blank lines gets the line number
  of its declaration.
- [x] A test shows that `public class`, `public static class`,
  `internal sealed class` and `class X : Base, IFoo` give the same groups as
  before.
- [ ] `ToolExcelCreateService.cs` in TOPCSCY parses in a few seconds.
  (18.5 s; see the implementation note and ticket 17.)
- [x] On each scan root, the classes, methods and properties from the old
  and the new parser are the same, except for the class line number above.
  Report each other difference. Do not accept it without a report.
- [x] The scan cache version rises by one.
- [x] The full test suite has no new failures.

**Out of scope:**
- `METHOD_PATTERN` (0.15 s on 2,000 spaces). Make a separate ticket if a
  measure shows that it costs time on a real file.
- Other slow causes in TTPUR (many files).
- Changes to `strip_csharp_comments`.
- The rescan of the shared cache. The user runs it locally.
