# 15 — A View Anchor follows the script file the view loads

**What to build:** On RTTalentDB, the action `TraditionalAssessment.GetApproveComment`
is called from `wwwroot/js/traditional-assessment-common.js:602`. A view loads
that file with `<script src>`. The parser reads only the view file, so no
Program Screen holds the action.

The parser must link a view to each `.js` file that it loads with
`<script src>`. It then reads URLs in that file as View Anchors. The strength
is `likely`, the same as a URL in the view's own `<script>` block.

This ticket decides three points: how to resolve `src` to a file (`~/`,
`/`, relative), whether a shared layout's script file reaches every screen
(ADR-0019 warns about noise), and the scan cache change.

See ticket 13, ADR-0019 and ticket 09.

## Agent Brief

**Category:** enhancement
**Summary:** The Razor parser reads each `.js` file that a view loads with
`<script src>`. A `/Controller/Action` URL in that file becomes a `likely` View
Anchor of the view.

**Current behavior:**
`RazorParser.parse_file` reads only the view file. A URL in a `.js` file that
the view loads is never a View Anchor. On RTTalentDB,
`TraditionalAssessment.GetApproveComment` is called from
`wwwroot/js/traditional-assessment-common.js`. Two views load that file, and
no Program Screen holds the action.

**Desired behavior:**
- Decision (2026-10-07): the parser reads the `.js` file at parse time, inside
  `parse_file`. The URLs go into `view_anchors_candidate` (strength `likely`).
  No new stage, no change to the Program Screen build.
- Resolve `src` like this:
  - `~/x` and `/x` go to `wwwroot/x` of the nearest project (Project
    Connection Scope rule: the nearest project file above the view).
  - A relative `src` goes to `wwwroot` first.
  - The file name match ignores case (`modalhandler.js` finds `modalHandler.js`).
  - Drop the query string (`?v=1`).
  - Skip `http://`, `https://`, `//` and any `src` that holds `@`.
  - A file that is not found gives no anchor and no error.
- Use the same string rules as the view's own `<script>` block: quotes `'`,
  `"` and backticks, an optional third route segment, no leading `/` needed.
  A `//` comment line in the `.js` file gives no anchor.
- A shared layout needs no special rule. The parser reads only the view file,
  so a script of the layout never reaches the child views. Add a test that
  proves it: a `.js` file that only a layout loads gives no anchor to a view.
- Two views that load the same `.js` file each get the anchors (both call it).
- The Program Screen keeps only a candidate that names a declared action, so
  a view URL such as `TraditionalAssessment/TraditionalAssessmentMtn` in the
  `.js` file stays no anchor.

**Key interfaces:**
- `code_analyzer/razor_parser.py`: `_extract_candidate_view_anchors` and a new
  `src` resolver. Reuse `_exact_controller_action`.
- `CONTEXT.md` entry **View Anchor**: add this form at strength `likely`.
- `service/scan_store.py` `_CACHE_VERSION`: raise it. It is 48 now. Merge the
  mainline first and take the next free number, because parallel tickets
  collide on it.
- A `.js` change alone does not refresh a scanned view. A local rescan does.
  Say so in the glossary or the ticket result.

**Acceptance criteria:** the checklist above, unchanged.

**Out of scope:**
- A script of a shared layout or a Shared partial reaching other screens.
- A `.js` file that another `.js` file loads (no chain of scripts).
- Actions in the `helper_parameter`, `no_caller`, `runtime_url` and
  `dynamic_view` reasons of `misses.json`.
