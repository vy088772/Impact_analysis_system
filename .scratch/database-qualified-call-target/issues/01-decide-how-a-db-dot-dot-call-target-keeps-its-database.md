# 01 — Decide how a `db..name` call target keeps its database

**What to build:** A decision on a call target that states a database but no schema. `dbo.usp_FreightImport_Sure` runs `exec master..xp_cmdshell`. The graph gives the calls relationship the target `stored_procedure:.xp_cmdshell`. The target id has an empty schema and no `master` database.

CONTEXT.md marks a `db..name` reference as Unproven Schema, so the empty schema can be correct. The question is whether the target must also keep the database that the text states, so that a reader does not take it for a procedure of the cache Database.

Source: problem 3 of `../../sql-graph-consistency/problems.md`.

**Blocked by:** None — can start immediately.

**Status:** done (2026-10-06). See "Implementation notes" at the end.

**Category:** bug

- [x] A decision: the current target is correct, or the target id must keep the database.

## Comments

> *This was generated by AI during triage.*

### Triage findings (2026-10-06)

- The calls relationship records the stated database. In the `PUR` cache, the relationship for `master..xp_cmdshell` has `target: stored_procedure:.xp_cmdshell`, `database: master`, and `schema_source: unresolved`. The empty schema agrees with ADR-0037.
- The defect is on the read side. The Execution Path builder follows a call when the target id is the id of a listed module. It does not read the `database` of the relationship.
- A scan of every cache found 64 calls relationships to another Database. Ten of them have a target id that is the id of a listed module of the cache. All ten are in the `eFinance` cache: `exec eFinanceD.COMMON.OpeneFinanceKey` gets the id `stored_procedure:COMMON.OpeneFinanceKey`, and that id is the id of the `eFinance` procedure. So the Execution Path uses the definition of the local procedure as evidence for a call to `eFinanceD`.
- The maintainer confirmed that `eFinanceD` is a separate Database, not an alias or a copy of `eFinance`. So the ten calls are real calls to another Database, and the Execution Path for them is wrong today.
- An unresolved path for `master..xp_cmdshell` shows `stored_procedure:.xp_cmdshell` in `unresolved_targets`. A reader cannot see `master`.

### Decision

Option A, accepted by the maintainer: the target id of a call to another Database keeps that Database. Option B (keep the id, and make each reader check the `database` of the relationship) was rejected. Each future reader of a calls target must then repeat the check, and the missed check in the Execution Path builder shows that this fails.

## Agent Brief

**Category:** bug
**Summary:** A call to another Database gets a target id that holds that Database, so the id never equals the id of a listed module of the cache.

**Current behavior:**
The call target rule gives every call target the id `stored_procedure:{schema}.{name}`. The id holds no database. The calls relationship records the stated database in its own `database` field. A call to another Database (for example `exec eFinanceD.COMMON.OpeneFinanceKey` in the `eFinance` cache) can therefore get the id of a listed module of the cache. The Execution Path builder then follows the call into the local module and reports its operations as evidence. A `db..name` call (for example `exec master..xp_cmdshell`) gets `stored_procedure:.xp_cmdshell`. Its unresolved path does not show `master`.

**Desired behavior:**
- A call that states a Database that is not the cache's own Database gets a target id that holds that Database. Use one unambiguous form that keeps an empty schema visible, for example `stored_procedure:master..xp_cmdshell` and `stored_procedure:eFinanceD.COMMON.OpeneFinanceKey`. Keep the database in the written case, as the schema and the name do now.
- A call through a linked server also states a server. Its id also holds the server, so that two servers with the same database name give two ids.
- A call that states the cache's own Database, or states no Database, keeps the current id. Schema Resolution and the module lookup for it do not change.
- "Another Database" uses the existing `names_another_database` comparison (case-insensitive, compared with the cache's own Database). Do not add an alias table.
- The Execution Path builder never follows a call to another Database into a local module. That call gives an unresolved path with the reason `called_procedure_not_in_graph`, and `unresolved_targets` shows the new id, so the reader sees the Database.
- The Unproven Schema mark on a `db..name` call does not change (`schema_source: unresolved`).
- The graph payload changes what a reader concludes, so `GRAPH_VERSION` rises by one. Add a version note in the same style as the earlier notes. Update the stale-version test.

**Key interfaces:**
- The call target rule (`_call_target`, which returns `_CallTarget`). It is the one site that holds the call target rule. The `node_id` it gives for a call to another Database must hold the Database (and the server, when stated).
- The node id helper for a stored procedure. Table, View, and Function node ids do not change: a table node stays shared, and its relationship records the Database.
- The `calls` relationship id. It already adds `@{server}.{database}`. Keep it unique and stable.
- The temp table expansion reads `names_module_node`. A call to another Database must still give `names_module_node = False`.
- Every reader that parses a `stored_procedure:` id back into schema and name (for example the rebuild report tool). It must read the new form, or ignore a call to another Database.

**Acceptance criteria:**
- [x] A test graph for Database `A` that lists `COMMON.P`, plus a module that runs `exec B.COMMON.P`, gives a calls target id that holds `B` and is not the id of the listed `COMMON.P`.
- [x] For that graph, the Execution Path of the calling module does not hold the operations of the local `COMMON.P`. It holds one unresolved path with the reason `called_procedure_not_in_graph`, and its `unresolved_targets` holds the new id.
- [x] `exec master..xp_cmdshell` gives a target id that holds `master` and an empty schema, and the relationship keeps `schema_source: unresolved`.
- [x] `exec A.dbo.P` and `exec A..P` in the cache of Database `A` give the same ids as before (the Database comparison ignores case).
- [x] A call through a linked server gives an id that holds the server and the Database.
- [x] `GRAPH_VERSION` rises by one, with a version note, and the stale-version test passes.
- [x] The full test suite passes.
- [x] A record of the decision exists: an ADR, or an entry in CONTEXT.md that states that a call target in another Database keeps its Database in the id, and why option B was rejected.

**Out of scope:**
- Table, View, and Function node ids, and the `database` field on reads and writes relationships.
- A Database alias table (for example, a rule that `eFinanceD` is a copy of `eFinance`).
- A lookup into the cache of the other Database to follow the call there.
- The plain-text credential in `usp_FreightImport_Sure` (tracked in `plain-text-credential-in-source-sql`).
- The rebuild of the caches on disk. The operator runs graph repair and then the index backfill after the merge.

- `tools/rebuild_report.py` already parses the new id with `parse`. Only its comment changed.
