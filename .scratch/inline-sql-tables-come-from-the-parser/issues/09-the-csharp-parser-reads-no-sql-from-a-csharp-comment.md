# 09 — The C# parser reads no SQL from a C# comment

**What to build:** An analyst sees no table relation and no stored procedure call from C# code that a programmer commented out. The C# parser removes each C# comment from the source text before it reads the text. This rule applies to every System that a scan reads, now and later. See the agent brief in the comments. The brief is the contract; the text below the status is the first report, kept as context.

The rescan of ticket 08 found this defect. It is not in the spec. Before the spec, the function-call guard hid the one local case. The triage of 2026-10-01 found that the defect is not only in the regular expression fallback, so the scope grew.

**Blocked by:** None — can start immediately.

**Status:** done (2026-10-01). See "Implementation notes" at the end. The service restart waits for the merge into the main line (see the notes).

**The local case:**

- `System_Dept_1/Y-DOCs/ATV/PO_ManifastUploadV3.aspx.cs`, line 131:
  `//this.DbCon.Edit_Data("insert into ManifestNew (R_ID,data) values('" + ... + "')");`
- The live code on line 122 calls the stored procedure `usp_PO_ManifaseUpload_AddData` in place of that insert.
- The C# Scan Result gives `ManifestNew` with the reason `inline_sql_regex` and the access type `UNRESOLVED`, in the method `Initial_IVObject`.
- Line 130 holds the same kind of commented-out insert into `ManifestTemp`. It gives no relation. So the parser is not even consistent about a C# comment.
- Spec user story 11 first called this insert "the real writer". That premise was false. Ticket 08 records the result, and the spec corrected story 11 on 2026-10-01.

**Cause, as far as ticket 08 looked:** `CSharpParser._extract_sql_queries` (`code_analyzer/csharp_parser.py`) runs its SQL patterns on the whole file content. No step removes C# comments first. `strip_sql_comments` removes SQL comments only, inside a SQL text.

**Questions for triage:**

- Remove C# comments before the SQL patterns run, with the line numbers kept? A C# string can hold `//` (for example a URL), so the removal must respect C# string literals.
- How many relations of the ten local Systems come from a C# comment? Ticket 08 counted the relations whose source line starts with `//`, `/*`, or `*`: 14 of the 44 fallback relations (10 in TTRDQ, 3 in TTPUR, 1 in ATV). All 14 carry `UNRESOLVED`, so no `write_only` answer counts them. A comment block that does not start on the relation's line can add more.
- A fix changes a relation, so it needs a C# Scan Result format version rise and a rescan.

## Agent Brief

**Category:** bug
**Summary:** The C# parser removes each C# comment from the source text before every extractor reads it, so commented-out code gives no SQL query, no table relation, and no stored procedure call.

**Current behavior:**
`CSharpParser.parse_file` reads a `.cs` file and gives its full text to each extractor. No step removes a C# comment. So a line such as `//this.DbCon.Edit_Data("insert into ManifestNew ...")` gives a fallback table relation for code that never runs. A `/* ... */` block that holds `objPUR.CreateReader("select ... from T")` gives a relation to `T` through the method-call path. A commented-out `new SqlCommand("usp_X", cn)` gives a stored procedure call, and the scanner builds a legacy stored procedure relation from it.

**Desired behavior:**

- `parse_file` removes each C# comment from the file text once, before any extractor runs. Every extractor reads the text without comments: namespaces, classes, methods, properties, SQL queries, stored procedure calls, API endpoints, and the connection analysis of the database tracker.
- The removal replaces each comment character with a space, but keeps each line break. So each line keeps its number, and the text keeps its length. Each location that an extractor records stays correct.
- The removal knows both C# comment forms: `// ...` to the line end, and `/* ... */`, also across lines. A `///` documentation comment is a `//` comment.
- The removal does not change a C# literal. A `//` or `/*` inside a literal is text, not a comment. The literal forms are:
  - a regular string `"..."`, with backslash escapes;
  - a verbatim string `@"..."`, where `""` is one quote;
  - an interpolated string `$"..."`, `$@"..."`, or `@$"..."`;
  - a raw string literal `"""..."""` (C# 11);
  - a character literal, for example `'"'` or `'\''`.
- When the removal cannot read a construct with certainty, it keeps the text. A comment that stays gives a false answer. A removed live line loses a real answer, which is worse.
- The line count statistics (code lines, comment lines, blank lines) still read the original lines. Their values do not change.
- `scan_store._CACHE_VERSION` rises by one. The version history comment states the change: old scans hold relations and stored procedure calls from C# comments, so they need a rescan.

**Key interfaces:**

- `CSharpParser.parse_file(file_path) -> FileAnalysisResult` — it removes C# comments once, before the extractors run. Its signature does not change.
- A new module-level function next to `strip_sql_comments`, for example `strip_csharp_comments(source: str) -> str`. It gives a text of the same length, with the same line breaks. Test it on its own.
- `FileAnalysisResult.sql_queries` and `FileAnalysisResult.stored_procedure_calls` — they lose each entry that came from a comment. Each kept entry keeps its line number.
- `FileAnalysisResult.comment_line_count` — no change.
- `service.scan_store._CACHE_VERSION` — 43 becomes 44, with a history note in the style of the earlier notes.

**Out of scope:**

- A change in a source file of a System.
- A change in the analyzer host, the SQL cache, or the graph format. The host reads C# through Roslyn and already skips comments.
- The quote pairing of the fallback pattern. It skips the `ManifestTemp` text on line 130 by chance, and that is a separate defect.
- `#if false` and other preprocessor blocks.
- The comments of an ASPX, Razor, or Vue file (`<%-- --%>`, `<!-- -->`, `@* *@`).
- A nested string inside an interpolation hole, for example `$"{(a ? "x" : "y")}"`. The removal may keep the text there, as the rule "keep the text when unsure" allows.
- A new ADR. The rule is a parser defect fix, not a design decision.

### How the removal works

- The removal reads the text once, from left to right. Outside a literal, `//` blanks to the line end, and `/* ... */` blanks to its close.
- It skips each literal as one piece: `"..."`, `@"..."`, `$"..."`, `$@"..."`, `@$"..."`, `"""..."""` (also `$$"""...""""`), and a character literal. An interpolation hole is skipped with its nested literals, for example `{Fmt('"')}`. A comment inside a hole stays.
- A line that starts with `#` is a preprocessor directive, and it stays as it is. Without this rule, `#region Don't touch` would start a character literal.
- When the end of a literal or of a `/*` block is not certain, the removal keeps the rest of the file unchanged.
- `_count_lines` still reads the original lines, so `comment_line_count` does not change.
