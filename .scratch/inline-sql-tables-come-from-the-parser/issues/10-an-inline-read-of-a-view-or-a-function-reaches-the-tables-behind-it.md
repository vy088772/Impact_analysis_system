# 10 — An inline read of a view or a function reaches the tables behind it

**What to build:** An analyst asks which programs read a table, and the answer includes a program whose inline SQL reads that table through a view or a table-valued function. The SQL Execution Graph already gives this answer for a stored procedure (`READ_INDIRECT`). An inline relation gives only the name of the view or the function. See the agent brief in the comments. The brief is the contract; the text below the status is the first report, kept as context.

The rescan of ticket 08 found this change. The first title was "A table-valued function in a FROM clause is not a table". The triage of 2026-10-01 found that the graph also matches the function by its name, so the title changed.

**Blocked by:** None — can start immediately.

**Status:** done (2026-10-01). See "Implementation notes" at the end.

**The local cases (rescan of 2026-10-01):**

- 6 parsed relations of TTPUR name a function: `fun_SplitToTable` (`HomePage1.aspx.cs` line 142), and `dbo.fun_GetRoleOrderTypeList` (`PUR_BillConfirm.aspx.cs` 55, `PUR_POPublish.aspx.cs` 65, `PUR_BalanceOrder.aspx.cs` 100, `PUR_SOMaintain.aspx.cs` 162, `PUR_SOPublish.aspx.cs` 36).
- Before the rescan, the function-call guard of the regular expressions dropped them.
- `HostSqlTextAnalysis` gives `read_tables = (dbo.fun_GetRoleOrderTypeList,)` and `function_references = ()` for the text of `PUR_BillConfirm.aspx.cs` line 55.

**The SQL Execution Graph has the same rule:** in the PUR SQL cache, the operation `dml_operation:stored_procedure:dbo.usp_SO_Publish:2` has `read_tables = [dbo.fun_GetRoleOrderTypeList]` and no function reference. So the inline answer and the graph answer agree today (user story 1). A fix belongs in the host, and it changes both places.

**Questions for triage:**

- Should the host report a table-valued function reference (ScriptDom `SchemaObjectFunctionTableReference`) as a function reference? A graph format rise and a SQL cache rebuild follow, and a C# Scan Result format rise and a rescan.
- Or is a read of a table-valued function a useful dependency, so that `/find_by_table fun_GetRoleOrderTypeList` correctly names its callers? Then only the spec sentence needs a correction.

### Triage notes (2026-10-01)

**What the triage verified:**

- The claim holds. The live TTPUR scan holds the 6 relations above, each with `inline_sql_parsed` and `SELECT`.
- The host puts a `SchemaObjectFunctionTableReference` in the read tables on purpose, since the AST-backed graph commit `c42db1b`. A function reference is a scalar `FunctionCall` only.
- The premise "the inline answer and the graph answer agree" is only half true. The graph build maps a read target to a listed view node or function node, not to a table node. In the PUR SQL cache, `dbo.fun_GetRoleOrderTypeList` is a `function` node, with `reads` and `uses` edges from its callers, and `contains` edges to its own operations, which read `RoleOrderAuth` and `OrderType`.
- An Execution Path keeps the view or the function in its read keys, so a graph `/find_by_table fun_GetRoleOrderTypeList` gives `READ`. The lineage rule of the graph queries also gives `READ_INDIRECT` for each table that the view or the function reaches. The inline by-table query gives only the first answer.
- The same gap applies to a view, at a larger scale. The ten local Systems hold 232 parsed relations and 6 fallback relations that read one of 24 listed views (mostly PUR), and 6 parsed relations that read one of 2 listed functions. No relation writes a view or a function.
- The graph `/flow_chain` forward lists the read names of a path, and it does not expand a view.
- `.out-of-scope/` does not exist, so no prior rejection applies.

**Decisions of the grilling session:**

- Q1: A view and a table-valued function take one rule. The ticket does not treat a function as a special case.
- Q2: The direct answer stays. Each table that the view or the function reaches gives one more answer. A fix that removes the relation was rejected: the graph also answers by the name, so a removal makes a new disagreement.
- Q3: The reached tables come from the SQL Execution Graph of the request's Database. A request with no Database gives only the direct answer, as the graph side gives no answer then. A relation whose connection Database is unresolved uses the same graph.
- Q4: A reached answer takes `READ_INDIRECT` from a parsed relation and `UNRESOLVED` from a fallback relation (ADR-0015). It keeps the reason of its relation.
- Q5: A reached answer names the view or the function that it passes through.
- Q6: `/flow_chain` forward, the `/analyze` screen table list, and the shared component table list do not change. They list the name of the view or the function, as the graph side does.
- Q7: The spec, ADR-0039, and `CONTEXT.md` now state the rule. The triage changed them. No new ADR.
- The rejected option: the host reports a table-valued function as a function reference. The graph already gives the correct answer, and that option costs a graph format rise, a SQL cache rebuild, a C# Scan Result format rise, and a rescan. It also removes the read edge that the lineage rule follows.

## Agent Brief

**Category:** bug
**Summary:** An inline read of a view or a table-valued function reaches the tables behind it in the by-table answers, as an Execution Path does.

**Current behavior:**
An Inline SQL Table Relation that reads a view or a table-valued function names that object, with the access type `SELECT` (parsed) or `UNRESOLVED` (fallback). The by-table query of the inline table relations module matches it only by that name. So `/find_by_table RoleOrderAuth` with the Database `PUR` names each stored procedure path that reads `dbo.fun_GetRoleOrderTypeList` (`READ_INDIRECT`), but it does not name `PUR_BillConfirm.aspx.cs`, whose inline SQL reads the same function. `/flow_chain` backward has the same gap, because it calls the same by-table query.

**Desired behavior:**

- When the request names a Database, the by-table query reads the SQL Execution Graph of that Database. A relation whose object, after Schema Resolution, is a listed view node or function node of that graph also reaches each table that the object reaches.
- "Reaches" uses the one lineage rule of the graph queries: the tables that the object's own operations read, plus the tables of each view or function that they read, to any depth, with a cycle safe. Do not write a second copy of this rule. Expose the reachable tables of one view or function from the existing lineage index, and call it from both sides.
- A relation whose stated Database names another Database than the graph's reaches nothing. The graph build has the same rule: that cache holds no definition of the object.
- A reached table that matches the question gives one answer:
  - The access type is `READ_INDIRECT` when the relation is `inline_sql_parsed`, and `UNRESOLVED` when it is `inline_sql_regex`.
  - The reason, the Database, the database candidates, the Database attribution, and the Evidence Status (`not_applicable`) are those of the relation.
  - The answer names the view or the function that it passes through, with its schema.
- The direct answer of the relation does not change. A question that names the view or the function still gets the `SELECT` answer.
- A request with no Database gives only the direct answers, as today.
- `/find_by_table` keeps one inline record for each file. When one file reads the table directly and also through a view, the record keeps the direct read. Today the rank of a record orders `READ_INDIRECT` above `SELECT`, so a plain merge picks the wrong one.
- A `write_only` question leaves out a reached answer, as it leaves out every read.
- The by-method query and its readers do not change.

**Key interfaces:**

- The by-table query of the inline table relations module (`by_table`) — it gains the SQL Execution Graph of the request's Database, or none. Both callers (`/find_by_table` and `/flow_chain` backward) already hold that graph when the request names a Database.
- `InlineTableAnswer` — it gains the view or the function that a reached answer passes through, and nothing for a direct answer.
- `TableMatchProgram` (the `/find_by_table` record) — it gains one field that carries that object. Choose a name that does not collide with `via_sp`, `sp_chain`, or `reads`.
- The lineage index of the graph queries (`_LineageIndex`) — it gains a query that gives the reachable tables of one view or function node id. The Execution Path lineage keeps its behavior.
- The C# Scan Result format does not change. The rule runs at question time, so no rescan is necessary.

**Acceptance criteria:**

- [x] A parsed relation that reads a view, which reads table `T`, gives a `READ_INDIRECT` answer to the question `T`, and the answer names the view.
- [x] The same relation still gives its `SELECT` answer to the question that names the view.
- [x] A fallback relation that reads the same view gives an `UNRESOLVED` answer to the question `T`.
- [x] A view that reads a table-valued function, which reads `T`, gives the answer to `T`, and the answer names the view that the relation reads.
- [x] A view and a function that read each other give a finite answer.
- [x] With no graph (no Database in the request), the question `T` gives no answer from that relation.
- [x] A relation that states another Database gives no reached answer.
- [x] When one file reads `T` directly and through a view, `/find_by_table T` gives one inline record for that file, with the direct access type.
- [x] `/find_by_table T write_only=True` does not count a reached answer as a write.
- [x] `/flow_chain` backward for `T` lists the method of the relation with `via` `direct_sql`.
- [x] `/flow_chain` forward and the `/analyze` screen table list still give the view name, and not `T`.
- [x] On the live TTPUR scan, `/find_by_table RoleOrderAuth` with the Database `PUR` names `PUR_BillConfirm.aspx.cs` with `READ_INDIRECT` through `dbo.fun_GetRoleOrderTypeList`.
- [x] The tests of the graph queries and of the inline table relations module pass. Compare the Impact suite with its baseline: three ids differ between a worktree and the main checkout, and that difference is not a regression.

**Out of scope:**

- A change in the analyzer host, the graph format, the SQL cache, or the C# Scan Result format.
- A rescan of the local Systems.
- Reached tables when the request names no Database.
- The expansion of a view in `/flow_chain` forward, the `/analyze` screen table list, or the shared component table list.
- A write to a view or a function. No local relation does this.
- The access type label of a direct inline read (`SELECT`) against a graph read (`READ`).
- A change in the Object Location Index.

## Implementation notes (2026-10-01)

The work ran on the branch `ticket10-view-lineage`, in the worktree `.claude/worktrees/ticket10-view-lineage`, because ticket 09 ran at the same time.

**Changed files:**

- `service/graph_queries.py`: `_LineageIndex` became `LineageIndex`, because the inline module now uses it. `_ensure_built` keeps the reachable tables of each View or Function in `_containers`. The new query `reachable_tables(node_id)` gives them, each as an `ObjectName` with its schema source. The worklist fixed point does not change, so the Execution Path lineage keeps its behavior.
- `service/sql_execution_graph.py`: one comment names `graph_queries.LineageIndex`.

**Decisions:**

- The node lookup takes the rule of the graph build (`_referenced_node_id`): Schema Resolution against the graph's Database, then a stated schema and the bare name. A relation with no schema reaches through `dbo.V` only when the Object Location Index of the graph's Database lists `dbo.V`.
- "Another Database" includes the Database of the connection, not only the Database that the SQL text states. The rule reads `relation.table.database or <the Database of the relation>`. The direct answer has the same rule: a relation of another Database does not match a question on the request's Database. A relation with an unresolved Database or with candidates uses the graph (Q3).
- `find_by_table` builds a second `LineageIndex` for the same graph, beside the one of `filter_table_accesses`. The build is lazy, so it runs only when one relation reads a listed View or Function. One shared index needs a change of the `filter_table_accesses` interface, so this ticket does not do it.
