# Unify Contract Registry Loading and Fingerprint-Revision Naming

## Problem Statement

The external wrapper contract registry (`external_wrapper_contracts.json`) is read, validated, and searched by two independent code paths: `contract_preflight.py` (the automatic, refresh-time onboarding path) and `contract_acceptance.py` (the explicit, human-reviewed acceptance path). Each path implements its own version of "load the registry," "find an entry by name ignoring letter case," and "pick an unused name for a new fingerprinted revision of an already-taken contract name." These implementations have already diverged in ways that matter:

- `contract_preflight.py`'s loader tolerates a missing or unparseable registry file by returning an empty registry, and never validates registry content (duplicate names, malformed entries) at all.
- `contract_acceptance.py`'s loader raises on a missing or unparseable file, and separately validates content structurally (rejects empty names, casefold-duplicate names, and non-object contract entries).
- `contract_preflight.py`'s name-assignment helper (`_unused_revision_name`) always terminates: it tries three fingerprint-length suffixes, then falls back to an incrementing ordinal suffix.
- `contract_acceptance.py`'s equivalent logic, inlined in `_prepare_versioned_registry`, only tries the same three fingerprint-length suffixes and has no ordinal fallback. When a contract name's short, medium, and full-fingerprint-suffixed variants are all already taken in the registry, this inline loop oscillates between two already-taken names forever — an unrecoverable hang during a human-triggered "accept this contract" request.

This is not a hypothetical risk born only of code review: a related divergence between these same two modules (a case-sensitivity mismatch that let the registry silently accumulate a second entry differing only by letter case) was already found and fixed once in production. Duplicated logic that is free to drift is producing real defects, and the naming-collision inline loop is a currently-untested, reachable infinite loop.

## Solution

Introduce one new module, `service/contract_registry.py`, that becomes the single owner of "how do I safely read the registry" and "how do I safely name a new fingerprinted revision." Both `contract_preflight.py` and `contract_acceptance.py` stop maintaining their own copies of this logic and become callers of the shared module instead.

This lands as two separate changes:

1. **An immediate, narrowly-scoped fix** that closes the infinite loop by sharing only the naming-collision algorithm (the version that already terminates, from `contract_preflight.py`) between both modules. This is small, low-risk, and does not touch registry-loading behavior at all.
2. **A follow-up consolidation** that finishes the job: registry loading (with its two existing, divergent failure/validation behaviors preserved exactly as an explicit `strict` flag rather than as two competing implementations), and the registry/catalog path constants that are today declared identically in three separate files (`contract_preflight.py`, `contract_acceptance.py`, and `contract_transaction.py`).

Both changes are designed to be behavior-preserving for every existing caller except the one bug being fixed: the automatic refresh path keeps its exact tolerant behavior, the explicit acceptance path keeps its exact strict behavior and its exact external error contract (`ContractAcceptanceError` with `.code`/`.details`, caught today by `service/api.py` and `tools/accept_external_wrapper_contract.py`), and the two entry points remain independent in *when* they trigger — consistent with ADR 0004, which already establishes that automatic detection (refresh) and explicit human review (acceptance) are deliberately separate triggers sharing common infrastructure underneath.

## User Stories

1. As a system operator, I want the explicit contract-acceptance workflow to never hang, so that submitting a contract proposal whose fingerprint collides with existing revision names always either succeeds or fails within a bounded time.
2. As a system operator, I want a contract name collision to be resolved the same safe way regardless of which workflow (automatic refresh or explicit acceptance) encountered it, so that the two workflows can't silently diverge on this again.
3. As a developer, I want the fingerprint-revision naming algorithm to exist in exactly one place, so that a future bug fix to it (like the ordinal fallback) benefits both callers automatically instead of requiring two separate patches.
4. As a developer, I want a regression test that reproduces the three-way naming collision (short, medium, and full-fingerprint suffixes all already taken) through the public `accept_external_wrapper_contract` entry point, so that the hang can never silently reappear.
5. As a developer, I want the naming-collision algorithm itself covered by direct unit tests against the new shared module, so that its termination and correctness don't depend on being exercised indirectly through a full acceptance workflow test.
6. As a maintainer of the automatic refresh path, I want its registry-loading behavior to be byte-for-byte unchanged after this refactor — missing or unparseable registry file degrades to an empty registry, and malformed registry content is never rejected — so that refresh never becomes more fragile than it is today.
7. As a maintainer of the explicit acceptance path, I want its registry-loading behavior to be byte-for-byte unchanged after this refactor — missing, unparseable, or structurally invalid registry content is always rejected with a clear error — so that a human accepting a contract proposal is never silently working from bad or incomplete registry data.
8. As a developer, I want the shared loader's two behaviors expressed as one `strict` flag on one function rather than as two separately-named functions or two independent parameters, so that there is one obvious place to look for "how does registry loading behave" and no speculative configuration surface that nothing currently needs.
9. As a developer, I want the shared module to raise its own error type for strict-mode failures rather than reusing `contract_acceptance.py`'s `ContractAcceptanceError`, so that the shared module has no dependency on either of its callers' domain-specific error shapes.
10. As a developer integrating with `service/api.py`'s `/wrapper_contracts/accept` endpoint or `tools/accept_external_wrapper_contract.py`, I want my existing `ContractAcceptanceError` handling (reading `.code` and `.details`) to keep working unchanged, so that this internal refactor requires no changes on my end.
11. As a developer, I want `contract_acceptance.py` to translate the shared module's strict-mode error into its own `ContractAcceptanceError` at the point it calls the shared loader, so that the error-shape translation lives at the one seam that needs it instead of leaking into the shared module.
12. As a developer, I want `analyze_service.py` to import `load_contract_registry` from its new home directly, with no compatibility re-export left behind in `contract_preflight.py`, so that `contract_preflight.py`'s own interface doesn't keep advertising ownership of a function it no longer implements.
13. As a developer, I want the existing test suite's monkeypatching of `load_contract_registry` (which patches the attribute directly on `analyze_service`, not on whichever module currently implements it) to keep working without modification, so that this refactor requires no test rewrites for behavior that hasn't changed.
14. As a developer, I want the registry and catalog file path constants (`DEFAULT_REGISTRY_PATH`, `DEFAULT_CATALOG_PATH`) declared in exactly one place, so that `contract_preflight.py`, `contract_acceptance.py`, and `contract_transaction.py` can never quietly point at different paths.
15. As a developer, I want the content-validation logic used in strict mode (non-empty names, casefold-uniqueness, object-shaped contract entries) to live behind the shared module's one public loading function rather than exposed as a separately-callable validator, so that callers depend on one interface instead of reaching past it into validation internals.
16. As a developer, I want `contract_acceptance.py`'s internal re-validation calls inside `_prepare_registry` and `_prepare_versioned_registry` (which validate the already-loaded registry a second time) to call the same shared validation logic the loader uses, so that there is one validation rule set instead of two that could drift apart, even though the double-validation itself is unchanged in this pass.
17. As a system maintainer, I want the two entry points (automatic refresh, explicit acceptance) to remain independent in when they trigger even after this refactor, so that ADR 0004's deliberate separation of automatic detection from explicit human review is not disturbed by sharing infrastructure underneath.
18. As a developer reading this codebase later, I want the shared module's existence and scope (registry loading and fingerprint-revision naming, not registry writing or contract-behavior comparison) documented clearly enough that nobody re-adds a third, independent copy of this logic in a future feature, so that the drift this spec fixes doesn't recur elsewhere.
19. As a system maintainer, I want the immediate bug-fix change to be reviewable and shippable independently of the larger consolidation, so that closing the hang doesn't have to wait on agreement about the full module boundary.

## Implementation Decisions

- New module `service/contract_registry.py` becomes the single owner of registry loading and fingerprint-revision naming for external wrapper contracts. Both `contract_preflight.py` and `contract_acceptance.py` import from it instead of defining their own copies.
- The naming-collision functions (case-insensitive lookup by name, "is this name already taken across active and staged entries," and "assign an unused revision name for a taken name plus a fingerprint") move into the shared module using the already-terminating algorithm from `contract_preflight.py` (three fingerprint-length suffixes, then an incrementing ordinal suffix as a guaranteed-terminating fallback). `contract_acceptance.py`'s `_prepare_versioned_registry` stops inlining its own version of this logic and calls the shared function instead, with no staged-name set of its own (it only ever resolves one proposal at a time, so it passes an empty staged-names collection).
- Registry loading becomes one function, `load_contract_registry(path, *, strict=False)`, in the shared module:
  - `strict=False` (used by the automatic refresh path) reproduces `contract_preflight.py`'s current behavior exactly: a missing or unparseable file degrades to an empty registry (`{"contracts": {}}`); registry content is not validated at all, and whatever parses is returned as-is.
  - `strict=True` (used by the explicit acceptance path) reproduces `contract_acceptance.py`'s current behavior exactly: a missing or unparseable file raises; registry content is validated (non-empty contract names, no casefold-duplicate names, every contract entry is object-shaped), raising on any violation.
  - Both the file-read/parse failure handling and the content-validation behavior are controlled by this single flag — there is no evidence either existing caller needs them to vary independently, and no third combination is introduced speculatively.
- A new `ContractRegistryError` exception type is defined in the shared module (carrying `code`, `message`, and `details`, matching the existing shape of `ContractAcceptanceError`) and is raised only by strict-mode failures. The shared module has no dependency on `contract_acceptance.py`'s exception type.
- `contract_acceptance.py` calls the shared loader with `strict=True` in place of its own loading function, and wraps any `ContractRegistryError` raised at that call site into its own `ContractAcceptanceError(exc.code, str(exc), exc.details)` — preserving the exact external error contract `service/api.py` and `tools/accept_external_wrapper_contract.py` already depend on. No change is needed at either of those call sites.
- `analyze_service.py`'s import changes from importing `load_contract_registry` out of `contract_preflight.py` to importing it out of the new shared module. `contract_preflight.py` does not keep a re-export shim for this name. Call sites and call signature in `analyze_service.py` are unchanged (still called with default `strict=False`).
- `DEFAULT_REGISTRY_PATH` and `DEFAULT_CATALOG_PATH` move into the shared module as the single source of truth. `contract_preflight.py`, `contract_acceptance.py`, and `contract_transaction.py` all import these constants from the shared module instead of each declaring their own copy.
- The content-coercion logic used in non-strict mode (accepting either a `{"contracts": {...}}`-shaped payload or a bare mapping of entries) and the content-validation logic used in strict mode both become internal, non-public helpers behind the one public `load_contract_registry` function — no separate public validator function is exposed.
- `_prepare_registry` and `_prepare_versioned_registry` in `contract_acceptance.py` continue to independently re-validate the registry payload they're given (as they do today), but now call the shared module's internal validation logic rather than a locally-defined copy of it. This preserves today's double-validation behavior exactly; removing the redundancy itself is out of scope.
- `CONTEXT.md` already defines the relevant domain terms this spec operates on (`Wrapper Contract`, `Contract Fingerprint`, `Append-only Contract Registry`, `Immutable Wrapper Contract`); no new glossary terms are introduced by this spec.

## Testing Decisions

- A good test here asserts externally observable outcomes only: the returned registry dict's shape and contents, whether an error was raised and its `.code`, and (for the naming function) the returned name string and that the call actually returns rather than hangs — never internal control flow inside the shared module.
- `service/contract_registry.py` is a new, dependency-free module (no I/O beyond reading a path it's given, no coupling to either caller) and gets direct unit tests as its primary seam:
  - Case-insensitive lookup behavior (name found regardless of case, `None` when absent).
  - Fingerprint-revision naming: the three-suffix happy path, and the collision case where all three fingerprint-length suffixes are already taken, asserting the ordinal fallback is used and the call returns promptly (bounded by a test timeout) rather than hanging.
  - `load_contract_registry` with `strict=False`: missing file, unparseable JSON, and malformed content (duplicate casefold names, non-object entries) all degrade to `{"contracts": {}}` or pass through unvalidated as appropriate — matching `contract_preflight.py`'s current test expectations.
  - `load_contract_registry` with `strict=True`: the same set of failure cases each raise `ContractRegistryError` with the expected `.code` — matching `contract_acceptance.py`'s current test expectations.
- A new regression test, added to `tests/test_contract_acceptance.py` (existing seam, prior art: `tests/test_refresh_contract_preflight.py:test_matching_fingerprint_reuses_the_entry_despite_name_case`), calls `accept_external_wrapper_contract` with a registry pre-populated so that a proposal's fingerprint-derived name collides on all three fingerprint-length suffixes, and asserts the call returns a distinct, valid name rather than hanging.
- Existing tests in `tests/test_refresh_atomic_commit.py`, `tests/test_refresh_decompile_onboarding.py`, and `tests/test_refresh_contract_preflight.py` — which monkeypatch `load_contract_registry` directly on the `analyze_service` module attribute — are expected to keep passing unmodified, since the patch target doesn't depend on where the real implementation lives. Confirm this holds rather than assuming it.
- Existing tests in `tests/test_contract_acceptance.py` that assert `ContractAcceptanceError` codes for registry-load failures (missing file, invalid JSON, invalid content) are expected to keep passing unmodified, since `strict=True` reproduces the exact current behavior and the error is translated back into `ContractAcceptanceError` at the same seam as before.

## Out of Scope

- Any change to the *content* of registry-validation rules (what counts as a valid contract name or entry) — only where that logic lives changes, not what it accepts or rejects.
- Removing the double-validation inside `_prepare_registry`/`_prepare_versioned_registry` (loading, then re-validating) — both calls move to the shared implementation, but the redundancy itself is untouched.
- Any change to `commit_staged_contract_transaction` or the atomic two-file write path (`contract_transaction.py`) beyond importing the shared path constants — the write/commit story was already unified separately (ADR 0004's completion note, `unify-contract-acceptance-transaction`).
- Any change to `DbInvocation` construction, wrapper-evidence field collapsing, or `ProjectScanner`'s scan loops — these were separate, independently-scoped candidates from the same architecture review and are not part of this spec.
- Any new ADR — this spec extends work already covered by ADR 0004 (the read/naming-side counterpart to its already-accepted write-side unification) and does not introduce a new architectural decision requiring its own ADR.
- Changing the fingerprint-suffix lengths (`[:12]`, `[:16]`) or the ordinal-fallback format themselves — the existing, already-shipped algorithm from `contract_preflight.py` is reused as-is.

## Further Notes

This spec was produced from a grilling session over architecture-review candidate #1 ("one registry, two implementations") from an `/improve-codebase-architecture` review of `Impact_analysis_system` and `llamaindex-spec-rag` together. The infinite-loop defect and the fail-open/fail-closed and content-validation divergences were confirmed by reading `contract_preflight.py`, `contract_acceptance.py`, and `contract_transaction.py` directly, and by checking `service/api.py`'s existing `ContractAcceptanceError` handling and the existing test suite's monkeypatch targets, rather than assumed. The two-commit split (immediate naming fix, then full consolidation) and the `strict` flag's exact semantics were both explicit decisions made during that session — see the `unify-contract-acceptance-transaction` spec for the closely related, already-specified sibling effort (the write-side counterpart to this read/naming-side change) and for the same repo's spec-writing conventions this document follows.
