# 03 — Repair existing caches and cut over to the fixed graph version

**What to build:** Every SQL Execution Graph cache already on disk was built under the old, corrupting write behavior — `01` and `02` alone don't fix data that's already wrong. This ticket invalidates every existing cache and repairs it in one pass, without needing a live SQL Server connection to any target database, so the whole system moves onto correct offsets (and the new `02` staleness field) in a single, coordinated cutover instead of leaving stale caches to fail unpredictably.

**Blocked by:** 02 — the repair tool must run only after `02`'s node-schema addition exists, so its one pass produces caches carrying both the corrected offsets and the new defensive-check field together. If the version bump and repair shipped before `02`, every repaired cache would need a second repair pass once `02` landed.

**Status:** done

- [x] `GRAPH_VERSION` in `service/sql_execution_graph.py` is bumped from `2` to `3`.
- [x] A new repair tool, modeled on the existing `tools/migrate_sql_cache_keys.py` pattern (read each cache file directly off disk, transform, re-save), rebuilds `sql_execution_graph` for every cache file using that cache's own already-persisted `procedures`/`views`/`functions` `definition` text — no SQL Server connection or credentials required.
- [x] The repair tool supports `--dry-run`, matching the existing migration tool's interface.
- [x] The repair tool only modifies each cache file's `sql_execution_graph` field and its `graph_version`; every other field in the cache file is left byte-identical.
- [x] `tests/test_sql_cache_store.py`'s `test_sql_cache_rejects_stale_graph_version` is extended/updated for the new constant value, confirming caches still carrying the old version are rejected.
- [x] A new test builds a fixture cache carrying the old `graph_version` and already-correct `definition` text (no live database), runs the repair tool against it, and asserts the resulting `graph_version` matches the current constant, every operation's offset is in-bounds for that cache's own definitions, and `02`'s stored-length field is populated.
- [x] The `GRAPH_VERSION` bump and the repair tool land together in this one ticket — the bump is never merged without the repair tool available to run immediately after, so declared databases never sit in a `SqlExecutionGraphRequiredError` window waiting on a manual SQL Server reconnect.

## Comments

- `service/sql_execution_graph.py`: `GRAPH_VERSION` bumped `2` → `3`, with a new comment explaining the bump forces every pre-01/02 cache through the repair tool before its offsets are trusted again. `service/sql_cache_store.py`'s `_is_valid_cache()` already rejects any cache whose `graph_version` doesn't match the constant, so this alone made every existing cache unusable until repaired — the new tool exists to close that window in one pass.
- New `tools/repair_sql_execution_graphs.py`, modeled on `tools/migrate_sql_cache_keys.py`'s CLI shape (`--cache-root`/`--dry-run`, a pure `repair_all_caches()`/`repair_cache_file()` returning per-file result dicts, `main()` printing labeled status lines). For each `*.json` cache file (skipping `*.meta.json`) it re-runs `build_sql_execution_graph()` against that file's own already-persisted `procedures`/`views`/`functions` definitions and replaces only the `sql_execution_graph` field — no SQL Server connection, since `StaticAnalyzerHost` is a local `dotnet`-built ScriptDom host, not a DB client. Unlike the migrate tool, this does a full `json.dumps()` re-write rather than a surgical byte splice (the field being replaced is a large nested object, not a scalar), which stays byte-identical for every other field only because `sql_cache_store._save()` is the sole real writer of these files and always uses the same `json.dumps(data, ensure_ascii=False, indent=2)` parameters — documented inline as a call-out, since this is exactly the concern the migrate tool's own comment names.
- `tests/test_sql_execution_graph.py`'s `test_sql_cache_rejects_stale_graph_version` (the actual home of the test the spec names — it lives here, not in `test_sql_cache_store.py`) now asserts `GRAPH_VERSION == 3` directly and rejects a fixture at `GRAPH_VERSION - 1` (i.e. `2`, the real pre-repair version) rather than an arbitrary stale value. Two adjacent fixtures in the same file (`test_sql_cache_rejects_database_mismatch_from_memory_and_disk`, `test_sql_cache_rejects_stale_payload_version`) were switched from a hardcoded `"graph_version": 2` to the imported `GRAPH_VERSION` constant, since their point is a *different* rejection reason and they should stay valid on the graph-version axis so the test isn't accidentally passing for the wrong reason.
- New `tests/test_repair_sql_execution_graphs.py`: builds a fixture cache at the old graph version with a real stored-procedure definition (a `DELETE` plus a dynamic-SQL `EXEC(@sql)`, so both `dml_operation` and `unresolved_dynamic_sql` node types are exercised — not just the former), runs the repair tool with the real `StaticAnalyzerHost` (no mocking, no live database), and asserts `graph_version` lands on the current constant, every offset-bearing node's `start_offset + length` stays within the definition's own length, and ticket 02's `module_definition_length` is populated on every such node. Also covers: the repaired cache is accepted by `sql_cache_store.load_cached()`; only `sql_execution_graph` changes (checked both by value-equality on every other field *and* by reconstructing the expected output bytes and comparing byte-for-byte, proving the rewrite is a pure field swap under identical serialization, not just an incidentally-matching one); `--dry-run` touches zero bytes on disk; repeated runs are idempotent (`repaired` then `already_current`); an already-current cache is left untouched.
- `/code-review` (Standards + Spec axes, via two parallel sub-agents) found two real issues, both fixed before landing: (1) Standards — the initial `entry["action"] = "error"` default in `repair_cache_file()` and the corresponding `"error"` label in `main()`'s label map were dead code (every return path overwrote `action` before returning); removed the default and switched the label lookup to `labels.get(action, ...)` with a safe fallback instead of indexing. (2) Spec — the byte-identity test only checked value-equality, not actual bytes, so the checklist's literal "byte-identical" claim was untested; added a true byte-level assertion (reconstruct expected output by splicing the new graph into the original dict and re-serializing, compare to what's actually on disk) and a code comment explaining why a full re-dump — rather than the migrate tool's surgical byte splice — still guarantees this. Standards axis also flagged the broad `except Exception` around the read/parse step as a judgement call (intentional: a batch repair over an unbounded glob of cache files shouldn't abort on one unreadable file, unlike the migrate tool's fixed 2-entry scope) — left as-is with its existing inline rationale comment.
