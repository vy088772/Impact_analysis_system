# Harden SQL Execution Graph Offset Integrity

## Problem Statement

When a change-impact question requires expanding an Execution Path's evidence — the source-backed SQL fragment for a terminal DML operation — the system sometimes fails outright with a `stale_path` (409) error, and, more dangerously, sometimes does not fail at all: it can silently return text sliced from the wrong position inside a stored procedure's definition. A user relying on the resulting AI-integrated answer either sees an unnecessary "cannot confirm" hedge on a fact the system had, in fact, already proven (observed live: a `TransactionApp.Page_Load` read of `STCSupplier` was downgraded to "unresolved" even though the underlying Database Invocation was rated `proven`), or — in the unconfirmed but structurally identical case of an operation earlier in a stored procedure — could receive outright wrong SQL content presented as confirmed evidence, with nothing in the system today able to tell the user or the developer that this happened.

Root cause, confirmed against real production data: this service's SQL Execution Graph is built by having a .NET ScriptDom parser compute character offsets against a temp file that `service/sql_execution_graph.py` writes from a stored procedure's `definition` text. That write uses Python's default text-mode `write_text()`, which translates every `\n` character to the host OS's line separator. This service's actual deployment target is Windows, where the line separator is `\r\n` — and because SQL Server's definition text already uses `\r\n` line endings, every existing `\r\n` gets its `\n` half translated too, doubling it to `\r\r\n` in the temp file ScriptDom actually parses. The JSON cache, meanwhile, persists the original, un-doubled `definition` text. Every offset ScriptDom records is therefore computed against a text one character longer per line than the text it will later be sliced against, and the drift compounds with every line: for an operation late in a procedure, slicing runs past the end of the real text and fails loudly (`stale_path`); for an operation earlier in the same procedure, the same class of drift can still land inside the real text's bounds and silently return a wrong slice with no error at all.

This was reproduced end-to-end against real data, not just inferred: this investigation took the real, correctly-stored `definition` text for STC's `spSelConsigneeDetailData` (server `vmsystest07.topmost.com.tw`), deliberately re-created the Windows write corruption on it, and fed the result to the real ScriptDom host (`StaticAnalyzerHost`, confirmed runnable in this dev environment — `dotnet` is cross-platform and this repo's existing test suite already exercises it directly). The reproduced offset for the affected operation (`1387`, length `165`) is byte-for-byte identical to the broken offset already sitting in the live production cache. Slicing the corrected offset against the un-corrupted text also reproduces, verbatim, the SQL fragment already independently observed in a real AI-generated analysis report.

## Solution

Stop the corruption at its source, invalidate and repair every SQL Execution Graph cache built under the old write behavior, and add a defensive check so that any future offset/text mismatch — regardless of cause — fails loudly instead of silently returning misaligned SQL text.

This spec covers only this root cause. A separate, related finding from the same investigation — `MAX_COMPACT_PATHS` truncation and the relevance-blind compact-path sort in `llamaindex-spec-rag` — is out of scope here and is being scoped as its own spec in session `e90e6716-bc51-4007-bf8c-51302bfa34ad`.

## Implementation Decisions

- **Root fix**: `service/sql_execution_graph.py`'s temp-file write for ScriptDom input changes from `input_path.write_text(definition, encoding="utf-8")` to `input_path.write_text(definition, encoding="utf-8", newline="")`. `newline=""` disables Python's text-mode newline translation entirely, so the bytes written match `definition` exactly regardless of host OS.
- **Confirmed single call site**: this is the only place in the codebase that writes raw multi-line source text to a temp file for a downstream offset-computing parser to re-read, and separately persists another copy of the same text for later comparison. No other `write_text()` call in `service/` or `code_analyzer/` shares this risk shape (the others write JSON or report content, with no downstream position-sensitive re-parsing against a separately-stored copy).
- **Version gate**: `service/sql_execution_graph.py`'s `GRAPH_VERSION` constant moves from `2` to `3`. `sql_cache_store._is_valid_cache()` already rejects any cached graph whose `graph_version` doesn't match the current constant, so this alone makes every existing on-disk cache (built under the old write behavior) invalid the moment this change ships.
- **Repair tool**: a new script, following `tools/migrate_sql_cache_keys.py`'s existing pattern — read each cache file directly off disk, transform, re-save — rebuilds `sql_execution_graph` for every cache using that cache's own already-persisted `procedures`/`views`/`functions` `definition` text (via `build_sql_execution_graph`, running under the fixed write path). No SQL Server connection or credentials are required. Only the `sql_execution_graph` field and its `graph_version` are overwritten; every other field in the cache file is left byte-identical. Supports `--dry-run`, matching the existing migration tool's interface.
- **Defensive length check**: at graph-build time, each `dml_operation`/`unresolved_dynamic_sql` node's `source` metadata gains the current length of the module's `definition` text at the moment the graph was built. At evidence-expansion time (`analyze_service.py`'s `_slice_utf16`/`get_path_evidence` path), before slicing, this stored length is compared against `len(operation_module.get("definition"))` as currently loaded; a mismatch raises `PathEvidenceError("stale_path", ...)` with a reason naming the mismatch, before any slicing is attempted. This closes the case that produced no error today: an operation early enough in a procedure that a drifted offset still lands inside the real text's bounds.
- **Rollout order**: the write fix, the `GRAPH_VERSION` bump, and the repair tool ship together in the same change. The `GRAPH_VERSION` bump is never deployed without the repair tool available to run immediately after, to avoid a window where every declared database reports `SqlExecutionGraphRequiredError` until someone manually reconnects to SQL Server per database.
- **Explicitly not part of this spec's interface**: `path_selection.py`'s (`llamaindex-spec-rag`) evidence-loading retry/backup-path behavior is untouched. It was investigated during the same session and found not to help this specific failure mode (the duplicate paths examined during that investigation all resolved to the same `terminal_operation_id`, so retrying via a different `path_id` reproduces the identical offset bug); it remains a distinct, agent-layer resilience question tracked in session `e90e6716-bc51-4007-bf8c-51302bfa34ad` alongside the `MAX_COMPACT_PATHS` follow-up.

## Testing Decisions

- A good test here asserts the externally observable relationship between a stored offset and the text it's sliced against — never ScriptDom's internal parse tree shape or the repair tool's internal call sequencing.
- **Root fix + reproduction**: extends `tests/test_sql_execution_graph.py`, using the same live-`StaticAnalyzerHost` pattern `test_sql_host_emits_typed_operations_with_module_and_source_evidence` already uses (no mocking of ScriptDom itself). Two paired tests: (1) a definition containing `\r\n` line endings, written through the fixed `write_text(..., newline="")` path, asserts every resulting operation's `start_offset + length` stays within the definition's own length; (2) the same definition, deliberately re-corrupted the way the old write behavior produced it (`\r\n` → `\r\r\n`), asserts the same class of out-of-bounds condition this investigation found in production reproduces. This is the same reproduction this investigation already ran manually; the tests pin it down permanently.
- **Version gate**: extends `tests/test_sql_cache_store.py`'s existing `test_sql_cache_rejects_stale_graph_version`, updated for the new constant value — same pattern, no new test infrastructure.
- **Defensive length check**: extends `tests/test_exact_path_evidence.py`'s existing `test_path_evidence_rejects_stale_source_snapshot` pattern (the C# side's analogous staleness test), adding the SQL-offset-length-mismatch case and asserting `PathEvidenceError.code == "stale_path"`.
- **Repair tool**: a new test builds a fixture cache (no live database) carrying an old `graph_version` and already-correct `definition` text, runs the repair tool against it, and asserts the resulting `graph_version` matches the current constant and every operation's offset is in-bounds for that cache's own definitions.
- No test in this spec requires a live SQL Server connection or a Windows host; the `StaticAnalyzerHost`/ScriptDom dependency is real (not mocked) and already runnable in this dev environment via `dotnet`, consistent with this repo's existing test suite.

- Any change to the C# side's existing `source_snapshot_hash` content-pinning mechanism — it is the working precedent this spec's new SQL-side check is modeled on, not something this spec modifies.

## Further Notes

This spec was produced from a live investigation that started as an unrelated question about `MAX_COMPACT_PATHS` truncation, escalated into an actual paid `mode 3` agentic run against the real system to observe LLM-router behavior, and serendipitously surfaced this offset-corruption bug via a `stale_path` 409 raised mid-run during evidence expansion. The root cause was not left as a plausible theory: this investigation reproduced it end-to-end against real production data — taking STC's real, correctly-cached `spSelConsigneeDetailData` definition text, deliberately re-creating the exact corruption the old write path would have produced, and feeding it to the real ScriptDom host — and the reproduced offset (`1387`, length `165`) matched the broken offset already sitting in the live cache byte-for-byte. The same reproduction, run against the fixed write path, produced an in-bounds offset. Both directions of this reproduction are what Testing Decisions above turns into permanent regression tests.

One assumption from earlier in the investigation was wrong and is corrected here: it was initially assumed the real ScriptDom/`StaticAnalyzerHost` parser couldn't be exercised in this (non-Windows) dev environment, and that verification would have to fall back to a hand-rolled Python string-slicing simulation plus a manually-run Windows checklist. That assumption was checked and found false — `dotnet` is cross-platform, `StaticAnalyzerHost` builds and runs here, and this repo's existing test suite already exercises it directly. Only the Windows-specific *newline-translation* behavior itself can't occur naturally on this host; the reproduction above works around that by constructing the corrupted byte sequence explicitly rather than relying on the host OS to produce it. This is why the manual-Windows-verification item from the original triage no longer appears in Testing Decisions.

Problem A (the `MAX_COMPACT_PATHS` / relevance-sort / `path_selection` retry cluster) continues in session `e90e6716-bc51-4007-bf8c-51302bfa34ad`; anyone picking that thread up should start from that session rather than this one.
