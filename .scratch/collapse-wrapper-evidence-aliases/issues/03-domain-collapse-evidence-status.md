# 03 — Collapse `evidence`/`evidence_status` to `evidence_status` at the domain seam

**What to build:** `project_wrapper_evidence` (introduced in ticket 02) and `WRAPPER_EVIDENCE_FIELDS` stop emitting the `evidence` key inside the wrapper-evidence bag, keeping only `evidence_status`. This is the one alias group in this spec with real cross-repo risk, so it lands only after `llamaindex-spec-rag` no longer depends on the old name.

**Blocked by:** 01 (spec-rag must have already migrated off `evidence`), 02 (builds on the `project_wrapper_evidence` seam and shrunk `WRAPPER_EVIDENCE_FIELDS` that ticket introduces).

**Status:** resolved

- [x] `project_wrapper_evidence`'s output no longer includes an `evidence` key inside the wrapper-evidence bag; `evidence_status` remains and continues to carry the same value `evidence` used to.
- [x] `WRAPPER_EVIDENCE_FIELDS` drops the `evidence` entry, keeping `evidence_status`.
- [x] `DbInvocation`'s own top-level `evidence: InvocationEvidence` field, and the top-level `evidence` key `_serialize_db_invocation` emits for it in `analyze_service.py`, are untouched — this ticket only removes the duplicate `evidence` key inside the wrapper-evidence bag on `PathEvidenceResponse`/`SPMatchProgram`/`TableMatchProgram`, not the invocation's own core evidence field.
- [x] Any existing test asserting `evidence` inside the wrapper-evidence bag (as opposed to the invocation's own top-level `evidence`) is rewritten to assert `evidence_status`.
- [x] Full existing test suite passes.

**Further Notes:** The `evidence` field on `PathEvidenceResponse`/`SPMatchProgram`/`TableMatchProgram` was not a byte-for-byte duplicate of `evidence_status` in one respect: on path-based responses (`PathEvidenceResponse` via `_materialize_path_evidence`, and the `via_sp` `TableMatchProgram` branch), the schema's `evidence` field was fed from the *path*-level rating (`path.get("evidence")`), which `execution_path_builder.py` can downgrade to `"unresolved"` on `missing_graph_target`/`unresolved_dynamic_sql`/`stored_procedure_call_cycle` even when the underlying invocation's own rating stayed `"proven"` — while the wrapper-evidence bag's `evidence_status` always carried the invocation's raw (non-downgraded) rating. Collapsing to one field kept the more informative, override-aware path-level value under the sole surviving name `evidence_status` (construction sites in `analyze_service.py` now pass `evidence_status=str(path.get("evidence") or "unresolved")` instead of the old `evidence=...` kwarg), so no downgrade information is lost. `DbInvocation`'s own top-level `evidence`/`_serialize_db_invocation`'s `evidence` key, and every non-schema raw-dict `"evidence"` key produced by `execution_path_builder.py`/`flow_chain_builder.py`/`graph_queries.py`/`migration_report.py` (the path/access-record's own core evidence rating, not part of the wrapper-evidence bag), are untouched — out of this ticket's scope. Full suite run: 389 passed, the same 11 pre-existing failures as before this change (verified via `git stash`), tests/test_search_roles.py and tests/test_sp_tables.py still fail collection for the pre-existing no-ODBC-driver reason.
