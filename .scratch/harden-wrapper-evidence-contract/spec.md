# Harden the Cross-Repo Wrapper Evidence Contract

## Problem Statement

`llamaindex-spec-rag`'s `impact_orch` package calls this service's `/analyze`, `/refresh`, and `/path_evidence` endpoints over HTTP and reads the JSON response with loose `dict.get(...)` calls. This service already made `evidence_status` the one canonical wire key for the wrapper-evidence bag (see `.scratch/collapse-wrapper-evidence-aliases/spec.md`, landed today), but that spec explicitly left "building a typed response model, client SDK, or cross-repo contract test for `llamaindex-spec-rag`" out of scope. Nothing mechanically enforces agreement across the repo boundary today:

- `RefreshResponse.wrapper_summary` is declared `Dict[str, Any]` — the one response shape with no Pydantic validation at all, unlike `PathEvidenceResponse`/`SPMatchProgram`/`TableMatchProgram`, which already inherit the canonical `WrapperEvidenceFields` base model.
- Neither repo publishes or consumes a shared schema. `impact_orch`'s tests (`tests/test_refresh_cli.py`, `tests/test_path_selection.py`, `tests/test_path_evidence_wiring.py`) build `wrapper_summary`/`review_items`/`evidence`/`evidence_status` payloads as hand-written literal dicts, so they can drift from what the service actually returns without any test failing.
- On the `impact_orch` side, the concept "Evidence Status" has no owning module. `context_builder.py`, `path_selection.py`, and `refresh_cli.py` each independently interpret the raw JSON, and the interpretation is inconsistent: some sites read a flat `evidence` string, some read a nested `evidence.evidence_status`, and `refresh_cli.py` reads `review_items[].evidence_status` directly. This exact mismatch already shipped as a bug, fixed reactively across five call sites in commit `90065e4`.
- A further hazard surfaced during design: `impact_orch`'s own `CONTEXT.md` separately defines "Evidence Status" as a 4-value concept (`proven`/`partial`/`ambiguous`/`unresolved`) describing a path-level or query-level conclusion. This service's `CONTEXT.md` defines "Evidence Status" as a 3-value concept plus a `not_applicable` sentinel (`proven`/`likely`/`unresolved`/`not_applicable`) describing a single Database Invocation's confidence rating. These are two distinct concepts that happen to share a name across the two repos' domain glossaries. Nothing today documents that they are unrelated, which risks a future contributor conflating them.

## Solution

Give the wrapper-evidence data a durable, mechanically-checked contract across the repo boundary, and give `impact_orch` a single module that owns parsing this service's Evidence Status data — so a future field rename either stays backward compatible or fails a test on the consumer side instead of silently returning a default.

This service publishes a versioned, machine-readable schema for its response shapes, including the currently-untyped `wrapper_summary`. `impact_orch` gains one small module responsible for turning this service's raw JSON into two explicitly distinct, statically-typed values — one for a Database Invocation's own evidence rating, one for a wrapper-evidence-bag's evidence status — and every existing consumer of that data switches to it. The two concepts stay explicitly separate at the type level; nothing in this spec merges or renames either repo's "Evidence Status" glossary entry, and the fact that they are two distinct concepts sharing a name gets documented in both repos' `CONTEXT.md`.

4. As a maintainer of this service, I want the OpenAPI export regenerated by a small script rather than hand-maintained, so that the exported file can't drift from the live FastAPI route definitions.

6. 7. As a maintainer of `llamaindex-spec-rag`, I want one module that owns interpreting this service's Evidence Status data, so that a rename on the producer side requires a change in one place instead of a grep across `context_builder.py`, `path_selection.py`, and `refresh_cli.py`.

9. As a maintainer of `llamaindex-spec-rag`, I want a small helper that turns a parsed evidence rating into a verified/unresolved boolean, so that the "is this good enough to present" decision is asked and answered in one place instead of being re-derived at each call site.
10. As a maintainer of `llamaindex-spec-rag`, I want `rag_client.py`'s `analyze()` and `path_evidence()` to return already-parsed, typed evidence values instead of raw JSON, so that every current and future caller gets the parsing for free instead of having to remember to call it themselves.
11. As a maintainer of `llamaindex-spec-rag`, I want `context_builder.py` to read evidence data exclusively through the new module, so that its rendering logic stops guessing which of several possible JSON shapes it was handed.
12. As a maintainer of `llamaindex-spec-rag`, I want `path_selection.py` to read evidence data exclusively through the new module, so that its decision loop's evidence checks share the same interpretation as the rest of the codebase.

14. As a maintainer of `llamaindex-spec-rag`, I want the module's interface to stay small — two typed accessors plus one boolean helper — so that learning to use it doesn't cost more than the ad hoc `dict.get(...)` calls it replaces.

16. As a maintainer of `llamaindex-spec-rag`, I want `CONTEXT.md` to note that this repo's own Evidence Status concept is unrelated to the producer service's identically-named concept, so that a future contributor reading both glossaries side by side isn't misled by the name collision.
17. As a system maintainer coordinating both repos, I want this service's changes (Pydantic model, OpenAPI export, ADR, `CONTEXT.md` update) to land and be verified working before `impact_orch`'s new module and its call-site migrations begin, so that the consumer-side work is built against a real, already-typed contract rather than guessing ahead of it.
18. As a code reviewer, I want this change to leave `DbInvocation`'s own `evidence` field and the wrapper-evidence bag's `evidence_status` field exactly as separate as they are today, so that no reviewer mistakes this spec for a field-renaming or field-merging change.

## Implementation Decisions

- **This service (`Impact_analysis_system`) — response typing**: `RefreshResponse.wrapper_summary` gains a Pydantic model matching the field set `reconcile_refresh_wrappers`/`wrapper_observation_fields` currently produce (`review_items`, each item's `evidence_status` restricted to the four known values `proven`/`likely`/`unresolved`/`not_applicable`, plus the existing `evidence_statuses`/`totals` aggregate fields). This is additive validation only — no field is renamed, dropped, or reshaped.
- **This service — schema export**: the FastAPI-generated OpenAPI schema is exported to a versioned file in the repo, regenerated by a small script rather than hand-maintained, covering at minimum the `/analyze`, `/refresh`, and `/path_evidence` response models.
- **This service — domain docs**: `CONTEXT.md`'s Evidence Status entry gains `not_applicable` as a documented fourth value. A new ADR (next number after the existing `docs/adr/0001`–`0006` sequence) records that this service's Evidence Status and `llamaindex-spec-rag`'s identically-named Evidence Status are two distinct concepts, and that this spec's contract-hardening work concerns only this service's concept. `llamaindex-spec-rag`'s `CONTEXT.md` references this ADR rather than duplicating its content, so the two repos don't maintain two copies of the same explanation.
- **`llamaindex-spec-rag` — new module**: one module owning Evidence Status interpretation, exposing exactly three functions:
  - an accessor that parses a Database Invocation's own evidence rating from raw response data into a typed value restricted to this service's controlled vocabulary,
  - a separately named accessor that parses a wrapper-evidence-bag's evidence status from raw response data into its own typed value (also covering the `not_applicable` sentinel),
  - a boolean helper that takes either typed value and reports whether it counts as verified (`proven`/`likely`) versus unresolved.

  The two accessors are deliberately kept as separate functions returning separate types rather than one function with a mode/kind parameter, so a caller cannot accidentally pass a Database-Invocation-shaped value to the wrapper-evidence-bag accessor or vice versa.
- **`llamaindex-spec-rag` — seam placement**: the two accessors are called from within `rag_client.py`'s `analyze()` and `path_evidence()` functions, at the HTTP response boundary, so those functions return already-typed evidence values rather than raw JSON. `rag_client.py`'s other five HTTP functions are not modified as part of this change; only `analyze()` and `path_evidence()` are touched, and only to add the parsing call at their existing return points.
- **`llamaindex-spec-rag` — call-site migration**: `context_builder.py`, `path_selection.py`, and `refresh_cli.py` all switch to reading evidence data through the new module's typed values (via `rag_client.py`'s now-typed returns, or by calling the module directly wherever a raw dict is still unavoidable, e.g. `refresh_cli.py`'s direct handling of `wrapper_summary.review_items`). All three call sites migrate together with the module's introduction — none are left on the old ad hoc parsing.
- **Rollout order**: this service's changes (Pydantic model, OpenAPI export, `CONTEXT.md`, ADR) are completed and verified first. `impact_orch`'s new module and the three call-site migrations begin only after that lands, so the consumer-side work is built and tested against the now-typed contract rather than in parallel with it.
- **Explicitly not part of this spec's interface**: the new module does not attempt to produce or interpret `impact_orch`'s own separate 4-value (`proven`/`partial`/`ambiguous`/`unresolved`) Evidence Status concept used for path-level or query-level conclusions elsewhere in the routing logic. That concept is computed by different logic (the path-selection decision loop) from different inputs and is untouched by this spec.

## Testing Decisions

- A good test here asserts observable behavior — the typed value an accessor returns for a given raw payload, or the externally observable JSON shape this service's response models produce — never internal call sequencing.
- **This service**: the new `wrapper_summary` Pydantic model gets a test asserting it accepts the exact shape `reconcile_refresh_wrappers` currently produces (regression guard: this change must not alter any currently-correct `/refresh` response), following the existing pattern in `tests/test_path_evidence_api.py` for asserting on response-model-validated payloads.
- **This service**: a test (or a documented manual step, if schema export isn't itself unit-testable) confirms the exported OpenAPI file matches the live schema, so the export can't silently go stale.
- **`llamaindex-spec-rag`**: the new module gets direct unit tests for each accessor and the verified/unresolved helper, covering all four known values plus an unrecognized/future value (to confirm the parser fails loudly rather than silently defaulting) — this is new test coverage the current ad hoc `dict.get(...)` reads don't have anywhere today.
- **`llamaindex-spec-rag`**: `tests/test_refresh_cli.py`, `tests/test_path_selection.py`, and `tests/test_path_evidence_wiring.py` have their hand-written dict fixtures replaced with fixtures validated against this service's exported OpenAPI schema (via `jsonschema` or equivalent), following the existing pattern each file already uses for constructing `monkeypatch`-based fixtures — only the fixture construction changes, not the assertions on rendered output.
- **`llamaindex-spec-rag`**: no live integration test against a running instance of this service is added as part of this spec; schema-based fixture validation is the full extent of contract testing here.

## Out of Scope

- `impact_orch`'s own separate 4-value Evidence Status concept (path-level/query-level conclusions) — untouched, and not something the new module produces or interprets.
- This service's residual internal cleanup of `wrapper_observation_fields`/`_serialize_db_invocation`'s triple-write (the part of the earlier alias-collapse effort left unfinished) — real, but a separate, independently-schedulable piece of work.
- `rag_client.py`'s boilerplate duplication across its six HTTP wrapper functions — only `analyze()` and `path_evidence()` are touched, and only to add the new parsing calls; the shared-`_call()`-helper collapse for all six stays a separate, lower-priority piece of work.
- Any live/E2E integration test that starts a real instance of this service — deferred; schema-based contract testing is this spec's full testing scope.
- Renaming, merging, or otherwise changing `DbInvocation`'s own `evidence` field or the wrapper-evidence bag's `evidence_status` field — they remain two separate, independently-populated facts, exactly as the earlier alias-collapse spec established.
- Any change to `/analyze`'s or `/path_evidence`'s already-typed response shapes (`PathEvidenceResponse`, `SPMatchProgram`, `TableMatchProgram`) — only the previously-untyped `RefreshResponse.wrapper_summary` gains new validation.

## Further Notes

This spec was produced from a grilling session (`codebase-design`/`grilling` skills) over a cross-repo architecture-review finding: `Impact_analysis_system`'s unfinished wrapper-evidence alias collapse and `llamaindex-spec-rag`'s missing Evidence-Status-owning module were flagged as two ends of the same seam, evidenced by the field-rename bug fixed in commit `90065e4`. Mid-session fact-finding corrected the original framing: the two repos' "Evidence Status" glossary entries are not the same concept under one name needing a single shared contract — they are two genuinely distinct concepts (a per-Database-Invocation rating vs. a per-path/query conclusion) that happen to share a name. That correction is load-bearing throughout this spec; see the "Explicitly not part of this spec's interface" and "Out of Scope" items above. The residual internal producer-side cleanup and the `rag_client.py` boilerplate collapse were both identified in the same architecture review but are deliberately deferred to separate specs rather than bundled here.
