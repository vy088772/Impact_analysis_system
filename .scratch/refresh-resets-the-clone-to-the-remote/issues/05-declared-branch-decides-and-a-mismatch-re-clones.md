# 05 — Changing the declared branch moves the clone to it

**What to build:** A maintainer changes the branch a System declares, runs a refresh, and gets a clone on the new branch. Today a clone tracks exactly one branch, because it is created shallow and single-branch, so fetching a different branch is not available to it. The refresh therefore deletes the whole directory and clones again.

**Blocked by:** 04

**Status:** done

- [x] A refresh reads the declared branch from settings and the catalog.
- [x] A refresh whose declared branch equals the recorded branch fetches and resets as usual.
- [x] A refresh whose declared branch differs from the recorded branch deletes the whole clone directory.
- [x] That refresh then clones the declared branch.
- [x] The new clone records the declared branch in `meta.json`.
- [x] A missing `meta.json` still does not count as a mismatch.

**Notes:** `CloneSynchroniser.synchronise()` (`code_analyzer/clone_synchroniser.py`) already received the declared branch as its `branch` parameter — `service/repo_manager.py`'s `_clone_or_pull()` was already resolving it from the catalog's `source.branch` (falling back to `settings.AZURE_DEVOPS_BRANCH`) before this ticket, so "reads the declared branch from settings and the catalog" needed no new code, only the comparison against what the clone actually holds. When an existing clone is found, `synchronise()` now reads the recorded branch out of `meta.json` via a new `_recorded_branch()` helper (rebuilding the file first via ticket 04's `_rebuild_meta()` if it's missing, so a missing file is resolved to git's own answer before comparison — never treated as a mismatch on its own) and compares it against the declared `branch` parameter. Equal → the existing fetch/reset/clean sequence, unchanged. Different → `shutil.rmtree(target)` deletes the whole directory, then a new `_clone_fresh()` helper (`mkdir` + `_clone`) rebuilds it on the declared branch — the same helper the never-cloned path now also calls, replacing what was two copies of the same two lines. This matches ADR-0023's reasoning directly: a shallow, single-branch clone's fetch configuration only tracks the one branch it was cloned with, so a branch change is not something `fetch`/`reset` can reach — proved in the test by planting a marker file inside `.git` before the mismatched refresh and asserting it's gone afterward, since an ordinary `clean -fd` never touches `.git`'s own contents but a full `rmtree` does. Tests: 3 new cases in `tests/test_clone_synchroniser.py` — matching-branch refresh (asserts `_clone` is not called, via `mock.patch.object`), mismatched-branch refresh (two real branches on the same bare remote, each with a file unique to it; asserts the `.git` marker is gone, the feature branch's file is present, and `meta.json` records the new branch and commit), and missing-`meta.json`-is-not-a-mismatch (deletes `meta.json`, refreshes on the *same* declared branch, asserts `_clone` is still not called). Ran `/code-review` (Standards + Spec sub-agents): Spec axis found all 6 checklist items implemented correctly, confirmed the "reads from settings and catalog" item is legitimately satisfied by existing `repo_manager.py` code rather than missing, found no scope creep from tickets 06/07 (no locking, no Windows-specific verification), and flagged only a non-atomicity observation (`rmtree` then `_clone` isn't atomic; a mid-clone failure leaves `target` without `.git`) that it judged fail-safe and not a spec gap, since the next `is_cloned()` check just sees no clone and retries.
