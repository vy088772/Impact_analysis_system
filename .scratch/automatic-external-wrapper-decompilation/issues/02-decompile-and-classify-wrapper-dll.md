# 02 — Decompile a referenced external wrapper DLL into classified facts

**What to build:** `StaticAnalyzerHost` gains the ability to take a wrapper receiver type that is unresolved against local source and the active contract registry, trace it to a concrete `.csproj` `<Reference>`/`HintPath` entry, decompile the referenced DLL with `ICSharpCode.Decompiler` (a build-time NuGet reference, no runtime download), and run the resulting syntax tree through the same `WrapperAnalyzer`/`CommandType`/terminal-sink classification logic already used for local wrapper source. Each classified snapshot carries an assembly identity computed as the SHA-256 hash of the DLL's raw bytes (not `AssemblyName`/`Version`). This only ever runs for a receiver traceable to a concrete `.csproj` reference — it never scans a directory for arbitrary DLLs, and a receiver that cannot be traced this way remains a review candidate.

**Blocked by:** 01.

**Status:** resolved

- [x] Given a receiver type, the host resolves the exact DLL path from the referencing project's `.csproj` `<Reference>`/`HintPath` entries, with no directory scanning
- [x] A receiver type that cannot be traced to a `.csproj` reference (e.g. dynamically loaded/reflection-only) is left as a review candidate, not a best-effort decompile
- [x] The DLL is decompiled to a C# syntax tree and classified through the existing `WrapperAnalyzer`/`CreateDefinition()` pipeline, producing the same shape of per-method facts (method identity, argument roles, `CommandType`/terminal sink) as local source
- [x] `SqlDataAdapter.Fill` remains a distinct terminal sink from `ExecuteReader` for decompiled input, exactly as for local source
- [x] Two methods with similar names but different fixed `CommandType` semantics are classified distinctly (no name-based merging)
- [x] Assembly identity is the SHA-256 hash of the DLL's raw bytes; two byte-identical DLLs produce the same identity, any other byte sequence produces a different one regardless of `AssemblyVersion`
- [x] A decompiler-reported translation problem for a method (unresolved IL construct, missing body, or equivalent error marker) is captured as a fact on that method's classification, not silently dropped
- [x] End-to-end smoke test: decompiling the checked-in `data/repos/System_Dept_1/STC/STC/bin/SQLFunc.dll` through the real `StaticAnalyzerHost` classifies `CreateAdapter` as fixed stored-procedure and `CreateAdapterTsql` as fixed inline text, and keeps `SqlDataAdapter.Fill`-based methods distinct from `ExecuteReader`-based ones

## Answer

Added `tools/StaticAnalyzerHost/WrapperDecompiler.cs` with three pieces:

- `AssemblyReferenceResolver.Resolve(csprojPath, receiverTypeName)` reads the `.csproj` XML directly and matches a `<Reference Include="Name, Version=...">`'s leading assembly-name segment (ordinal, exact) against the receiver type name, then resolves its `<HintPath>` relative to the `.csproj`'s directory. It never scans a directory; a `Reference` with no `HintPath` (GAC-style), no matching `Reference` at all, a missing `.csproj`, or a `HintPath` pointing at a non-existent file each return a distinct `UnresolvedReason` (`hint_path_missing` / `receiver_not_referenced` / `csproj_not_found` / `csproj_unreadable` / `referenced_dll_missing`) so the caller can leave the receiver as a review candidate.
- `WrapperAssemblyDecompiler.Decompile(dllPath, receiverTypeName)` hashes the DLL's raw bytes with SHA-256 for the assembly identity, then decompiles **per method** (`CSharpDecompiler.DecompileAsString(method.MetadataToken)`) rather than via `DecompileWholeModuleAsSingleFile()`, because the installed `ICSharpCode.Decompiler` 8.2.0.7535 release re-throws a `DecompilerException` out of a failing method instead of degrading to an inline error comment (that resilient per-member behavior is only in a newer/unreleased build). Decompiling per method means one untranslatable method (caught as `Exception` and recorded by name) never aborts the rest of the type. Each method snippet's own `using` directives are hoisted and de-duplicated above a synthetic `class {ReceiverTypeName} { ... }` wrapper (a `using` is not valid mid-class-body) before the whole thing is re-parsed by Roslyn (`CSharpSyntaxTree.ParseText`) into the same `CompilationUnitSyntax` shape `WrapperAnalyzer` already consumes for local source. A `.NET Framework` DLL like `SQLFunc.dll` needs `mscorlib`/`System.Data` reference assemblies to resolve its type system; these are obtained via a `PackageDownload` of `Microsoft.NETFramework.ReferenceAssemblies.net48` in the `.csproj` (restored into the NuGet cache, never referenced/shipped) and located at runtime via `NUGET_PACKAGES`/`~/.nuget/packages`.
- `DecompiledWrapperClassifier.Classify(csprojPath, receiverTypeName)` composes the two and calls the existing `WrapperAnalyzer.GetDefinitions(...)`, which gained a new overload accepting `assemblyIdentity`/`assemblyRevision` (previously hardcoded to `""`/`""`). A method whose body could not be decompiled at all never becomes a `MethodDeclarationSyntax` (so `CreateDefinition` could never classify it); `WrapperAssemblyDecompiler` instead builds a synthetic `WrapperDefinition` directly from the underlying `IMethod` metadata (name, parameter types, assembly identity) with `UnresolvedReason = "decompiler_translation_problem"`, appended to the same `wrapper_definitions` list the classifier returns — so a failed method is captured as a distinct, identifiable fact rather than silently vanishing from the output.

Exposed as a new `decompile-wrapper --csproj <path> --receiver-type <name>` command on the existing `StaticAnalyzerHost` console contract (contract version unchanged at 2; `--version`'s `commands` list gained the new command name), and a matching `StaticAnalyzerHost.decompile_wrapper()` Python client method, following the same subprocess/JSON pattern as `analyze_csharp`/`analyze_sql`.

Verified against the real checked-out `data/repos/System_Dept_1/STC/STC/STC.csproj` + `bin/SQLFunc.dll`: `CreateAdapter` classifies as `fixed_stored_procedure`, `CreateAdapterTsql` as `fixed_inline_sql`, `ExeTable`/`CreateTable`/`ExeProcDataSet` all resolve `terminal_sink: "Fill"` while `CreateReader`/`ExeProcRead` resolve `terminal_sink: "ExecuteReader"`, and `assembly_identity` matches an independently computed `hashlib.sha256` of the DLL's bytes. Contrary to the spec's expectation (based on a different decompiler/version rendering `CommandType` as `(CommandType)4`), this decompiler version and settings render `CommandType.StoredProcedure`/`.Text` as named members — issue 01's numeric-cast recognition remains in place defensively but wasn't exercised by this specific DLL. The translation-problem path was manually verified by temporarily forcing one real method's decompile to throw and confirming it surfaced as a `decompiler_translation_problem`-tagged fact in `wrapper_definitions` (reverted before commit; SQLFunc.dll itself decompiles cleanly with zero translation problems, so this path isn't exercised by the checked-in automated smoke test).

Validation: `dotnet build tools/StaticAnalyzerHost/StaticAnalyzerHost.csproj` succeeds with 0 warnings/errors.
