# Automatic External Wrapper Decompilation for Contract Onboarding

## Problem Statement

`refresh_cli` already runs `Contract Preflight` for every system whose `wrapper_contract` selector is unspecified, but preflight can only reuse or create a contract when a `Verified Implementation Snapshot` is already available. For an opaque external wrapper backed by a `.dll` with no available caller-visible source — for example `SQLFunc.dll`, referenced by the `STC` system — no such snapshot exists today. Every call through `SQLFunc.ExeProcRead`, `SQLFunc.ExeProcNon`, and similar methods therefore stays `unresolved_contract` forever, even though the DLL itself is sitting on disk and can be decompiled by a human at any time (as verified by manually inspecting a decompiled `SQLFunc.cs` during this session).

The operator's actual workflow today is manual and out of band: open the DLL in a decompiler, read the method bodies by hand, and either give up or hand-write an `Implementation Snapshot` for the explicit acceptance tool. This does not scale to every opaque wrapper in every system, and it means a normal `refresh_cli` run can never resolve this class of `Database Invocation` on its own.

## Solution

Extend `refresh_cli`'s existing Contract Preflight so that, specifically when a system's `wrapper_contract` selector is unspecified and a full-system (non-program-scoped) refresh is running, an unresolved external wrapper whose receiver type resolves to a `.csproj` assembly reference is decompiled automatically, analyzed with the same Roslyn-based wrapper-analysis engine already used for local source, and — when the result is judged complete — staged and committed as a new or reused contract with no human review step, exactly like the existing local-source onboarding path.

The decompilation step lives in `StaticAnalyzerHost` (the existing .NET/Roslyn analyzer host), not in a separate Python-orchestrated tool. It uses `ICSharpCode.Decompiler` to turn the referenced assembly into a syntax tree, then reuses the existing wrapper-definition, `CommandType`, and terminal-sink resolution logic that already classifies local wrapper source such as `SQLObject`. That existing logic must be extended to recognize a numeric `CommandType` cast (for example `(CommandType)4`) as equivalent to the named member access (`CommandType.StoredProcedure`) it already recognizes, because decompiled output from this DLL renders the enum as a cast rather than a named member.

Assembly identity is the SHA-256 hash of the DLL's bytes, not its `AssemblyName`/`Version` string, because the observed reference (`SQLFunc, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null`) is unsigned and its version number does not change between rebuilds. This means a byte-identical rebuild with no logic change is treated as the same assembly, but a rebuild that changes only compiler output (without changing source) is treated as a new revision and re-decompiled; this cost is accepted deliberately. A failed or incomplete decompilation attempt is cached against the DLL's hash so an unchanged DLL is not re-decompiled on every subsequent refresh.

A contract produced this way is functionally identical to one produced from local source or a hand-authored snapshot, but its registry entry carries an additional provenance marker identifying it as decompiler-sourced, so a later audit can find every contract that was never read by a human before taking effect.

This feature narrows and supersedes the specific clause in ADR 0004 (and the companion `unified-database-invocation-classification` spec's Out of Scope) that forbids "downloading or decompiling an arbitrary external DLL as an automatic refresh side effect." It does not relax any other rule from that spec: `Evidence Status`, `SP Catalog` validation, connection-source resolution, and the separation between `wrapper_contract` selection and procedure proof all remain exactly as previously specified. Decompilation only ever supplies method semantics and terminal sink facts — never a stored-procedure target's existence, which still requires the resolved connection source's `SP Catalog`.

## User Stories

1. As a system operator, I want `refresh_cli` to automatically decompile an opaque external wrapper DLL when the system has no configured `wrapper_contract`, so that I don't have to manually decompile and hand-write a snapshot for every legacy DLL wrapper.
2. As a system operator, I want this decompilation to trigger only when the catalog's `wrapper_contract` selector for that system is unspecified, so that an explicitly configured contract remains fully authoritative and is never second-guessed by an automatic decompile.
3. As a system operator, I want decompilation-based onboarding to run only during a full-system refresh, never a program-scoped refresh, so that a partial update can never introduce an incomplete or one-off contract.
4. As a system analyst, I want the receiver type observed at a call site (for example `SQLFunc`) to be matched against the referencing project's `.csproj` `<Reference>`/`HintPath` entries, so that the system can locate the exact DLL on disk without guessing or scanning unrelated files.
5. As a system analyst, I want the decompilation itself to run inside the existing `StaticAnalyzerHost` .NET process, so that it reuses the same Roslyn syntax-tree infrastructure already used for local source instead of introducing a second toolchain.
6. As a system analyst, I want the decompiled syntax tree to be classified by the same wrapper-definition, `CommandType`, and terminal-sink resolution logic already used for local wrapper source, so that decompiled and hand-written source produce identical classification semantics.
7. As a system analyst, I want the `CommandType` resolution logic to recognize a numeric cast such as `(CommandType)4` as equivalent to `CommandType.StoredProcedure`, so that decompiled output (which frequently loses the named enum member) is not silently misclassified as unresolved or as inline SQL.
8. As a system analyst, I want the numeric-to-named `CommandType` mapping to cover at least `Text` (1), `StoredProcedure` (4), and `TableDirect` (512), so that every standard ADO.NET `CommandType` value is recognized regardless of how a decompiler renders it.
9. As a system analyst, I want `SqlDataAdapter.Fill` to remain a distinct terminal sink when classifying decompiled code, exactly as it already is for local source, so that a decompiled `CreateTable`/`ExeTable`-style method is not reported as `ExecuteReader`.
10. As a system analyst, I want two methods with similar names but different fixed `CommandType` semantics (for example a decompiled `CreateAdapter` that is fixed stored-procedure versus a `CreateAdapterTsql` that is fixed text) to remain distinct, so that a naming coincidence never merges two different behaviors.
11. As a system maintainer, I want the completeness check for a decompiled snapshot to reuse the existing `Implementation Snapshot` validation rules (every public database operation has a resolved method body, `CommandType`, and terminal sink; no unknown overloads; single assembly revision), so that decompiled evidence is held to the same bar as hand-authored evidence.
12. As a system maintainer, I want the completeness check to additionally fail whenever the decompiler itself reports a translation problem for any relevant method (an unresolved IL construct, a missing body, or an equivalent decompiler-emitted error marker), so that a method the decompiler could not faithfully render never contributes to an active contract.
13. As a system maintainer, I want a decompiled snapshot that fails completeness to leave the affected wrapper `unresolved` with a `contract_preflight_failed` reason, exactly like any other incomplete preflight proposal, so that this path introduces no new failure semantics.
14. As a system maintainer, I want a decompiled snapshot that passes completeness to be staged and, on successful formal classification and reconciliation, committed through the existing two-file atomic transaction, exactly like any other complete preflight proposal, so that no second commit mechanism is introduced.
15. As a system maintainer, I want no human review step between a complete decompiled snapshot and its contract becoming active, so that the operator does not have to manually confirm every legacy wrapper before it can be used.
16. As a system maintainer, I want every contract created from a decompiled snapshot to carry a distinct provenance marker (for example a `decompiled_auto` evidence kind) separate from `contract_lifecycle_status`, so that an auditor can later find every contract that went active without a human ever reading the code.
17. As a system maintainer, I want this provenance marker to be visible in the refresh response's wrapper summary and in the contract registry entry, so that it survives into every later report without requiring a second lookup.
18. As a system maintainer, I want the assembly identity of a decompiled snapshot to be the SHA-256 hash of the DLL's raw bytes, so that an unsigned, unversioned legacy DLL still gets a reliable, change-sensitive identity.
19. As a system maintainer, I want a rebuild of the same DLL with unchanged logic but different compiled bytes to be treated as a new revision requiring a fresh decompile, so that the system never silently assumes two different binaries are identical.
20. As a system maintainer, I want a completed or failed decompilation attempt to be cached against the DLL's hash, so that an unchanged DLL is not re-decompiled on every subsequent refresh.
21. As a system maintainer, I want the cached failure to be invalidated only when the DLL's hash changes or a maintainer explicitly requests a re-run, so that a persistently incomplete DLL does not cause repeated wasted work.
22. As a system maintainer, I want this capability to apply to any future opaque external wrapper DLL, not only `SQLFunc`, so that the next legacy wrapper does not require a second bespoke implementation.
23. As a system analyst, I want a stored-procedure candidate discovered via a decompiled contract to still require a resolved connection source and a matching database-scoped `SP Catalog` entry before it is `proven`, so that decompilation is never treated as proof of a procedure's existence.
24. As a system analyst, I want `connection source` and `invocation mode` to remain separate facts for decompiled invocations exactly as they already are for source-backed and explicitly selected ones, so that this feature does not introduce a second, weaker evidence model.
25. As a system maintainer, I want local source-backed implementation evidence to remain stronger than a decompiled contract when both are somehow available for the same receiver, so that a current, caller-visible `.cs` file is never overridden by a decompiled guess.
26. As a system maintainer, I want a receiver type that cannot be traced to a `.csproj` reference (for example a dynamically loaded or reflection-only assembly) to remain a review candidate rather than trigger a best-effort decompile, so that the system never guesses at a DLL location.
27. As a system operator, I want the refresh summary to report when a decompilation attempt was made, its outcome (complete, incomplete, cached-skip), and the reasons for an incomplete result, so that I don't have to read raw logs to understand why a wrapper is still unresolved.

As a maintainer, I want a new ADR to record that this feature narrows the prior "no automatic DLL decompilation" boundary, and exactly which conditions (unspecified selector, full-system refresh, hash-based identity, automatic completeness judgment, provenance-tagged, cached-by-hash) make the narrower version safe, so that a future reader understands why the boundary changed.
32. As a maintainer, I want `Implementation Snapshot`, `Verified Implementation Snapshot`, and `Assembly Revision Boundary` added to the project glossary, since they are used extensively by the existing spec but were never captured in `CONTEXT.md`.

## Implementation Decisions

- The seam for this feature is the existing `StaticAnalyzerHost` versioned console contract plus the existing `run_contract_preflight()` entry point in `service/contract_preflight.py`. No new high-level module or second classifier is introduced.
- `StaticAnalyzerHost` gains the ability to: resolve a wrapper receiver type to a `.csproj` `<Reference>`/`HintPath` DLL path, decompile that DLL with `ICSharpCode.Decompiler`, and run the resulting syntax tree through the same wrapper-definition/`CommandType`/terminal-sink resolution already used for local source (`WrapperAnalyzer` and related helpers in `CSharpAnalyzer.cs`). This is exposed as an additive capability of the existing analyzer host, not a separate executable.
- The `CommandType` recognition helpers are extended to treat a cast of a numeric literal to `CommandType` as equivalent to the named member access they already recognize, mapping at least `1` → `Text`, `4` → `StoredProcedure`, and `512` → `TableDirect`. This extension applies uniformly to both local source and decompiled input; it is not a decompile-only special case.
- The decompile step only runs for a receiver type that is unresolved against the local wrapper registry and against the active contract registry, and only when it can be traced to a concrete `.csproj` reference; it never scans a directory for arbitrary DLLs.
- `ProjectScanResult.contract_preflight_proposals` / `contract_proposals` (already present but currently always empty) are populated with the decompiled snapshot proposal when this path succeeds. `run_contract_preflight()`'s existing consumption of these fields via `_iter_scan_proposals` requires no change.
- Completeness validation reuses the existing `validate_implementation_snapshot` rules (identity fields present, every relevant operation has a resolved method identity, argument roles, connection behavior boundary, `effective_command_semantics`, and `terminal_sink`, no unresolved overloads, single assembly revision) and adds one more failure reason specific to decompiled input: any decompiler-reported translation problem for a relevant operation makes the snapshot incomplete.
- Assembly identity (`artifact_identity`/`assembly_identity`/`assembly_revision`) for a decompiled snapshot is derived from the SHA-256 hash of the DLL's bytes rather than its `AssemblyName`/`Version` string. A byte-identical DLL is the same revision; any other byte sequence is a new revision, regardless of whether its `AssemblyVersion` changed.
- A decompilation attempt's outcome (complete, incomplete with reasons, or not attempted) is cached keyed by the DLL's hash so that an unchanged DLL is not re-decompiled on every refresh. The cache is invalidated only when the hash changes or an explicit re-run is requested; it is a separate concern from the existing C# source-scan cache.
- A contract produced from a decompiled snapshot is staged and committed through the existing two-file atomic transaction (`service/contract_transaction.py`) exactly like any other complete preflight proposal; no new commit mechanism is introduced.
- Every registry entry created from a decompiled snapshot records a distinct evidence-kind/provenance marker (for example `decompiled_auto`), separate from and in addition to the existing `contract_lifecycle_status` (`reused`/`created`/`preflight_failed`/`conflicted`/etc.). This marker is additive to the response schema (`RefreshResponse`'s wrapper summary and the registry entry itself) and does not change any existing field's meaning.
- Decompilation-based onboarding is subject to every existing precondition from the `unified-database-invocation-classification` spec and ADR 0004: it only runs when the selector is unspecified, only for a full-system refresh (never program-scoped), it never overrides a valid explicit selector, and local source-backed implementation evidence remains stronger than a decompiled contract if both are somehow available.
- "Selector is unspecified" (US2) is read as *no selector was ever configured*, not merely *the configured selector currently fails to resolve*. `normalize_contract_selector()` reports `status="unspecified"` even for a selector that was given but is broken (`selector_contract_not_found`, `selector_type_invalid`) — it also sets a non-empty `reason` in exactly that case. `refresh_source` treats a non-empty `reason` the same as a resolved/valid selector for decompile-gating purposes, i.e. it disables decompile-based onboarding whenever the operator configured *something*, even if that something is currently broken. This is the stricter, fail-closed reading of US2's "an explicitly configured contract remains fully authoritative and is never second-guessed by an automatic decompile": a broken selector is still an explicit, deliberate operator choice, and silently falling back to auto-decompile would second-guess it exactly as US2 forbids. An operator who wants decompile onboarding for a system with a broken selector must clear the selector, not rely on it being reinterpreted as absent.
- This feature narrows the specific "no automatic DLL decompilation" clause in ADR 0004 and the companion spec's Out of Scope; a new ADR documents the narrower, conditional replacement rather than editing the historical ADR in place.
- `CONTEXT.md` gains entries for `Implementation Snapshot`, `Verified Implementation Snapshot`, and `Assembly Revision Boundary`, reflecting terms already used by the existing spec but not yet captured in the glossary.

## Testing Decisions

- The highest-value seam is `run_contract_preflight()`, exercised the same way `tests/test_refresh_contract_preflight.py` already does: a synthetic `ProjectScanResult`/`SimpleNamespace` carrying a `contract_proposals` entry shaped like what the decompile step would produce. Most tests assert externally observable outcome (onboarding status, staged registry entry, formal selector, evidence-kind provenance marker) through this seam, not through StaticAnalyzerHost's internal decompiler wiring.
- A narrow, StaticAnalyzerHost-level test verifies that the `CommandType` resolution logic recognizes a numeric cast (`(CommandType)4`, `(CommandType)1`) exactly as it already recognizes the named member access, using a small synthetic C# fixture — this is the concrete gap found while inspecting real decompiled output during this session, and is the one behavior that cannot be verified purely through the Python-side seam.
- One bounded end-to-end smoke test decompiles a real fixture DLL (the checked-in `SQLFunc.dll` already present under `data/repos/System_Dept_1/STC/STC/bin/`) through the real `StaticAnalyzerHost` and asserts that at least one fixed-stored-procedure method and one fixed-inline-SQL method are classified correctly and that `SqlDataAdapter.Fill` remains a distinct sink — matching the existing pattern where "one end-to-end smoke test may use the real StaticAnalyzerHost."
- Tests assert on typed facts only (mode, sink, overload identity, evidence-kind provenance, cache hit/miss) — never on decompiler-internal syntax tree shape, IL offsets, or decompiled text formatting.
- Cache-by-hash tests verify that a second refresh against an unchanged DLL does not re-invoke decompilation, and that a changed DLL hash does trigger a fresh attempt.
- Completeness-rejection tests verify that a decompiler-reported translation problem on any relevant method makes the snapshot incomplete and leaves the wrapper `unresolved` with `contract_preflight_failed`, reusing the existing incomplete-proposal test pattern in `tests/test_refresh_contract_preflight.py`.
- Precondition tests verify that a program-scoped refresh never triggers decompilation-based onboarding, and that a valid existing `wrapper_contract` selector prevents it exactly as it already prevents source-backed onboarding, reusing the existing seams in `tests/test_program_refresh.py` and `tests/test_refresh_contract_preflight.py`.
- No test requires network access to fetch a decompiler package; the dependency is a build-time NuGet reference resolved like the project's existing `Microsoft.CodeAnalysis`/`Microsoft.SqlServer.TransactSql.ScriptDom` references.

## Out of Scope

- Any human review or approval step for a decompiled snapshot that already passes the automatic completeness check — that trust decision was made explicitly in this spec; the existing explicit-acceptance tool remains available separately for cases that fail the automatic check.
- Scanning a directory or `bin/` folder for arbitrary DLLs — only a DLL traceable to an unresolved wrapper receiver's `.csproj` reference is ever decompiled.
- Decompilation-based onboarding during a program-scoped/partial refresh — this remains full-system-refresh only.
- Weakening any existing rule about `Evidence Status`, `SP Catalog` validation, connection-source resolution, or the separation between `wrapper_contract` selection and procedure proof.
- Overriding a valid, explicitly configured `wrapper_contract` selector.
- Reverse-engineering obfuscated, encrypted, or otherwise non-decompilable assemblies, or assemblies with no resolvable `.csproj` reference.
- Changing the two-file atomic commit/rollback mechanism itself.
- Selecting or pinning a specific decompiler library version as part of this spec — that is an implementation detail for the agent building this feature.
- Combining decompiled evidence from two different DLL revisions into one synthetic snapshot.

## Further Notes

This spec was produced from a grilling session that started from a real failure: running `refresh_cli STC` produced `contract preflight: onboarding=preflight_failed` because `SQLFunc.dll` had no available implementation evidence. Manually decompiling `SQLFunc.dll` during that session (via the editor's built-in Metadata-as-Source decompilation) confirmed two concrete facts that shaped this spec: the decompiled method bodies are complete and readable (no untranslatable regions), and `CommandType` is rendered as a numeric cast (`(CommandType)4`) rather than a named member — which the existing classification logic does not yet recognize. The same inspection also surfaced a real, previously uncatalogued behavior divergence (`SQLFunc.CreateAdapter` is fixed stored-procedure while `SQLFunc.CreateAdapterTsql` is fixed inline text), which is exactly the kind of name-based assumption the broader `unified-database-invocation-classification` effort already warns against.

This feature is a deliberate, narrow amendment to ADR 0004's prior boundary, not a wholesale reversal of it: automatic decompilation is permitted only under the specific conditions enumerated here (unspecified selector, full-system refresh, hash-based identity, automatic completeness judgment including decompiler-error detection, provenance-tagged output, cached-by-hash re-run avoidance). Every other safety property from the `unified-database-invocation-classification` spec — Evidence Status, SP Catalog validation, connection-source separation, selector precedence — is inherited unchanged.
